Lab Upload — how it works today

Users drag a lab PDF/image/ZIP into the widget. A Claude Haiku call extracts target metrics, the server resolves units to SI, and the user confirms before bulk-saving to Supabase. This document maps the current pipeline against the failure path a customer recently reported, to ground the upcoming redesign discussion.

Shipped: v341, March 2026 · commits 296d9ab, dee69c2, 06aa627 Companion doc: docs/lab-upload.md (implementation detail) Status: Redesign under consideration
Customer report — Dr. Michael J. Schmidberger (physicist)
"Health Roadmap parsed my Apo-B incorrectly. It parsed 0.79 from the PDF, but the PDF states 0.5 g/L. I tried to explain to the AI that this value was incorrect, but the AI could not change it. Therefore it kept giving me advice centred around this (very important) marker, which was completely wrong for me."

His two asks: 1 Dual OCR with consensus — discard values when two engines disagree. 2 Let users correct values from the menu.

1 · End-to-end data flow

Three trust zones: the browser (file parsing), the Remix backend (LLM proxy + unit resolution), and Supabase (storage). Raw PDFs never leave the browser — only extracted text or page images are sent to the LLM. The backend never persists the file.

Hardcoded system prompt + server-side unit resolution mean the client never sees extraction logic. The dashed return arrow carries { metric, valueSI, displayValue, displayUnit, confidence, question? }.

2 · Performance: extraction pipelining

Single LLM call per file. The widget runs a producer/consumer pipeline (processPipeline() in UploadModal.tsx) so file extraction overlaps with the in-flight LLM call. The producer extracts pages (pdf.js, JSZip, canvas); the consumer sends them to the LLM.

Concurrency = 1 at the LLM step: while (activeWorkers < 1 && queue.length > 0) at UploadModal.tsx:313. Set in commit 011b906 (Mar 27 2026) when the pipeline was rewritten to overlap extraction with the in-flight LLM call.

Why concurrency 1 today (and what unblocks more)

  • Anthropic Build Tier 1 cap. 10K output tokens/min. Unified extraction emits up to ~4K output tokens per file (markdown conversion of scans/letters is the worst case). Two concurrent files = ~8K/min (safe); three = ~12K/min (429s).
  • The pipelining trick. Because pdf.js extraction (~3–5s for scanned PDFs) and the LLM call (~5s) are roughly equal in duration, overlapping them gives the same wall-clock as concurrency 2 *if* extraction is the bottleneck. For text-heavy PDFs where extraction is fast (<1s), the LLM dominates and concurrency 2 would clearly win.
  • Server-side retry on 429. callAnthropic() in anthropic.server.ts retries twice with exponential backoff. So even at concurrency 2 on Tier 1, occasional 429s are absorbed silently (with added latency).
  • Bumping to concurrency 2 is a one-character change (< 1 → < 2) once Tier 2 is confirmed. No queue/UI refactor needed.

A separate path: Anthropic Batch API for 20+ files

The widget routes uploads of ≥ BATCH_THRESHOLD files through processBatch() → Anthropic Batch API instead of the interactive pipeline. This is 50% cheaper per call but async with up to 24h SLA (typically minutes). Used for bulk historical imports (ZIP of a decade of lab reports), not the common 1–5 file case. Polled via /api/lab-import?batchId=<id>.

Implemented in widget-src/src/components/UploadModal.tsx. Linear flow with one cancel path.

4 · LLM extraction contract

The system prompt lives in app/lib/anthropic.server.ts (hardcoded server-side so a malicious PDF can't override it). One LLM call per file. Two prompts exist: SYSTEM_PROMPT (lab-only, legacy) and UNIFIED_SYSTEM_PROMPT (classify + extract or convert to markdown). Both target the same 11 core metrics.

Target metrics (11)

ldl · hdl · total_cholesterol · triglycerides · hba1c · creatinine · apob · psa · lpa · systolic_bp · diastolic_bp

Anything outside this list goes to additionalValues (unified) or unrecognized (legacy).

Critical rules in the prompt

  1. Extract measured values only — never reference ranges or targets
  2. If current + previous shown, take only the most recent
  3. Use the collection date, not the print/report date
  4. Ambiguous dates: DD/MM/YYYY for non-US labs, else low confidence
  5. Uncertain values → confidence: "low" + a question string

Output schema (after server-side unit resolution)

// per file, returned by /api/lab-import
{
  "reportDate": "2024-11-21",
  "values": [
    {
      "metric": "apob",
      "valueSI": 0.79,           // saved to DB
      "displayValue": 0.79,      // what the LLM read
      "displayUnit": "g/L",
      "confidence": "high",      // LLM's self-rating
      "question": undefined
    }
  ],
  "additionalValues": [ /* sodium, ferritin, alt, … */ ],
  "unrecognized": [ "vitamin D: 45 ng/mL" ],
  "document": null                // non-null for scans, letters, etc.
}

5 · Unit resolution decision tree

The LLM returns a unit string like "mg/dL" or "g/L". The backend converts to SI canonical via resolveUnit() in app/lib/anthropic.server.ts. The lookup table is built from UNIT_DEFS (auto-populated) plus a handful of manual aliases.

Note: the resolver only downgrades confidence on a lookup miss. A lookup hit always trusts the LLM's self-rating — including when the LLM misread the digit itself. This is the trust seam that Michael's case sits on.

UNIT_LOOKUP for ApoB (today)

KeyMaps toSource
g/lSIauto from UNIT_DEFS.apob.label.si
mg/dlconventionalauto from UNIT_DEFS.apob.label.conventional
mg/dl (alias)conventionalmanual addAlias() — redundant

ApoB SI canonical = g/L, validation range 0–3. Conventional = mg/dL, range 0–300. So both 0.5 g/L and 0.79 g/L (and 50 mg/dL, 79 mg/dL) are in range — nothing here will catch a digit misread.

6 · Confidence semantics — what each label means today

LevelSet when…What the UI does with it
high LLM self-rated "high" and the unit was a direct lookup hit Row pre-checked. No question shown.
medium LLM rated "medium", OR LLM rated "high" but unit was inferred via range fallback Row pre-checked. question string shown below row if present.
low LLM rated "low" (ambiguous date, both current+previous visible, etc.) Row pre-unchecked. question string shown.

Confidence is advisory, not gating. Nothing in the pipeline cross-checks the LLM against itself or against a second engine. Confidence comes entirely from the LLM's own introspection, which it is not particularly good at when the input is a low-resolution scanned PDF.

7 · Storage map

Three tables receive data from one upload. All writes carry source: 'lab_import' for future filtering.

TableReceivesSchema highlightsMutable?
health_measurements The 11 core metrics — converted to SI canonical metric_type, value (SI), recorded_at, source, external_id No append-only (no UPDATE policy)
lab_values Everything else numeric (sodium, ferritin, alt, etc.) — stored as-is metric_name, value, unit, reference_low/high No append-only
health_documents Non-lab classifications (scans, clinic letters, discharge summaries…) document_type, title, content_md, metadata JSON Delete-only

What is not stored: the original PDF, the LLM response, the extracted text/images, the displayValue/displayUnit pair, or the confidence rating. After save, all we have is the SI value, the date, and the source tag. There is no audit trail back to "which upload session produced this row".

8 · The correction gap

Once a wrong value is saved, here is what a user can — and cannot — do today.

What works

  • Re-upload the corrected PDF — produces a new measurement at the same date. But: duplicate detection (same metric + same date prefix) flags it as "Already saved" and pre-unchecks it.
  • Type a new value into the longitudinal field and click Save — adds a new row at today's date.
  • Delete a single measurement from the history view (DELETE /api/measurements with measurementId).

What doesn't work

  • No edit-extracted-value UI. The review-table value cell is a <span> (ReviewTable.tsx:428). User can uncheck but not type a corrected number.
  • Chatbot is read-only against measurements. Telling it "that ApoB is wrong" can't change health_measurements. The system prompt has no tool to update measurements; the row stays in chat context and continues to drive advice.
  • Append-only history. Once saved, a row can be deleted but never edited. The original wrong value can never be transformed in place.
  • No re-OCR path. No "the LLM got this wrong, try a different model" affordance.

9 · Tracing Michael's ApoB failure through the pipeline

Reconstructing the path his 0.5 g/L took to become a stored 0.79 g/L. Marked steps: ● bug occurs · ● intervention point missing.

1

PDF uploaded, page rendered to image

His lab report's ApoB row reads 0.5 g/L. pdf.js sees a thin text layer (or none), falls back to canvas rendering at 1.5× scale, sends as JPEG base64.

widget-src/src/lib/pdf-extract.ts

2

Claude Haiku 4.5 misreads the digit

Vision pass returns { metric: "apob", value: 0.79, unit: "g/L", confidence: "high" }. The character "5" was misread as "79", or — more likely — Haiku picked up an adjacent value (a reference-range edge, a different row, a previous result). Both rules 1 and 2 in the system prompt warn against this, but the model is the only thing enforcing them.

app/lib/anthropic.server.ts:180–212 (SYSTEM_PROMPT) · model: claude-haiku-4-5-20251001

3

Unit resolution: lookup hit

norm("g/L") = "g/l" → UNIT_LOOKUP.apob["g/l"] = "si" → valueSI = 0.79, confident: true. No fallback, no confidence downgrade.

app/lib/anthropic.server.ts → resolveUnit() · ApoB SI range 0–3 (0.79 fits cleanly)

4

Review table renders value as read-only text

Row shows 0.79 g/L · high · checkbox pre-checked. Michael sees the wrong number on screen but has no input to fix it. He clicks Save anyway (or accepts the default), since the alternative is just not saving.

widget-src/src/components/ReviewTable.tsx:428 — <span className="review-row-value">

5

Bulk save

POST /api/measurements { bulkMeasurements: [{ metricType: "apob", value: 0.79, recordedAt, source: "lab_import" }] }. Row inserted into health_measurements. No displayValue, displayUnit, or confidence retained.

app/routes/api.measurements.ts:353–385

6

Suggestion engine fires on 0.79 g/L

ApoB 0.79 g/L is high; cascade suggests escalating lipid therapy. Suggestions render in the widget and in any reminder email.

packages/health-core/src/suggestions.ts (ApoB-driven cascade)

7

User tells the chatbot "this is wrong"

Chat has the value in latestValues.apob = 0.79. It can acknowledge the complaint but cannot write to health_measurements — there is no tool for that. It also has no way to know the value came from an upload (the source field isn't in chat context). So next turn, it keeps recommending based on 0.79.

app/lib/chat.server.ts → assembleChatContext() · app/lib/chat-system-prompt.md

8

Only escape hatch: delete + re-enter

Michael's options are (a) delete the row from history then type 0.5 manually, or (b) accept the wrong value lives in his history forever. Neither was discoverable from his vantage point, so he emailed instead.

10 · Where Michael's asks would intervene

Ask 1 — dual OCR with consensus

Intervenes at step 2 of the trace. Today's pipeline trusts a single Haiku call. Possible shapes:

  • Two Claude calls with different temperatures or different prompts; require value-level agreement to mark confidence: high.
  • Claude + a non-LLM OCR (Tesseract or a vendor) for the numeric fields; consensus required, otherwise downgrade to low (pre-unchecked).
  • Same prompt, two models — Haiku + Sonnet, or Haiku + a vision-OCR specialised model. Cheaper than Sonnet-twice; catches digit misreads of the kind Michael hit.

Worth noting: today, confidence is advisory. A consensus check only helps if disagreement actually blocks the value from being pre-checked. That's a UX call.

Ask 2 — let users correct values

Intervenes at steps 4 and 7 of the trace. Two surfaces:

  • Edit during review — turn <span className="review-row-value"> into an editable input. Cheapest change; catches the bug at the strongest moment (user is looking at the PDF and the extracted value side by side).
  • Edit after save — currently impossible because health_measurements has no UPDATE RLS policy. Would require either making rows mutable (breaks the audit-trail design) or modelling a correction as delete + insert with a paired corrects_id reference.

Other intervention points worth thinking about

  • Validation ranges as guard rails: ApoB < 0.3 or > 2.5 g/L is rare enough to warrant a "double-check this" prompt. Today, anything in the wide validation range passes silently.
  • Cross-metric sanity: if LDL and ApoB both extracted, they should roughly correlate. A digit misread on one would show up. Not currently checked.
  • Show the PDF alongside the value: the v2 list in lab-upload.md already mentions "OCR confidence preview — show rendered PDF page alongside extracted values for visual verification". This is the same idea.
  • Chatbot write tool: a correct_measurement tool exposed to the bot would let "this ApoB is wrong, it's 0.5" actually update the row. Not free — opens a write surface that needs careful confirmation UX.
  • Tag every measurement with provenance: persist displayValue, displayUnit, model name, confidence, and a hash of the source PDF page. Lets us go back and re-OCR with a better model when one ships.

11 · Design decisions that constrain the redesign

Sourced from docs/lab-upload.md §"Design Decisions" plus what was verified live in the code. These are the load-bearing choices a redesign should either preserve or knowingly overturn.

DecisionWhy it was chosenWhat overturning it would cost
Server-side system prompt Prevents prompt injection — a malicious PDF can't override extraction instructions because the content is in the user message, not the system prompt. Security regression. Don't overturn.
Never auto-save Health data, no exceptions. Every value passes through an explicit user confirmation step. HIPAA + user-trust regression. Don't overturn.
HMAC auth on every endpoint App-proxy convention. Any new endpoint (re-extract, correction) must follow the same pattern. Security regression. Don't overturn.
Append-only health_measurements Mirrors the Apple Health model — measurements are facts at a moment in time. No UPDATE RLS policy. Maintains a clean audit trail. FHIR/audit story changes. Overturning is a deliberate tradeoff worth discussing in the redesign — see "in-place vs replaces vs delete-and-re-add" below.
Server-side unit resolution Centralises all unit logic in units.ts + anthropic.server.ts. Client receives values ready to save. Duplicated logic, more places to drift. Preserve.
One LLM call per file (no cross-file batching in the prompt) Prevents cross-contamination between files from different dates/labs/patients. Simpler error handling — one file fails, others unaffected. Save a few cents per upload, gain a tangled prompt and harder failure-mode reasoning. Preserve.
Pipelined producer/consumer at concurrency 1 Today: a deliberate match to Anthropic Build Tier 1's 10K output tokens/min cap. The pipelining trick keeps the API busy near-continuously even at concurrency 1. If on Tier 2, raising to concurrency 2 is a one-character change (< 1 → < 2) and gives ~40% wall-clock improvement for 3–5 file uploads.
Claude Haiku 4.5 (not Sonnet) Structured parsing, not complex reasoning. ~$0.003–0.005 per report. Vision support for scanned pages. Swap model ID to Sonnet for ~10× cost if accuracy issues persist after other fixes. No code changes beyond the constant.
No raw PDF storage Privacy-first. Files never leave the browser; only extracted text/images reach the backend. Backend never persists the file. Storing PDFs opens HIPAA scope, S3 costs, encryption-at-rest requirements. Don't overturn lightly.
Confidence is advisory, not gating Low-confidence rows are pre-unchecked (ReviewTable.tsx:144) but still visible — the user can override and save them. The system never silently drops a value. Switching to "gating" (refuse to display low-confidence values) would prevent some bad saves but force users to re-upload more often. Status quo treats the user as the final arbiter.

The append-only question, in FHIR terms

The current design follows Apple HealthKit's "delete + re-add" pattern. FHIR's official answer is different: it uses the entered-in-error status on the original Observation resource, optionally with a new Observation that references it via replaces. Both records remain visible in history; only the corrected one is canonical. This is closer to "soft delete + replacement record" than to "UPDATE in place." A redesign that needs to support post-save correction has three flavours:

  1. Delete + re-enter (today). One row in DB after the fix. Loses the "this used to read 0.79" audit trail. Cheap to implement.
  2. FHIR-style replacement. Mark old row entered-in-error, insert new row with corrects_id → old.id. Two rows in DB, history view filters by status. Needs a schema column + a small RLS-update policy on a single boolean.
  3. True in-place UPDATE. Lose the prior value entirely. Cheapest UX, worst audit story. Not recommended.
