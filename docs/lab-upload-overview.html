Lab Upload — how it works

Users drag a lab PDF/image/ZIP into the widget. Claude Haiku calls extract target metrics in parallel, the server resolves units to SI, the user reviews and (optionally) edits each value before bulk-saving. Saved values are correctable via a FHIR replaces pattern — original values are preserved as entered-in-error, never overwritten.

1 · End-to-end data flow

Three trust zones: the browser (file parsing), the Remix backend (LLM proxy + unit resolution), and Supabase (storage). Raw PDFs never leave the browser — only extracted text or page images are sent to the LLM. The backend never persists the file.

Hardcoded system prompt + server-side unit resolution mean the client never sees extraction logic. The dashed return arrow carries { metric, valueSI, displayValue, displayUnit, confidence, question? }.

2 · Performance: parallel extraction + LLM workers

The widget runs a producer/consumer pipeline (processPipeline() in UploadModal.tsx). 3 parallel pdf.js extractors feed a queue; 5 LLM workers drain it. Wall-clock for a 12-file ZIP drops from ~50s (concurrency 1) to ~12s (the longest-LLM-call + queue drain). Verified live in Chrome DevTools: max 5 concurrent /api/lab-import calls in flight.

LLM_CONCURRENCY = 5 + EXTRACT_CONCURRENCY = 3 in UploadModal.tsx. The producer is a worker pool over a shared extractIndex (safe on single-threaded JS); the consumer is tryStartWorker() draining the queue with up to 5 LLM calls in flight.

Why 5 + 3

  • Anthropic Build Tier 2 cap. 80K output tokens/min. Lab-report extraction emits ~500–1,500 output tokens per call (scan/letter markdown conversion is the worst case at ~4K). 5 concurrent calls × 1.5K avg ≈ 7.5K/min — comfortable.
  • Extraction parallelism unblocks the pipeline. pdf.js extraction is CPU-bound on the main thread (~2–3s per file). With 1 extractor, LLM workers starve — they finish in ~5s but the next item isn't ready. 3 extractors keep the queue feeding 5 workers without UI jank.
  • Server-side retry on 429. callAnthropic() in anthropic.server.ts retries twice with exponential backoff. Absorbs occasional bursts above the per-second cap.
  • Verified in production: 13-call upload on 12-file ZIP showed maxConcurrent = 5 in DevTools timing (commit 052ada1).

A separate path: Anthropic Batch API for 20+ files

The widget routes uploads of ≥ BATCH_THRESHOLD files through processBatch() → Anthropic Batch API instead of the interactive pipeline. This is 50% cheaper per call but async with up to 24h SLA (typically minutes). Used for bulk historical imports (ZIP of a decade of lab reports), not the common 1–5 file case. Polled via /api/lab-import?batchId=<id>.

4 · LLM extraction contract

The system prompt lives in app/lib/anthropic.server.ts (hardcoded server-side so a malicious PDF can't override it). One LLM call per file. Two prompts exist: SYSTEM_PROMPT (lab-only, legacy) and UNIFIED_SYSTEM_PROMPT (classify + extract or convert to markdown). Both target the same 11 core metrics.

Target metrics (11)

ldl · hdl · total_cholesterol · triglycerides · hba1c · creatinine · apob · psa · lpa · systolic_bp · diastolic_bp

Anything outside this list goes to additionalValues (unified) or unrecognized (legacy).

Critical rules in the prompt

  1. Extract measured values only — never reference ranges or targets
  2. If current + previous shown, take only the most recent
  3. Use the collection date, not the print/report date
  4. Ambiguous dates: DD/MM/YYYY for non-US labs, else low confidence
  5. Uncertain values → confidence: "low" + a question string

Output schema (after server-side unit resolution)

// per file, returned by /api/lab-import
{
  "reportDate": "2024-11-21",
  "values": [
    {
      "metric": "apob",
      "valueSI": 0.79,           // saved to DB
      "displayValue": 0.79,      // what the LLM read
      "displayUnit": "g/L",
      "confidence": "high",      // LLM's self-rating
      "question": undefined
    }
  ],
  "additionalValues": [ /* sodium, ferritin, alt, … */ ],
  "unrecognized": [ "vitamin D: 45 ng/mL" ],
  "document": null                // non-null for scans, letters, etc.
}

5 · Unit resolution decision tree

The LLM returns a unit string like "mg/dL" or "g/L". The backend converts to SI canonical via resolveUnit() in app/lib/anthropic.server.ts. The lookup table is built from UNIT_DEFS (auto-populated) plus a handful of manual aliases.

Note: the resolver only downgrades confidence on a lookup miss. A lookup hit always trusts the LLM's self-rating — including when the LLM misread the digit itself. This is the trust seam that Michael's case sits on.

UNIT_LOOKUP for ApoB (today)

KeyMaps toSource
g/lSIauto from UNIT_DEFS.apob.label.si
mg/dlconventionalauto from UNIT_DEFS.apob.label.conventional
mg/dl (alias)conventionalmanual addAlias() — redundant

ApoB SI canonical = g/L, validation range 0–3. Conventional = mg/dL, range 0–300. So both 0.5 g/L and 0.79 g/L (and 50 mg/dL, 79 mg/dL) are in range — nothing here will catch a digit misread.

6 · Confidence semantics — what each label means today

LevelSet when…What the UI does with it
high LLM self-rated "high" and the unit was a direct lookup hit Row pre-checked. No question shown.
medium LLM rated "medium", OR LLM rated "high" but unit was inferred via range fallback Row pre-checked. question string shown below row if present.
low LLM rated "low" (ambiguous date, both current+previous visible, etc.) Row pre-unchecked. question string shown.

Confidence is advisory, not gating. Nothing in the pipeline cross-checks the LLM against itself or against a second engine. Confidence comes entirely from the LLM's own introspection, which it is not particularly good at when the input is a low-resolution scanned PDF.

7 · Storage map (FHIR Observation)

Three tables receive data from one upload. health_measurements follows the FHIR R4 Observation shape: rows are immutable except for the status column, which is mutated only by the correct_measurement RPC (§10).

TableReceivesSchema highlightsMutability
health_measurements The 11 core metrics — converted to SI canonical metric_type, value (SI), recorded_at, source, external_id, status ('active' | 'entered-in-error'), corrects_id (self-FK) Status-only via RPC
lab_values Everything else numeric (sodium, ferritin, alt, etc.) — stored as-is metric_name, value, unit, reference_low/high No append-only
health_documents Non-lab classifications (scans, clinic letters, discharge summaries…) document_type, title, content_md, metadata JSON Delete-only

source enum values (MEASUREMENT_SOURCES in validation.ts)

ValueWhen it's used
manualUser typed into the form (default)
lab_importLLM-extracted, not edited at review time
lab_import_editedLLM-extracted then user-corrected at review time (tracks digit misreads caught early)
manual_correctionInserted by the correct_measurement RPC (post-save correction)
apple_health, fitbitFuture HealthKit-style imports

Partial UNIQUE index uniq_measurements_user_metric_active on (user_id, metric_type, recorded_at) WHERE status = 'active' — guarantees at most one active row per slot. Historical entered-in-error rows coexist freely. A duplicate active insert surfaces as Postgres 23505 → mapped to HTTP 409 with "Use the correction UI to update it."

What is not stored: the original PDF, the LLM response, the extracted text/images, the displayValue/displayUnit pair, or the confidence rating. After save, all we have is the SI value, the date, the source tag, the status, and any corrects_id link.

8 · Corrections — review-edit + click-to-correct

Two surfaces let the user fix a wrong value, intervening at different moments:

① Edit at review time

In ReviewTable.tsx, each value cell is a numeric input (type="text", inputMode="decimal", locale-aware so 0,5 and 0.5 both parse). User types over the LLM's extraction before clicking Save. An "edited from 1.5" badge renders inline so the change is visible.

  • Edited rows save with source: 'lab_import_edited'.
  • Unedited rows save with source: 'lab_import' (server default).
  • Catches the bug at the strongest moment: user is looking at the PDF and the extracted value side-by-side.

② Click-to-correct after save

In BloodTestTimeline.tsx, every saved value is a clickable button (bt-cell-clickable, title="Click to correct this value"). Clicking opens an inline edit form. Enter or click-away saves (if validation passes); Escape discards. Behind the scenes:

  1. Widget calls correctMeasurement(oldId, newValueSI) → POST /api/measurements.
  2. The correct_measurement RPC (§10) flips the old row's status to entered-in-error AND inserts a new row with source='manual_correction' + corrects_id=oldId.
  3. Audit log records MEASUREMENT_CORRECTED with {oldId}.
  4. Widget optimistically patches local state — no refetch unless the row vanished mid-flight (rare).

Failure modes the UI surfaces

  • 409 conflict. Another value was saved at this (metric, date) during the round-trip. Server returns 409; widget shows "Another value was saved at this date. Refresh and try again."
  • 404 not found. Row missing, not owned, or already corrected. Widget shows "This value was deleted or already updated. Refresh to see the latest."
  • Network error. Form stays open with "Could not save. Check your connection and try again." — user can retry without re-typing.

Re-upload behaviour (idempotent)

Re-uploading the same ZIP shows an "Already saved" badge on every row whose (metric, recorded_at) matches an existing active row. The checkbox is pre-unchecked. If the user force-re-checks and clicks Save, the server's partial UNIQUE index rejects the dupe (Postgres 23505) and the bulk handler reports it in skippedDuplicates. The done screen reads: "N values were already saved at the same date. Close this dialog and click the existing value in the Blood Test Results table to correct it."

9 · FHIR schema (status, corrects_id, partial UNIQUE)

Three additions to health_measurements + two triggers + a partial UNIQUE index. See supabase/rls-policies.sql for the canonical text (with COMMENT ON annotations).

Columns

ColumnTypeSemantics
status TEXT NOT NULL DEFAULT 'active' CHECK IN ('active', 'entered-in-error') FHIR R4 Observation status. Only active rows feed reads. Sticky forward (no revert).
corrects_id UUID REFERENCES health_measurements(id) ON DELETE SET NULL Self-FK: this row replaces corrects_id. NULL on originals. SET NULL on delete so a hard-deleted old row doesn't cascade.
Partial UNIQUE index uniq_measurements_user_metric_active ON (user_id, metric_type, recorded_at) WHERE status = 'active' — at most one active row per slot.

Defence-in-depth (4 layers)

LayerWhat it catches
L1 · Postgres grants
REVOKE UPDATE ON health_measurements FROM authenticated		 Users have no direct UPDATE permission via PostgREST, raw SQL, or the Supabase JS client. The RPC is the only writer.
L2 · RPC ownership check
WHERE user_id = auth.uid()		 The correct_measurement RPC is SECURITY DEFINER but explicitly checks auth.uid() against the row's user_id in the UPDATE step. Forged oldId values are rejected.
L3 · BEFORE UPDATE trigger
enforce_measurement_correction_only()		 Schema-resilient guard using to_jsonb(NEW) - 'status' IS DISTINCT FROM to_jsonb(OLD) - 'status'. Any column change other than status raises. Also blocks reverts away from entered-in-error.
L4 · BEFORE INSERT trigger
validate_corrects_id_ownership()		 Rejects any INSERT whose corrects_id references another user's row. Closes the cross-user FK-forge gap that RLS alone can't catch on insert.

10 · The correct_measurement RPC

Atomic UPDATE-first-then-INSERT, SECURITY DEFINER with explicit auth.uid() ownership check. Race-safe: two concurrent corrections on the same row serialise via Postgres row-locking. The loser sees ROW_COUNT = 0 and raises "not correctable". A naïve SELECT-then-UPDATE would let both calls observe status = 'active' under MVCC and produce two active replacements. 

CREATE OR REPLACE FUNCTION correct_measurement(
  old_measurement_id UUID,
  new_value          NUMERIC,
  new_recorded_at    TIMESTAMPTZ DEFAULT NULL
) RETURNS UUID AS $$
DECLARE
  old_row    public.health_measurements%ROWTYPE;
  rows_affected INTEGER;
  new_id     UUID;
BEGIN
  -- 1. Atomic lock-and-check: flip status to entered-in-error
  --    only if (a) the row is the caller's, (b) status is still 'active'.
  --    Concurrent callers serialise here — the loser gets rows_affected=0.
  UPDATE public.health_measurements
     SET status = 'entered-in-error'
   WHERE id = old_measurement_id
     AND user_id = auth.uid()
     AND status = 'active'
   RETURNING * INTO old_row;

  GET DIAGNOSTICS rows_affected = ROW_COUNT;
  IF rows_affected = 0 THEN
    RAISE EXCEPTION 'Measurement not found or not correctable';
  END IF;

  -- 2. Insert the corrected row, linked to the now-flagged old row.
  BEGIN
    INSERT INTO public.health_measurements
      (user_id, metric_type, value, recorded_at, source, corrects_id)
    VALUES
      (old_row.user_id, old_row.metric_type, new_value,
       COALESCE(new_recorded_at, old_row.recorded_at),
       'manual_correction', old_measurement_id)
    RETURNING id INTO new_id;
  EXCEPTION WHEN unique_violation THEN
    -- Another active row was inserted at this (metric, recorded_at)
    -- between our UPDATE and our INSERT. Re-raise so the route maps to 409.
    RAISE EXCEPTION 'Conflict: another value was saved at this date while you were correcting. Refresh and try again.'
      USING ERRCODE = '23505';
  END;

  RETURN new_id;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = '';

Result mapping at the API boundary (api.measurements.ts):

  • 'ok' → HTTP 200, { success: true, newId } + audit log MEASUREMENT_CORRECTED with { oldId }.
  • 'conflict' (23505) → HTTP 409 with "Another value was saved at this date while you were correcting. Refresh and try again."
  • 'not_found' → HTTP 404 with "Measurement not found or not correctable" — same message regardless of which of (missing / not owned / already corrected) so we don't leak ownership.

Appendix · Tracing Michael's ApoB failure (historical)

Pre-redesign trace. Steps 4 and 7 (the no-edit-path gaps that prompted the work) are now addressed by §8. Kept here for context on the motivating bug.

1

PDF uploaded, page rendered to image

His lab report's ApoB row reads 0.5 g/L. pdf.js sees a thin text layer (or none), falls back to canvas rendering at 1.5× scale, sends as JPEG base64.

widget-src/src/lib/pdf-extract.ts

2

Claude Haiku 4.5 misreads the digit

Vision pass returns { metric: "apob", value: 0.79, unit: "g/L", confidence: "high" }. The character "5" was misread as "79", or — more likely — Haiku picked up an adjacent value (a reference-range edge, a different row, a previous result). Both rules 1 and 2 in the system prompt warn against this, but the model is the only thing enforcing them.

3

app/lib/anthropic.server.ts → resolveUnit() · ApoB SI range 0–3 (0.79 fits cleanly)

4

Row shows 0.79 g/L · high · checkbox pre-checked. Michael sees the wrong number on screen but has no input to fix it. He clicks Save anyway (or accepts the default), since the alternative is just not saving.

8

Only escape hatch: delete + re-enter

Michael's options are (a) delete the row from history then type 0.5 manually, or (b) accept the wrong value lives in his history forever. Neither was discoverable from his vantage point, so he emailed instead.

Future interventions not in scope this round

  • Dual-OCR consensus. Two Claude calls (or Claude + a vision-OCR specialist) with value-level agreement gating confidence: high. Rejected for this round (D4 below): meaningful cost (~2× LLM spend), questionable ROI now that the user has two correction surfaces. Revisit if production correction frequency stays high.
  • Validation ranges as guard rails. ApoB < 0.3 or > 2.5 g/L is rare enough to warrant a "double-check this" prompt. The threshold helpers in units.ts already encode the ranges — wiring them into the review UI is small.
  • Show the PDF page alongside the value at review time. Strongest signal for digit-misread catches.
  • Chatbot write tool. A correct_measurement tool exposed to the bot would let "that ApoB is wrong, it's 0.5" actually update the row. Opens a write surface that needs careful confirmation UX.
  • Provenance preservation. Persist displayValue, displayUnit, model name, and a hash of the source PDF page so we can re-OCR with a better model when one ships.

11 · Design decisions (post-ship)

Load-bearing choices that future work should preserve unless deliberately overturning.

DecisionWhyWhat overturning costs
D1 · Inline-edit at review time Catches LLM digit misreads at the strongest moment — user sees the source PDF and the extracted value side-by-side. Edited rows tagged lab_import_edited for audit analytics. Reintroduces the original "no way to fix wrong extractions" gap. Don't overturn.
D2 · FHIR replaces for post-save corrections Append-only data with status mutation only via the correct_measurement RPC. Old values preserved as entered-in-error; new values link via corrects_id. Matches FHIR R4 Observation semantics and plays nicely with future EHR/Apple HealthKit export. Alternative was true-UPDATE (loses prior value) or delete-and-re-add (loses correction semantics). Either weakens the audit trail.
D3 · Concurrency 5 LLM × 3 extractors Tier 2 absorbs 5 concurrent ~1.5K-token extractions. 3 parallel pdf.js workers keep the queue feeding the LLM workers without UI jank. Bumping further hits Anthropic Tier 2's 80K/min output cap on scan-heavy uploads. Increasing extractor count hurts main-thread responsiveness.
D4 · No dual-OCR / second-engine consensus ~2× LLM spend; ROI unclear once users have two correction surfaces. Revisit if production correction frequency stays high. Deferred, not rejected — see "Future interventions" above.
Server-side system prompt Prevents prompt injection — a malicious PDF can't override extraction instructions because the content is in the user message, not the system prompt. Security regression. Don't overturn.
Never auto-save Health data, no exceptions. Every value passes through an explicit user confirmation step. HIPAA + user-trust regression. Don't overturn.
HMAC auth on every endpoint App-proxy convention. Any new endpoint (re-extract, correction) must follow the same pattern. Security regression. Don't overturn.
Server-side unit resolution Centralises all unit logic in units.ts + anthropic.server.ts. Client receives values ready to save. Duplicated logic, more places to drift. Preserve.
One LLM call per page-list (no cross-file batching in the prompt) Prevents cross-contamination between files from different dates/labs/patients. Simpler error handling — one file fails, others unaffected. Save a few cents per upload, gain a tangled prompt and harder failure-mode reasoning. Preserve.
Claude Haiku 4.5 (not Sonnet) Structured parsing, not complex reasoning. ~$0.003–0.005 per report. Vision support for scanned pages. Swap model ID to Sonnet for ~10× cost if accuracy issues persist after other fixes. No code changes beyond the constant.
No raw PDF storage Privacy-first. Files never leave the browser; only extracted text/images reach the backend. Backend never persists the file. Storing PDFs opens HIPAA scope, S3 costs, encryption-at-rest requirements. Don't overturn lightly.
Confidence is advisory, not gating Low-confidence rows are pre-unchecked but still visible — the user can override and save them. The system never silently drops a value. Switching to "gating" (refuse to display low-confidence values) would prevent some bad saves but force users to re-upload more often. Status quo treats the user as the final arbiter.
