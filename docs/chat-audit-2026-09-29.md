# Chatbot audit — 2026-09-29

Clean-slate audit of the chat stack on drstanfield.com and microvitamin.com, prompted by the release of Claude Sonnet 5.5 (`claude-sonnet-5-5`, listed on the account 2026-09-28). Method: read every chat code path and prompt, pulled 30 days of Supabase telemetry, ran the live chat as a guest on both stores through Chrome DevTools, and benchmarked Haiku 4.5 against Sonnet 5.5 on the router and classifier fixtures. A fresh Opus adversary (19 findings) and a Codex review (5) checked the first draft; every accepted finding is folded in below, and the two Codex findings that belong to another session's uncommitted work are noted in §7.

## 1. What runs today

One pipeline, four surfaces (widget chat, blog bubble + chatbot embed, Discord, YouTube auto-reply) plus a BYOK path on the Pages build.

```
message → Haiku classifier (1 label) → Haiku router (0–3 handles, 49K-token cached index) → Sonnet 5 answer (adaptive thinking, effort medium, 2 form-edit tools) → one JSON response
```

Model ids are hard-coded in 12 places across 9 files: the three server hops, lab extraction, BYOK chat, and five harnesses (router, classifier, answer-check, tool-edits, YouTube dry run). Only the main answer is on Sonnet 5; every other pin is `claude-haiku-4-5-20251001`.

30-day telemetry (Supabase, to 2026-09-29): 456 pipeline turns, of which about 222 produced an answer someone saw (YouTube 94 posted of 328 rows, the rest classifier GREETING skips and no-reply decisions; web 113, widget 38 + blog and embed 75; Discord 15). Classifier: 163 ROUTE labels plus 6 fail-open errors, so the router runs on 37% of turns. Router p50 1.36 s, p90 1.99 s; 7 failures (5 timeouts, 1 parse, 1 HTTP 400). Router returned no handle on 68 of 169 calls (web 10 of 41, YouTube 54 of 117). One main-LLM fallback. `chat_opened` fired 120 times; there is no "message sent" event.

Live guest test, desktop Chrome, 2026-09-29: drstanfield roadmap page 15.7 s from send to answer (an ApoB and ezetimibe question: correct thresholds, three DOI links, one blog link, matched `hyperlipidaemia`); microvitamin.com home 12.2 s (a MicroVitamin question: brand posture, structure-function wording, ingredient list, no drstanfield link). Both answers were clinically and posture-correct.

## 2. Findings, ranked

**F1 — Twelve model pins, three stale statements.** `docs/chat-feature.md` and `docs/architecture-v2.html` still say the chat runs on Haiku 4.5, and the router file's own comment says "same as main LLM (Haiku 4.5)". The answer-check and tool-edit harnesses test Haiku with `temperature`, so their assertions have not exercised the production model since the Sonnet 5 cutover on 2026-08-06, and they cannot run on Sonnet 5 or 5.5 as written (both 400 on `temperature`). BYOK stays on Haiku on purpose (the user pays; a chat costs under a cent) but its comment claiming to match the website is wrong. Fix: one `packages/health-core/src/models.ts` with the four production ids, deep-imported by the server files and imported by the harnesses; the harnesses also need per-family request shapes (first built in `tools/model-arm.ts`, now merged into `packages/health-core/src/models.ts` as `modelParams`, which every harness imports). Net prod LOC about 0.

**F2 — Refusals and truncation are invisible, and on YouTube a refusal loops.** Nothing reads `stop_reason`. Sonnet returns HTTP 200 with `stop_reason: "refusal"` and empty content, which today becomes "No text in Anthropic response" and the generic fallback. On YouTube (72% of pipeline rows) a fallback unclaims the comment, so the same comment is retried every 30-minute tick for up to 7 days, three model calls each time. Sonnet 5.5 declines in more categories (`general_harms` can fire on benign text), so the upgrade makes this loop more likely. A `max_tokens` stop (4096 caps thinking plus answer) truncates mid-sentence with no signal. Fix, one commit: read `stop_reason` and `stop_details.category` in `fetchAnthropicRaw` and return them; discard partial text on a refusal; a third outcome beside answer and fallback: YouTube skips the comment without unclaiming, web and Discord get a short category-aware line; log the bounded category in `chat_timing` and the Sentry tag.

**F3 — The 12–16 s wait is filled with fiction, and generation is most of it.** `THINKING_MESSAGES` rotates ten canned lines ("Reviewing your health data…", "Pulling the latest guidelines…") on a random timer, including for guests with no data. The pre-answer leg is about 2 s at the median (router p50 1.36 s, classifier about 0.6 s overlapped on Shopify); the rest of a 12–16 s turn is Sonnet generating. The pipeline does not stream: the app-proxy route returns one JSON body that also carries `proposedEdits`. Without streaming, nothing can fill the wait honestly, including Sonnet 5.5's reasoning summaries, which would arrive with the answer. Order of work: (a) replace the ten lines with one truthful status; (b) a streaming spike through the Shopify app proxy, unproven for this route and to be measured before it is promised. Showing reasoning summaries to end users is not recommended for a health chat even with streaming: summaries hedge, self-correct and name conditions the answer then rules out. Answers already carry inline DOI and blog citations; a sources footer, if wanted, must be derived from those citations, not from router handles (handles are what was loaded, not what was used, and the loader silently stops at 80K characters).

**F4 — The microvitamin.com chat copy belongs to the roadmap widget.** The FAB chat on the store opens with "Answers cite your plan & the guidelines above" and an empty state about "your personalized suggestions based on your health data". On the commerce store there is no plan and nothing above. `ChatSection` needs a surface-aware subtitle and empty state; the embed's `muted` prop is a form-stage flag, not a surface flag, so it is not reusable as is.

**F5 — Sonnet 5.5 changes one thing this pipeline relies on.** On 5.5, text the model writes before a tool call can come back as an empty `thinking` block instead of `text`, so a form-edit turn surfaces as the generic `PREFILL_ACK_MESSAGE`. That message says "review and press Save", which is wrong for medication edits, which save immediately (the undo banner mitigates). The tool-edit harness must run on 5.5 before cutover, which needs F1's harness fix first. Everything else in the current body is 5.5-compatible: no sampling params, adaptive thinking, effort set explicitly, `tool_choice` never forced, thinking blocks never replayed (history is stored as text).

**F6 — The router is patched by example, and the examples are production misses.** Of the ten web ROUTE-empty turns, at least five were real misses by the prompt's own rule 7 (a request to assess the user's data routes to the guideline entries), three were product or supply questions, two were read-back requests. YouTube: 52 of 110 ROUTE turns since 2026-09-01 returned nothing, among them statin side-effect, lithium, K2 and omega-3 questions the index covers. Three of those comments (2026-09-04 to 09-06: stopping natto, a vascular surgeon recommending K2, a cardiologist's omega-3 study) were then written into rule 6 as close paraphrases on 2026-09-24. That is the signature of a model that cannot generalise the rule, and it is the argument for testing a stronger router (§3).

**F7 — Storefront copy drift.** microvitamin.com's hero says "25 Ingredients"; `docs/products.md` (the master) says 26 for USA v8, 25 for UK/EU v7. The bot answered 26. Which is right for the US storefront is Brad's call.

**F8 — Klaviyo popups cover the chat on both stores at load.** On the roadmap page the "supplement checklist" popup sits over the embedded chat panel.

**F9 — Prompt cache misses dominate cost and latency at this volume.** Router calls within 5 minutes of the previous one: 38 of 169 (a 60-minute window would cover 78). All turns, which share the main system prefix: 170 of 456 within 5 minutes, 292 within 60. So most calls pay the cache write and the cold prefill. A 1-hour cache TTL on the router index and the main system blocks would roughly double hit rates for about the same monthly spend (1-hour writes cost 1.6x, but there are half as many); the gain is latency, not cost, and it needs measuring.

**F10 — The classifier smoke test was empty.** `tools/test-classifier.ts --runs 1` without `--concurrency` never called the API and printed "All classifier tests passed" on zero runs (flag parsing read the wrong argv slot). The documented command in `docs/loops/chat-health/LOOP.md` is that command. Fixed in this change; the harness also sent `max_tokens` 5 where production sends 8, now 8.

## 3. Haiku 4.5 vs Sonnet 5.5 on the classifier and router

Method: the production router prompt and index, the 304-query routing fixture (`tools/test-queries.json`), one run each, concurrency 2, the test-workspace key, `--model` and `--thinking-off` flags added to both harnesses for this comparison. The benchmark ran warm: the index was in cache on every counted call, which production is not (F9), so the warm columns understate production cost and latency for both models. Cold-cache figures are from five cache-busting calls per model, run separately.

| Router arm | Pass | Warm p50 / p90 | Cold p50 (n=5) | Per 1,000 warm calls | Est. per month, 169 calls at the observed 22% hit rate |
|---|---|---|---|---|---|
| Haiku 4.5, temperature 0 (today) | 281/304 (92.4%) | 1.09 s / 1.47 s | 1.0 s (0.96–2.0) | $5.07 | about $8 |
| Sonnet 5.5, thinking off (`between_tools`) | 290/304 (95.4%) | 1.31 s / 1.53 s | 2.2 s (0.8–2.5) | $15.31 | about $25 |
| Sonnet 5.5, adaptive thinking, effort low | 292/304 (96.1%) | 1.32 s / 1.82 s | not measured | $15.41 | about $25 |

No API errors on any arm. Sonnet 5.5's tokenizer counts the same index as about 77K tokens where Haiku counts 55K, so its cache writes cost 3x, not 2x. Cold Sonnet calls sit inside the router's 5 s timeout but add about 1.2 s over Haiku at the median. Every arm ran once per query, so single flips are within noise; before acting on any one, rerun its category with `--runs 3`.

The flips matter more than the totals. Sonnet 5.5 fixes 19 to 20 Haiku failures: symptom presentations (snoring and tired, lump in throat after eating, heavy periods), mechanism questions (Lp(a) and the arterial wall, why PCSK9 evolved, statin and cognitive decline), "is there a test for genetic LDL", the salt-to-potassium ratio, and three paediatric cases where Haiku picked a wrong or partial page (only 12 of Haiku's 23 failures are empty lists; the rest are wrong pages). Sonnet 5.5 newly fails 9 to 10, and most expect an EMPTY list: MicroVitamin with blood thinners or with Lixiana (Sonnet loads the DOAC, warfarin and vitamin K pathways), MicroVitamin versus AG1, simvastatin timing (a pharmacist-redirect fixture), a homemade protein shake, Brad's BPC-157, "I feel bad". This is not only wasted context. The drug-interaction fixtures exist because loaded pathway text once produced unsafe answers, and the system prompt's pharmacist redirect is a hard boundary the answer must hold against whatever was loaded. The benchmark bypasses the classifier (which sends many product questions past the router in production) and generated no answers for the over-routed cases, so the safety effect is unmeasured, not proven benign.

Classifier (18 labelled fixtures, production `max_tokens` 8): Haiku 18/18 at p50 0.64 s; Sonnet 5.5 thinking off 16/18 at p50 1.2 s (one miss is ACCOUNT versus PRODUCT, which the fixture calls equivalent; the other, "female" → ROUTE, is a documented known failure). Sonnet is twice as slow on a one-label call for no gain. Keep Haiku.

Recommendation: the router move to Sonnet 5.5 (thinking off, `max_tokens` 200, no temperature) is the right direction on retrieval quality, at about $17 a month more and about 1.2 s more on a cold call. It is gated on two things this audit did not do: run classifier → router → answer end to end on the over-route fixtures (blood thinners, Lixiana, simvastatin timing) and confirm the answer holds the pharmacist boundary; and check the production key's Sonnet 5.5 rate-limit pool, since cache writes count against it. Then retire the rule-6 example patches the new model no longer needs, one at a time with the harness as the gate, and add rule-7 wording for product-with-drug questions.

## 4. Recommendation

1. **Upgrade the main answer to Sonnet 5.5.** Same price and tokenizer as Sonnet 5, better reasoning. Keep adaptive thinking at `effort: "medium"`: thinking is the self-check against fabricated citations, and the answer-check harness (substring matching) cannot catch a fabricated DOI, so `low` is not safe to adopt on the harness alone. Handle `stop_reason` (F2) in the same commit. Run the tool-edit harness on 5.5 after F1's harness fix (F5).
2. **Router and classifier:** §3.
3. **"Always the newest Sonnet."** The Models API lists every model with `created_at`, so a boot-time "newest `claude-sonnet-*`" pick is a few lines, and it is the wrong design: every Sonnet generation so far shipped request-shape breaks (Sonnet 5 rejected `temperature`; Sonnet 5.5 rejects `disabled` thinking and forced `tool_choice`, moves pre-tool text into thinking blocks, and declines in more categories). An automatic pick would flip production to an untested model the morning it lands. The version that meets Brad's intent without that risk uses the repo's own pipeline: a weekly loop step lists models, and when a Sonnet newer than the pin exists it runs the four harnesses with `--model` (F1 makes that possible), writes the numbers into a PR that bumps the pin, and ships through the Tier 3 auto-ship veto. No manual edit, but nothing reaches production without a measured run and the 30-minute veto. A runtime env override was considered and rejected: it is an unreviewed change to clinical answer behaviour, has to be set per Fly app, and is coupled to the request shape.
4. **UI:** one truthful status line (F3a), surface-aware copy on microvitamin.com (F4), then a streaming spike (F3b), which is the only lever on the 12–16 s wait.
5. **Cache:** try a 1-hour TTL on the router index and main system blocks and measure latency (F9).
6. **Docs and pins:** F1 in one commit.

## 5. Roadmap tool linkage

On drstanfield.com the chat is the widget's step 3 ("Discuss your health") and the blog bubble sends the saved record with every message; both work as designed. On microvitamin.com there is no tool to link to: `/pages/roadmap` returns 404 and `/pages/health-plan` mounts only the site-chat bundle (known since 2026-08-07, `docs/deploy-runbook.md`, still an open decision). The brand posture also forbids linking drstanfield.com. So a store visitor who asks a health question gets an educational answer and no path to the roadmap, and CLAUDE.md plus `docs/architecture-v2.html` still say both stores serve the tool. Brad's decision: restore a tool page on the store and let the posture link it, or let the brand bot link drstanfield.com/pages/roadmap for clinical questions. Until then the store chat is a product assistant, not a roadmap entry point.
