Guardrails (do not violate)

  1. Brad never stores health data. No health values land in any database Brad runs. (Opt-in AI features transit content in-memory — never stored; see AI features.)
  2. Folder-scoped cloud access only. The app touches only its own data, never the rest of a user's cloud (enforced by access method).
  3. No client-side encryption in the default tier. Plain, open-format files. Privacy-maximalists self-host.
  4. Two-layer separation as folders in ONE public repo. Core (client + health-core + adapters) and any server code live side-by-side and deploy separately; nothing private. Secrets are env-only + scanned.
  5. The live app must not break. v2 is built in parallel; cut over only when proven; existing users' Supabase data migrates without loss.
  6. No paid tier for now — ship fully free. revised 2026-06-08 Economics ride on the supplement business + the email list; adoption first, monetize later. (Was: "charge for what needs Brad's server, billed annually.") Never paywall the advice.
  7. Honest positioning — do NOT oversell privacy. The default tier is never marketed as "encrypted/maximum privacy" (Google/Dropbox can technically read the files). Approved claim: "Your health data lives in the cloud account you already use and trust — not on our servers. We never store your health data." Never "we never see it" (the AI proxy transits content).

Rules

  • schemaVersion is forward-proofing only — built clean from v1, no back-compat layer (add a migration step only if the shape changes).

  • Email bootstrap (opt-in, the anti-spam gate): the server must learn the user's provider-verified email — never trust the client-supplied address (else an attacker connects their own cloud but types a stranger's email). Two paths: Google = the browser hands a signed ID token, server verifies the signature against Google's keys (no file-access token ever touches the server). The chosen approach.

Issued at opt-in, stored in the user's own cloud file so it follows them across devices. It authorizes in-app schedule edits AND powers the one-click unsubscribe (clicked from the inbox where the user is NOT cloud-authed; legally must be one-click → must carry a server token). We do NOT reuse the cloud token for edits — it rotates every few hours and re-sending it would re-expose the user's whole-folder key.
  • Daily cron — no token, no re-auth: it is Brad's own server reading its own stored schedule table and sending via Resend (reuse the existing email.server.ts / cron infra). It does not authenticate as the user.
  • What the server stores (the minimum): provider-verified email + due-item label (e.g. "Colonoscopy") + due date + capability token. Never lab values, results, history, the reasoning, or the cloud login/token. Data minimisation, not de-clinicalisation — reminders stay specific ("your 5-yearly colonoscopy is due"; that's the point), only the due item + date are kept. The message text is health-adjacent — accepted minimal exception. Each visit re-computes & upserts the schedule.
