1 · Goals + non-goals

Goals

  • User can edit any extracted value in the review table before saving — fixes Michael's class of failure where the LLM misreads a digit.
  • User can correct a saved measurement and the system preserves both versions in FHIR-compatible form (status: entered-in-error on the old row, new row links via corrects_id).
  • Wall-clock time for 3–10 file uploads drops by ~40–60% via concurrency 5 in the LLM pipeline.
  • Existing reads keep working unchanged at deploy time — schema migration is additive with safe defaults.

Non-goals (this round)

  • Dual-OCR consensus across two engines. Cost + complexity not justified once inline edit ships.
  • True in-place UPDATE of measurement values. Loses prior-value audit trail; FHIR-incompatible.
  • Chatbot tool to update measurements. Possible later; out of scope now.
  • Storing the raw PDF on the server.
  • Validation guard-rails on extracted values (e.g. "ApoB < 0.3 is rare — double-check"). Worth doing eventually, separate work.

2 · Decisions taken

D1 · Inline-edit the value at review time

Replace the read-only <span className="review-row-value"> at ReviewTable.tsx:428 with an editable number input. User sees the LLM's extracted value, types over it if wrong, then saves. Confidence dot stays.

D2 · FHIR entered-in-error + replaces pattern for post-save correction

Adopted instead of in-place UPDATE or silent delete-and-re-add. Old row keeps its values and gets status = 'entered-in-error'; new row links to it via corrects_id. Both remain in the database; the active-only read filter hides the old row from suggestion/chat/chart paths.

D3 · Concurrency 5 at the LLM step

Tier 2 supports it (80K output tokens/min ceiling vs ~15–45K/min sustained at conc 5 for typical lab reports). Server-side 429 retry absorbs the rare scan-heavy overflow. Beyond 5, pdf.js extraction becomes the wall-clock bottleneck — diminishing returns.

D4 · No dual-OCR / second-engine consensus

Inline edit + visual confidence dots give the user the verification step Michael actually wanted, without doubling cost or introducing "engines disagree, now what?" UI states.

3 · Open questions

Q1 · Show a thumbnail of the rendered PDF page next to each row?

Strong UX win for verification (user can scan source vs extraction without leaving the modal), but requires keeping the rendered page image in memory through the review state. Adds ~200–500KB per file to in-browser memory. Recommend: yes, but with a lazy "Show source" affordance per file rather than always-visible thumbnails. Still deferred — not in this round.

Q2 · Should correcting a saved measurement also let the user change the recorded_at date?

The RPC signature already accommodates it (new_recorded_at TIMESTAMPTZ DEFAULT NULL). Recommend: yes, allow date change as part of the correction so users can fix "LLM picked the report date not the collection date" mistakes. UI shows both a value input and a date picker in the correction form.

All other decisions resolved (see §2 D1–D4 and the consequences note in §8). The audit-mode toggle ships as a non-persisted UI state. The validation pattern matches InputPanel via reuse of UNIT_DEFS and the existing Zod schema.

4 · Schema migration

Append to supabase/rls-policies.sql. All IF NOT EXISTS / DROP/CREATE so it can run repeatedly on staging before production.

Security model: authenticated users have SELECT, INSERT, DELETE only on health_measurements. No user-facing UPDATE policy and no UPDATE GRANT. Direct UPDATEs via PostgREST are rejected at the permission layer. The only path to mutate an existing row is the correct_measurement RPC (§5), which is SECURITY DEFINER, verifies auth.uid() ownership inside, and writes an audit row. A BEFORE UPDATE trigger remains as defence-in-depth against bugs in the RPC itself or future SECURITY DEFINER additions that touch the table. 

-- 4.1 Add columns
ALTER TABLE health_measurements
  ADD COLUMN IF NOT EXISTS status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'entered-in-error'));

ALTER TABLE health_measurements
  ADD COLUMN IF NOT EXISTS corrects_id UUID REFERENCES health_measurements(id)
    ON DELETE SET NULL;
-- ON DELETE SET NULL: if a referenced entered-in-error row is hard-deleted via
-- DELETE /api/measurements, the corrector's link is nulled instead of cascading.
-- Audit mode renders the corrector with no "replaces" arrow. Honest about the gap.

-- 4.2 Partial index for the common "active only" reads
CREATE INDEX IF NOT EXISTS idx_measurements_user_active
  ON health_measurements(user_id, metric_type, recorded_at DESC)
  WHERE status = 'active';

-- 4.3 Explicitly REMOVE any direct-UPDATE pathway. The RPC in §5 is the only writer.
DROP POLICY IF EXISTS "Users can correct own measurements" ON health_measurements;
REVOKE UPDATE ON health_measurements FROM authenticated;
-- Confirm the only writes available to authenticated are INSERT + DELETE:
-- GRANT SELECT, INSERT, DELETE ON health_measurements TO authenticated;  (already set)

-- 4.4 BEFORE UPDATE trigger — schema-evolution-resilient (to_jsonb minus status)
-- so new columns added later are automatically locked down. Final line of defence
-- against a bug in the RPC or any future SECURITY DEFINER function.
CREATE OR REPLACE FUNCTION enforce_measurement_correction_only()
RETURNS TRIGGER AS $$
BEGIN
  -- Reject any UPDATE that changes columns other than status
  IF (to_jsonb(NEW) - 'status') IS DISTINCT FROM (to_jsonb(OLD) - 'status') THEN
    RAISE EXCEPTION 'health_measurements is append-only; only status may change (via correct_measurement RPC)';
  END IF;
  -- Forward-only: entered-in-error is sticky
  IF OLD.status = 'entered-in-error' AND NEW.status != 'entered-in-error' THEN
    RAISE EXCEPTION 'status cannot be reverted from entered-in-error';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SET search_path = '';

DROP TRIGGER IF EXISTS trg_measurement_correction_only ON health_measurements;
CREATE TRIGGER trg_measurement_correction_only
  BEFORE UPDATE ON health_measurements
  FOR EACH ROW EXECUTE FUNCTION enforce_measurement_correction_only();

-- 4.5 Optional: INSERT-time validation that corrects_id (if set) belongs to the same user.
-- Closes the "forge corrects_id pointing at another user's row" edge case. Cheap and clean.
CREATE OR REPLACE FUNCTION validate_corrects_id_ownership()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.corrects_id IS NOT NULL THEN
    IF NOT EXISTS (
      SELECT 1 FROM public.health_measurements
      WHERE id = NEW.corrects_id AND user_id = NEW.user_id
    ) THEN
      RAISE EXCEPTION 'corrects_id must reference a row owned by the same user';
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SET search_path = '';

DROP TRIGGER IF EXISTS trg_validate_corrects_id ON health_measurements;
CREATE TRIGGER trg_validate_corrects_id
  BEFORE INSERT ON health_measurements
  FOR EACH ROW EXECUTE FUNCTION validate_corrects_id_ownership();

NOTIFY pgrst, 'reload schema';

Defence-in-depth summary

LayerWhat it catches
L1 · Postgres grants
REVOKE UPDATE ... FROM authenticated		 Users have no direct UPDATE permission on this table by any route — PostgREST, raw SQL, Supabase JS client. The only path to UPDATE is the RPC.
L2 · RPC ownership check
(inside correct_measurement)		 SELECT inside the RPC requires user_id = auth.uid() AND status = 'active'. Even though the RPC is SECURITY DEFINER and could see all rows, the check restricts it to the caller's own active rows.
L3 · BEFORE UPDATE trigger
to_jsonb(NEW) - 'status'		 Final safety net. Fires regardless of how the UPDATE arrived (RPC, future migration, hypothetical bug). Rejects any change to columns other than status, and any reversion away from entered-in-error.
L4 · BEFORE INSERT trigger
(corrects_id validation)		 Prevents forging a corrects_id that points at another user's row. Mostly cosmetic protection but cheap to add and closes the audit-chain integrity loop.

5 · The correct_measurement RPC

Atomic two-step: INSERT new row + UPDATE old row's status. Runs SECURITY DEFINER with an explicit auth.uid() check inside the function. Mirrors the pattern used by deduct_message_credit() and add_message_credits().

Race-condition safe: the RPC does the UPDATE first as an atomic lock-and-check, then the INSERT. Two concurrent corrections on the same row are serialised by Postgres row-locking. The loser sees ROW_COUNT = 0 and raises "not correctable". A naive SELECT-then-UPDATE would let both calls observe status = 'active' under MVCC and produce two active replacements — bug. 

CREATE OR REPLACE FUNCTION correct_measurement(
  old_measurement_id UUID,
  new_value          NUMERIC,
  new_recorded_at    TIMESTAMPTZ DEFAULT NULL
) RETURNS UUID AS $$
DECLARE
  old_row    health_measurements;
  rows_affected INTEGER;
  new_id     UUID;
BEGIN
  -- 1. Atomic lock-and-check: flip status to entered-in-error
  --    only if (a) the row is the caller's, (b) status is still 'active'.
  --    Concurrent callers serialise here — the loser gets rows_affected=0.
  UPDATE public.health_measurements
     SET status = 'entered-in-error'
   WHERE id = old_measurement_id
     AND user_id = auth.uid()
     AND status = 'active'
   RETURNING * INTO old_row;

  GET DIAGNOSTICS rows_affected = ROW_COUNT;
  IF rows_affected = 0 THEN
    RAISE EXCEPTION 'Measurement not found or not correctable';
  END IF;

  -- 2. Insert the corrected row, linked to the now-flagged old row.
  --    (Trigger validates corrects_id ownership; RLS validates user_id.)
  INSERT INTO public.health_measurements
    (user_id, metric_type, value, recorded_at, source, corrects_id)
  VALUES
    (old_row.user_id, old_row.metric_type, new_value,
     COALESCE(new_recorded_at, old_row.recorded_at),
     'manual_correction', old_measurement_id)
  RETURNING id INTO new_id;

  RETURN new_id;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = '';

GRANT EXECUTE ON FUNCTION correct_measurement(UUID, NUMERIC, TIMESTAMPTZ) TO authenticated;

Backend API surface: add a new branch to api.measurements.ts action(): POST { correctMeasurement: { oldId, newValue, newRecordedAt? } } calls the RPC and logs to audit_logs with action MEASUREMENT_CORRECTED and metadata { old_id, old_value, new_value, metric_type }.

Implementation sketch

  • Replace ReviewTable.tsx:428 with a controlled <input type="number" step="any" inputmode="decimal">.
  • State: editedValues: Record<string, number> keyed by ${fi}-${vi}. Initial value is displayValue from the LLM.
  • API contract change: the ExtractedValue response from /api/lab-import gains one field, displaySystem: 'si' | 'conventional'. The backend already resolves this internally in resolveUnit(); we just surface it. Without this, the client can't know whether to treat the edited number as SI or conventional when recomputing valueSI.
  • On save, recompute valueSI = toCanonicalValue(metric, editedDisplayValue, displaySystem) using the existing helper in packages/health-core/src/units.ts.
  • If edited value differs from LLM extraction: show small "edited from X" annotation, source becomes 'lab_import_edited' instead of 'lab_import'.
  • Validation: reuse the InputPanel pattern. The existing field inputs use UNIT_DEFS[metric].validationRange[unitSystem] and the Zod measurementSchema from packages/health-core/src/validation.ts. Identify the exact reusable utility during implementation; if InputPanel inlines the check, extract it into a shared widget-src/src/lib/validateMeasurementValue.ts and call from both places. The DB CHECK constraint on value_range remains the canonical enforcement; client-side validation is soft (warn-on-blur, doesn't block save) consistent with the existing "confidence is advisory" principle.
  • Decimal separator: small parseLocalisedNumber() helper that accepts both 0.5 and 0,5 in all locales. Tested with German, French, US-English form values.

8 · UI · history-view correction

From the history panel, the user clicks a row's "⋯" menu and picks "Correct value" or "Delete". Correct opens a small inline form; Delete calls the existing DELETE /api/measurements (still a hard delete — see §3 decision and the consequences note below).

Audit-mode toggle behaviour: defaults to off on every page load (not persisted in localStorage). Defensive — users don't get unexpectedly surprised by strikethrough entries when returning to the page.

11 · Testing strategy

LayerTests to add
Schema SQL test on staging:
  1. Insert active row, call correct_measurement, verify (a) new active row exists with corrects_id set, (b) old row has status = 'entered-in-error'.
  2. Negative: direct UPDATE blocked. As an authenticated user via the Supabase JS client, attempt .update({ status: 'entered-in-error' }) — should fail with a permission error (no UPDATE grant).
  3. Negative: cross-user correction blocked. Call correct_measurement with another user's row ID — should raise "Measurement not found or not correctable".
  4. Negative: trigger rejects column-changing UPDATE. As the table owner (bypassing grants), attempt UPDATE ... SET value = 999, status = 'entered-in-error' — trigger should raise "health_measurements is append-only".
  5. Negative: trigger rejects status reversion. As table owner, attempt UPDATE ... SET status = 'active' on an entered-in-error row — trigger should raise "status cannot be reverted".
  6. Negative: forged corrects_id blocked. Attempt to INSERT a row with corrects_id pointing at another user's row — INSERT trigger should raise "corrects_id must reference a row owned by the same user".
  7. Concurrent corrections race. Fire two correct_measurement calls on the same active row in parallel. Exactly one must succeed and produce one new active row. The loser must raise "not correctable". Verifies the UPDATE-first lock-and-check pattern.
  8. Hard delete breaks audit chain (expected). Correct a value, then hard-DELETE the entered-in-error row via DELETE /api/measurements. Verify the corrector's corrects_id is set to NULL (the ON DELETE SET NULL FK behaviour). Audit mode renders the corrector with no replaces-arrow. Accepted tradeoff of keeping DELETE as a hard pathway.
RPC Vitest integration test against staging Supabase: success path + permission denied + double-correction (correcting an already-corrected row should fail with "not correctable").
Read paths Existing get_latest_measurements tests in supabase.server.test.ts extended with a row marked entered-in-error — must not appear.
Review UI Widget tests: edit a value → check it persists in component state, save → verify payload uses edited valueSI, source flagged lab_import_edited.
History UI E2E with Chrome DevTools MCP per CLAUDE.md testing rules: upload a known-bad PDF, correct the value, refresh, verify suggestions update, toggle audit mode, verify struck-through row appears with arrow.
Concurrency Manual: upload 10 small lab PDFs on staging with concurrency 5, watch network panel for parallel requests, monitor Sentry for 429s.
