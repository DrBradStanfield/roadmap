Loop Fleet Architecture

Decision record + research citations for the autonomous-loop system in docs/loops/. Authored 2026-08-10 (Brad + Claude). The operative rules live in LOOP.md (the constitution) — this page explains why they are what they are. Update only when an architectural decision changes.

The vision (Brad, 2026-08-07 → 08-10)

Not one loop but a fleet — potentially hundreds — each compounding knowledge about one aspect of the product: usage, chatbot quality, ads, and whatever comes next. Shared invariants: the main thread runs on the best available model as an orchestrator that fans out efficient, task-matched worker agents; every loop improves itself; everything is documented so data, docs, and product improve together; and — critically — the system fights entropy so self-improvement never becomes sprawl.

The structure

docs/loops/
  LOOP.md          ← THE CONSTITUTION: shared rules every loop inherits (Brad-guarded)
  REGISTRY.md      ← fleet index: one row per loop (schedule, trigger, signal, status)
  _TEMPLATE.md     ← charter template for new loops
  loop-master-architecture-explanation.html   ← this page
  <name>/
    LOOP.md        ← the loop's CHARTER: deltas only (mission, sources, scope, delivery)
    LEARNINGS.md   ← curated qualitative findings (capped, compacted)
    metrics.csv    ← append-only numeric ledger (never summarized away)
    YYYY-Www.md    ← weekly reports

Each trigger is a three-line bootstrap: read the constitution, then your charter; charters never override Guardrails. A loop only ever loads the constitution + its own folder — never the fleet (progressive disclosure at fleet scale). Improving the constitution improves every loop at once.

Decision 1 — the 200-line / 25KB cap (researched, not arbitrary)

Brad challenged the first proposed cap (~120 lines) as arbitrary. Research agents were fanned out against Anthropic's primary sources (2026-08-10). Findings:

NumberSourceWhat it governs
200 linescode.claude.com/docs/en/memoryCLAUDE.md-class always-loaded instruction files: "target under 200 lines… Longer files consume more context and reduce adherence."
200 lines / 25KBsameClaude Code's own self-amending memory index (MEMORY.md) — a hard, enforced cap: content past it is silently dropped on load. The closest structural analog to a loop playbook.
500 linesAgent Skills docsSKILL.md body — but only because skills use progressive disclosure (detail split into reference files).
1,000–2,000 tokensanthropic.com/engineering/effective-context-engineering-for-ai-agentsThe stated right-size for distilled sub-agent summaries.

Two principles from the same sources drive the design: bloat causes silent rule-dropping, not graceful degradation (a live model deprioritizes buried instructions — the exact failure mode a playbook can't afford), and large context windows are not an exemption (attention degradation scales with length architecturally). In every doc, the remedy for outgrowing a ceiling is the same: split into linked reference files — never raise the number. Hence the constitution's uniform rule: every operative file ≤200 lines / 25KB; one-in-one-out within 20 lines of the cap; split, don't grow.

Empirical validation from this very repo: the chat-health playbook, self-amending without a cap, hit 211 lines in three days.

Decision 2 — learnings split by shape: prose vs ledger

Records split by durability and shape, not topic:

TypeDestinationWhy
Time-series numbers (funnel counts, deltas)metrics.csv, append-onlyTrends must never be prose-summarized — "usage was up" destroys the number. Greppable, diffable, chartable. Precedent: the business repo already runs two such ledgers (ad-creative-results.csv, title-thumbnail-results.csv).
Qualitative findingsLEARNINGS.md, capped 200/25KBNuance needs sentences; the cap + compaction keep it a live index, not an archive (git is the archive).
NarrativeWeekly report filesAlready the right shape — the "topic file" tier.

Compaction is a standing constraint, not a chore (modeled on Claude Code's own memory mechanism): within 20 lines of the cap, compact in the same run — merge near-duplicates, drop superseded entries, demote aged-obvious ones. Dedup is mechanical: same tag + same subsystem → update the existing entry in place, never append a paraphrase (grep-by-wording can't catch restatements; this rule can). Entries needing >3 sentences become topic files with one-line index entries — the index/topic-file split Claude Code's harness memory uses in production.

Decision 3 — entropy is fought on a schedule, and the budget is Brad-locked

Monthly pruning pass (first run of the month): the retro must name the least-earning rule and compress or delete it — entropy-fighting that isn't on the calendar doesn't happen. Line counts are published in every report as vital signs. And the enforcement asymmetry is deliberate: the entropy caps live in the constitution's Guardrails section, which only Brad may edit — the one thing a self-improving loop can never do is relax the rules about its own growth. Loops optimize within the budget; only Brad sets the budget.

Decision 4 — fleet-level entropy: loops must earn their keep

At hundreds of loops, the biggest sprawl risk isn't file length — it's loops nobody reads. So loops are treated as features under the repo's own Lane B discipline: every charter declares a success signal (what proves its outputs are acted on) before its first run, the registry makes the fleet visible in one screen, and a quarterly review kills or merges non-earning loops. This mirrors the lesson that created the loop system in the first place: the reminders feature sat at 2 opt-ins for months because nothing measured it.

Decision 5 — orchestration economics

Orchestrator = strongest available model (judgment, synthesis, retro — never delegated). Workers = model strength chosen by the orchestrator per task (Brad's 2026-08-10 refinement): Haiku-tier for trivial mechanical work, Sonnet-tier for standard mechanical work, strongest-tier where a delegated subproblem needs real reasoning — erring one tier up when unsure. Fan-out is sized to the work, not to a number — a handful for a weekly gather, hundreds for an exhaustive sweep — bounded only by crisp per-worker deliverables and spend proportionate to the output's worth (unusual scale justified in the retro). This generalizes the repo's documented plan-big/execute-small pattern (≈92–96% of top-model quality at ≈46–63% of cost, per CLAUDE.md's benchmarks). Practical note: all three current loops fire Monday morning NZ within ~96 minutes and share one plan-usage pool — stagger across days if runs truncate.

Decision 6 — deploy capability: agents end at the PR; CI holds the keys (constitution v3, 2026-08-10)

Brad's proposal — author loop → PR → reviewer loop → merge → deploy → dual live verification — was researched against Anthropic's docs, the 2026 security literature, and this repo's deploy audit (full write-up: deploy-pipeline-proposal.md). The design survived with one structural change: no agent ever executes the deploy or holds a deploy credential. Three findings forced it: Claude's cloud environments have no secrets store (env vars are documented as visible to anyone using the environment); Anthropic blocks agent-fired production deploys by design (their Auto Mode classifier did exactly that when this pipeline's first run was attempted from a session — the boundary works); and our loops read user free-text (feedback forms, chat transcripts), making a credential-holding loop a textbook confused deputy. A Fly "deploy" token can also set the app's secrets — it limits blast radius, not capability — so it lives where no model can read it.

The shipped pipeline (.github/workflows/deploy.yml + claude-review.yml, Brad-only files): author agent opens a PR from a claude/ branch → a fresh-context reviewer (correctness-only mandate; approves or requests changes, never merges) → merge with the ship label fires deploy.yml → gate (≥1 approval + green checks, verified independently) → GitHub Pages WebKit smoke (Brad's addition: the auto-deployed Pages build is tested before production — a smoke gate only, since Pages has no theme CSS and no Fly server) → full suite on the exact commit → Shopify deploy ×2 → Fly deploy ×2 with --strategy canary → health gates → live WebKit verify against production. Hard branch protection is deliberately deferred (it would block Brad's direct-push workflow and loop report commits); the gate job enforces the same conditions in code. Prerequisite unblocked the same day: the docs/products.md symlink was inverted (master is now a real file in this repo; claude_business holds the symlink) so headless builds ship real chatbot knowledge.
