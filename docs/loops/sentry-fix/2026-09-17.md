## Root cause (from event data)

Every same-second pair is ONE page load reported twice: the connect-time lift
(`liftLocalInto` → `SyncManager.save` → `GoogleDriveAdapter.read`, handled,
`area=cloud-connect op=migrate-up`) then `main` → `initRoadmapStore` →
`SyncManager.load` → `driveFindFileId` → `fail`, unhandled. Three of four
sessions start with `POST health-tool-app.fly.dev` 200 plus a `navigation`
crumb (`completeRedirect`'s exchange and `replaceState`): fresh `prompt=consent`
connects. The fourth (13:04Z) is the refresh path: exchange 200 at 25.154Z,
403 at 25.595Z. So every grant lacked `drive.file` from issue, and the app
never checks the granted scope ("connected" = "tokens exist"). `main()` has
no catch, so `createRoot` never runs: an empty mount on every visit (1-4
loads per session) until site storage is cleared.

**Two hypotheses fit; this run could not separate them.** Requested scope is
`openid email drive.file`, so the Drive box is the only checkbox on Google's
granular consent: (a) left unticked three times on two browsers, or (b) the
OAuth client no longer grants `drive.file` to anyone. The discriminator, a
Drive connect that works after 09-10, is unreadable here (Supabase key 401;
and `cloud_connect_success` fires after a swallowed lift failure, so the
funnel counts these as successes). **Brad: one live Drive connect on a
scratch account decides it.** Pushed as a notification.

Why now: PR #73 (allowUrls) live from deploy run 58, 09-08 20:59Z; the SDK
dropped main-bundle events before it. Newly visible, not old.
