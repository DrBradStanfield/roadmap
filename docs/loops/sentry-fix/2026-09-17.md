## Root cause (from event data)

Widget events, `platform=javascript`. Every same-second pair is ONE page
load reported twice: the connect-time lift (`liftLocalInto` → `SyncManager.save`
→ `GoogleDriveAdapter.read`, handled, `area=cloud-connect op=migrate-up`) and
then `main` → `initRoadmapStore` → `SyncManager.load` → `driveFindFileId` →
`fail`, unhandled. Three of four sessions start with `POST
health-tool-app.fly.dev` 200 plus a `navigation` crumb — `completeRedirect`'s
exchange and `replaceState`, i.e. a fresh `prompt=consent` connect; the
fourth (13:04Z) is the refresh path (exchange 200 at 25.154Z, 403 at 25.595Z).
So every grant lacked `drive.file` from issue, and the app never checks the
granted scope: "connected" means "tokens exist". `main()` has no catch, so
`createRoot(...).render` never runs: an empty mount on every visit (1-4
loads per session) until site storage is cleared.

**Two hypotheses fit; this run could not separate them.** Requested scope is
`openid email drive.file`, so with Google's granular consent the Drive box is
the only checkbox: (a) it was left unticked three times on two browsers, or
(b) the OAuth client no longer grants `drive.file` to anyone. The
discriminator is a Drive connect that works after 09-10 — unreadable here:
the Supabase key answered 401, and `cloud_connect_success` fires after a
swallowed lift failure, so the funnel counts these as successes anyway.
**Brad: one live Drive connect on a scratch account decides it.**

dropped main-bundle events before it. Newly visible, not old: the sessions
