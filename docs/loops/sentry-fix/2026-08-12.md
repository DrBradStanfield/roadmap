## Root cause — JAVASCRIPT-REMIX-1M

A user's chat POST returned **500 with no Content-Type and an empty body**
(Aug 7 16:06:41Z). Every 500 path in `app/routes/api.chat.ts` returns JSON and
captures to Sentry; no server-side event exists for that moment and Supabase
shows **no DB writes** — so the failure happened upstream of our handler
(Shopify app proxy / Fly edge, machine unreachable or killed mid-request).
A likely retry by the same user at 16:21:14Z died mid-LLM-call, leaving an
orphaned user row with no assistant reply and again no server capture. No
deploy occurred that day. Client UX on this failure was a dead end: optimistic
message removed, input already cleared, bare error.

Fix (PR): retry transient upstream failures once in `chat-api.ts` — any
response ≥500 whose body is not JSON (i.e. the proxy/edge answered, not our
handler) is refetched once after 1s. Our handler's own JSON 5xx errors and
429s are never retried. The server's consecutive-duplicate dedup
(`chat-dedup.server.ts`) makes an identical chat resend safe — and free when
the first attempt completed server-side. Covers the dormant -22 class too.

## Escape analysis

No test exercised the client data layer's behavior when the response comes
from the proxy/edge instead of our handler. `parseJsonResponse` handled the
"HTML with 200" case (tested), but every `!response.ok` path treated a
proxy-generated 5xx as final. New `chat-api.test.ts` pins the retry contract
for both the evidenced signatures (500/no-content-type, 503/text/html).
Class rule → LEARNINGS: a 5xx whose body isn't our JSON is infrastructure
weather, not an application answer — client code must not treat it as final.
