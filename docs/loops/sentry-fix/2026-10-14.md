## Root cause (from event data)

Server event, `platform=node`, tags `feature=chat subsystem=router`. A widget
chat turn: POST `/api/chat` through the drstanfield.com proxy, Edge 154 on
Windows, machine `86de05f750e168` (health-tool-edu, Fly `iad`). Extra:
`latencyMs 11006`. The capture is `reportRouterFailure`
(`app/lib/chat-router.server.ts:381`). It sends no error text by design.

The text is in Supabase. `chat_match_events.router_error` for that turn reads
"The operation was aborted due to timeout". `routeQuery` calls Anthropic with
a 5 s budget. `fetchAnthropicRaw` retries a `TimeoutError` once after 1 s.
5 s + 1 s + 5 s = 11 s: both attempts timed out.

Base rate (71 routed turns since the Sonnet 5.5 router switch on 09-29, read
from `chat_match_events`):

- Two errors: this timeout and a parse error on 10-07 (fixed by US-15
  AC28). This is the only timeout. The 09-23 400 predates the switch.
- The 69 good turns: median 1.7 s, p90 3.3 s, p95 3.5 s, max 4.0 s (10-12).
- Cache misses run 1.0 to 3.5 s.

So the call usually finishes in under 4 s against a 5 s budget. This one
took over 5 s twice in a row. Nothing in our request changed. The day's one
deploy (`health-tool-edu@0e72c516`, 00:12Z, which booted this machine) has no
diff from the prior release in `app/lib`, `api.chat.ts`, `models.ts` or
`docs/chatbot`. That reads as an upstream slowdown, not a defect.

**Impact:** the turn was still answered (a `chat_match_events` row exists),
with no knowledge-base articles and an extra ~11 s before the answer began.
It was not the fallback message.

**PR:** none (no code change).

**Verdict: triaged-ours, not claimed.** One event is not a pattern. The
resurface rule in the ledger row: 2+ router timeouts in 7 days means the 5 s
budget is too tight for Sonnet 5.5.

## Tier 0 options, for a recurrence only

The headroom is thin, about 1 s at p95. If timeouts repeat, two fixes are
possible in `chat-router.server.ts` (inside the grant):

1. Raise the router budget to 8 s. This rescues slow calls; worst case 17 s.
2. Pass `maxAttempts: 1`. A timeout then costs 5 s, not 11 s. A retry after a
   slow upstream rarely lands faster.

Both trade answer quality against wait. The data does not justify either yet.
