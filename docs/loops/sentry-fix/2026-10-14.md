## Root cause (from event data)

A widget chat turn (POST `/api/chat`, Edge 154, health-tool-edu machine
`86de05f750e168`), `latencyMs 11006`. The capture is `reportRouterFailure`
(`app/lib/chat-router.server.ts:381`); it sends no error text by design.

The text is in Supabase. `chat_match_events.router_error` for that turn reads
"The operation was aborted due to timeout". `routeQuery` calls Anthropic with
a 5 s budget. `fetchAnthropicRaw` retries a `TimeoutError` once after 1 s.
5 s + 1 s + 5 s = 11 s: both attempts timed out.

Base rate (`chat_match_events`, 71 routed turns from 09-29 12:00Z; the 8
earlier Sonnet 5.5 turns were all good):

- Two errors: this timeout and a parse error on 10-07 (fixed by US-15
  AC28). This is the only timeout. The 09-23 400 predates the switch.
- The 69 good turns: median 1.7 s, p90 3.3 s, p95 3.5 s, max 4.0 s (10-12).
- Cache misses run 1.0 to 3.5 s.

So the call usually finishes in under 4 s against a 5 s budget. This one
took over 5 s twice in a row. Nothing in our request changed. The day's one
deploy (`health-tool-edu@0e72c516`, 00:12Z, which booted this machine) has no
diff from the prior release in `app/lib`, `api.chat.ts`, `models.ts` or
`docs/chatbot` or the router index (`docs/blog/index.json`). The request was
1 KB. The next routed widget turn, 44 s later, missed the cache and took 2.3 s.
Cache-miss medians fell over the window (2.8, 2.0, 1.3 s by five-day slice).
Most likely an upstream slowdown. Not proven: router output tokens are not
logged, so a question that draws a long reply (up to `max_tokens` 200) would
time out on both tries and look the same. Latency tracks output, not cache:
hits run up to 4.0 s.

**Impact:** the turn was answered with no knowledge-base articles. Its row
reads `is_fallback=false`, `failure_mode` null, 0 handles. The wait was ~9 s
longer than a median routing. (A refusal would not set `is_fallback`, and
whether the stream reached the client is not logged.)

**Verdict: triaged-ours, not claimed; no PR.** One event is not a pattern. Resurface
rule (ledger row): 2+ router timeouts in 7 days on ANY surface, counted in
Supabase (`router_error ilike '%timeout%'`). Sentry cannot see it: only
`/api/chat` reports router failures (YouTube and Discord, 36 of 71 turns, do
not), and a second 6Z event lands on a ledgered id the fast path skips.

**Tier 0 options, for a recurrence only** (headroom ~1 s at p95; both in
`chat-router.server.ts`, inside the grant): (1) raise the router budget to 8 s,
worst case 17 s; (2) `maxAttempts: 1`, so a timeout costs 5 s, not 11 s. Both
trade answer quality against wait; one event justifies neither. First, log
router output tokens, so a long reply can be told from a slow upstream.
