## Root cause (from data, not theory)

- No deploy since Aug 20 (deploy.yml run 18, success 20:34Z) → nothing changed
  on our side when errors began 08-26 09:47Z.
- Probe: 25/25 requests with the legacy-style product-health JWT (iat
  2026-08-07) against the same project's PostgREST succeeded → project DB
  clock is sane vs fixed old iats.
- The cloud env's anon key is new-format `sb_publishable_` → production
  service key is almost certainly `sb_secret_`. Those are exchanged at
  Supabase's gateway for a per-request minted JWT (iat = gateway clock); a
  gateway node running ahead of the project's PostgREST yields exactly this
  intermittent per-request PGRST303. **Platform-side fault** — Brad's to
  escalate (decision issue opened; link added below after review).
- **Our real defect (what PR #30 fixes):** the failure was fail-open on the
  public-posting path. `countTodayPosts` error → `0`, `fetchVideoPostCounts`
  error → empty map — indistinguishable from "nothing posted", so every
  affected tick silently re-armed the full 50/day cap and dropped all
  10/video lifetime caps.

## Tier 0 proposal (7693659330, cron-lock day-skip)

`tryAcquireCronLock` returns `false` on error; `youtube-bot-summary-cron.ts`
(line ~51) treats false as "another machine won" and sets
`lastRunDate = todayStr` — a transient Supabase error silently skips that
day's summary email (likely happened 08-26→28; Brad: check inbox). Proposed:
let acquisition errors throw (or return a third state) so the hourly check
retries the same day. Touches all 5 cron callers → left as proposal, not
widened into PR #30.
