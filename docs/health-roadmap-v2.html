Health Roadmap v2 — Direction & Architecture Decision Record

Status: LIVE IN PRODUCTION 2026-06-12 — /pages/roadmap serves v2 (health-roadmap-726). Remaining: delete old Supabase per-user data + tear down dead server routes  ·  Date: 2026-06-08  ·  Updated: 2026-06-12  ·  Owner: Dr Brad Stanfield  ·  Supersedes: the current Supabase/Fly app-proxy architecture (~/Documents/roadmap/docs/architecture.html)

Health Roadmap is changing direction entirely. It moves from a server-backed app that stores users' health data in Brad's database, to a local-first, open-source app where each user's health data lives in their own cloud (Google Drive, Dropbox, GitHub, or self-hosted) — Brad never stores it and cannot read the user's cloud. (The optional AI features transit the content you choose to be processed, never stored — §7.) This document records that decision, why it was made, what gets built, and the paths we deliberately rejected.

TL;DR — the decision

The one-paragraph version

A free, open-source, client-side app — usable two equal ways: through drstanfield.com (Shopify) or self-hosted / GitHub Pages. Health data lives in the user's own Google Drive / Dropbox / GitHub / self-host as plain, open-format files; Brad stores no health data (and can't read the user's cloud). Recommendations and history run entirely in the browser and keep working even if Brad disappears. A thin, separate server (free, website-only) powers the chatbot, lab-PDF extraction, and email reminders; the AI features transit the content you choose to be processed, then discard it — never stored (§7). No paid tier for now updated 2026-06-08 — the app is fully free, monetized via the supplement business + the email list (§13). The old server-side data layer (Supabase / HMAC auth / Supabase Auth) is gutted.

Open

Code public on GitHub. Self-hosting is a first-class option, not a footnote.

Private

Brad is never the data custodian. Data sits in the user's own cloud.

Durable

Your data is never trapped (in your own cloud, openable offline). Auto-sync continues while the OAuth apps live — honest caveat + break-glass in impl §15 (H6).

1. Philosophy & goals

The architecture is downstream of Brad's health philosophy. Every choice traces back to these:

  • "Be healthy so you can live" — not the reverse. The tool must not demand daily attention or make people track everything. Aim for ~95% of the benefit for ~5–10% of the effort.
  • Intermittent by design — meaningful use is roughly every 2–3 months, paced by blood-test and screening intervals. This is a feature, not a bug (and it shapes monetization — see §13).
  • Put the user in charge of their health — input your data, get the high-leverage things to do. Doctor disclaimers are a legal backstop, not the intended workflow.
  • Maximum privacy at the heart — the user owns and controls their data; big companies and LLMs don't get it; Brad doesn't get it.
  • Three goals at once — mission (help everyone, free), funnel (trust → brand + supplements), and revenue (a tier that pays for itself). These are reconciled, not traded off.

The avatar: a 70-year-old, non-technical grandma

Every design decision is stress-tested against her. She will never run a server, use a terminal, or safely store a 24-word recovery phrase. If a choice fails the grandma test, it loses — even if it's more "pure". This single constraint kills several otherwise-attractive options (see §16).

2. The strategic reframe

The starting question was "open-source like PewDiePie, or closed/revenue like Ed Lawrence?" That framing was a trap — it fused three independent decisions into one false binary:

DecisionThe false binaryThe real answer
Licensingopen vs closedOpen source (mission + trust with a skeptical audience)
Architecturelocal "no server" vs cloudLocal-first, user-owned cloud (no Brad server in the data path)
Moneyfree vs paidFree app, paid service — not feature-freemium (see §13)

Neither reference model fits, and for symmetric reasons:

  • Ed Lawrence's model works because of daily, per-task use — the opposite of "don't let health rule your life". Bolting a use-it-constantly business onto a use-it-rarely tool is a contradiction.
  • PewDiePie's model serves technical privacy-maximalists who self-host their own server — the opposite of the grandma avatar. (His app doesn't escape the server; it makes the user the server operator.)

Both creators monetize a tool as the product. Brad already has a product business (supplements + brand). So the app's highest-value role is a trust/funnel asset with an optional paid service — not a standalone SaaS fighting Function Health ($2.5B) and Superpower ($300M) on capital.

3. Interpretation is the product; storage is a tombstone

The single most important lesson from the PHR landscape

Google Health (shut 2012) and Microsoft HealthVault (shut 2019) had unlimited money and distribution and still died — because they were passive vaults: storage with no interpretation, no behavior loop, no reason to come back. Self-hosted open-source PHRs (e.g. Fasten Health) stay tiny because they're storage for hobbyists. The product is the recommendation engine, not the database.

Implications baked into v2:

  • The recommendations engine is the moat and stays free (mission + funnel).
  • The reminder/recall loop is what turns intermittent use into retention — and fixes the "empty vault" abandonment problem the big PHRs never solved.
  • Brad's edge is being a practising GP who won't overclaim, vs functional-medicine players who do.

4. The v2 architecture

5. Two equal front doors

Both are first-class from day one — self-hosting is a genuine alternative, presented to demonstrate that the user is truly in control, not a hidden escape hatch.

A · drstanfield.com

The app runs as a Shopify theme-extension widget (static JS/CSS on Shopify's CDN). Easiest path for the mainstream user / grandma. Discoverable next to the products and brand.

B · Self-host / GitHub Pages

The same open-source app, hosted by the user — on GitHub Pages (free static hosting straight from the public repo) or their own machine. For the privacy-maximalist / PewDiePie crowd. Proves the project isn't a walled garden.

Either door loads the same client-side app, which talks directly to the user's chosen cloud. The choice of front door does not change where data lives or who can see it (no one but the user).

6. Data: the user-owned cloud

  • Storage targets (user picks one): Google Drive, Dropbox, GitHub (a private repo), or self-host. Chosen during the same step as "turn on sync". iCloud Drive is NOT viable on web — no third-party API. The web app / PWA serves Apple devices too via the same Drive/Dropbox sync; no native app is needed for sync (a future Apple Health / HealthKit iOS app is a separate, planned thing — §16, impl §12).
  • Audience split: Google Drive + Dropbox are the consumer/mainstream targets (grandma). GitHub (free, gives a full version history of every change) + self-host are the developer/privacy targets — GitHub is a developer platform, so it isn't a grandma option, but it's a natural fit for the open-source crowd.
  • Delivery ≠ storage: where the app is served from (§5) and where data is stored are independent choices — e.g. use the drstanfield.com app but store in GitHub, or self-host the app and store in Dropbox.
  • Access: the browser does client-side OAuth (PKCE) directly with Google/Dropbox. No Brad server in the loop. The user's cloud account is their identity — Shopify login becomes irrelevant to the data layer.
  • Scope: Google's drive.file scope means the app can only touch files it created — it literally cannot see the rest of the user's Drive.
  • Format: plain, open-format files (e.g. JSON). Today's schema (profile + append-only measurements + meds/supplements + history + lab values) serialises cleanly to one file (or a few).
  • Gutted: Supabase, the HMAC app-proxy auth, Supabase Auth user creation, JWT minting — all deleted from the core data path.

Hard requirement: folder-scoped access only — never the user's whole cloud

The app must touch only its own Health Roadmap data, never the rest of a person's files — and this is enforced by the access method, not a promise:

  • Google Drive: the drive.file scope — the app accesses only files it created and never even sees the rest of Drive. Non-sensitive scope; no Google security review needed.
  • Dropbox: register the app as "App folder" type — it gets a dedicated /Apps/Health Roadmap by Dr Brad folder and physically cannot reach anything outside it. (Dropbox fixes App-folder apps under /Apps/; it can't be at the Dropbox root — that would require "Full Dropbox" access, which breaks the folder-scoping promise. So /Apps/ is the privacy-preserving choice.)
  • GitHub: a user-pasted fine-grained Personal Access Token scoped to one repo (Contents read/write). A full OAuth/App web flow isn't viable purely client-side (GitHub token endpoints lack CORS + need a client secret), so the pasted PAT is the no-server path — dev-audience only. See impl §4.

Why plain files (not an app-locked database)

Open-format files are openable by any tool, forever — the Obsidian "your data outlives the app" principle. It also makes the self-host / "start-here" viewer trivial and guarantees data is never trapped.

7. Privacy model

ActorCan read health data?Notes

Self-host userOnly themThe maximum-privacy path: nobody but the user.

Decision: NO client-side encryption in the default version

Encryption was considered and rejected for the default tier. Rationale: it reintroduces the key-recovery landmine (forgotten key = years of health history gone forever) — the single worst failure mode for the grandma avatar. Plain files are also more portable. Users who want provider-proof privacy choose the self-hosted version. (An optional encryption toggle could be added later for the privacy-conscious-but-not-technical user; not now.)

Honest positioning — do NOT oversell

The default version must not be marketed as "maximum privacy" or "encrypted" — Google/Dropbox can technically read it, and the skeptical audience will check. The true, strong, on-brand claim is:

"Your health data lives in the cloud account you already use and already trust — not on our servers — we never store your health data. (The optional AI lab-import and chatbot send the content you choose to be processed, then discard it — clearly opt-in.) Want it locked down even from Google or Dropbox? Run the self-hosted version."

Reality check: realistically <1% will self-host, so for ~99% of users the honest privacy story is "Brad is blind; the user's chosen cloud technically isn't". Accept this with eyes open.

8. The recommendations engine

Already client-side today (packages/health-core runs in the browser) — no change needed in principle. calculateHealthResults() generates suggestions + attaches evidence entirely in the browser. The server never regenerates them. This is exactly what makes the local-first move feasible: the valuable part already runs where the data now lives. Stays free.

9. History & past advice

  • User-facing history is preserved and improved. The full append-only record lives in the user's cloud file, so trends over time work naturally — and are visible only to the user.
  • Past recommendations are snapshotted into the file each session, so the user can see "what was I advised 6 months ago", not just raw numbers.
  • The HIPAA tamper-proof audit-log table goes away — it existed because Brad was the custodian. He no longer is, so that compliance artifact (and its burden) is shed. The user's append-only file is their record.

10. Reminders — how the cron works without reading the data built · e2e verified live 2026-06-10

Email reminders are the one feature that can't live purely on the user's device: they fire on a timer (a daily cron) when the browser is closed, so Brad's server must hold a tiny bit of data to send them. Two risks come with that — spam/abuse (someone typing a stranger's email as the destination) and privacy (storing more than the bare minimum). The model below closes both.

Reminders are email-only, free, and website/server-only

Email only — no calendar (.ics / Google Calendar) injection. Free for every cloud-authed user (no paid tier). They need the server + daily cron, so they are a website/server feature, not a GitHub-Pages/self-host one. Raw WebDAV / self-host has no provider-verified identity, so it is out of scope for email reminders. The schedule itself is computed client-side (computeReminderSchedule()) and pushed up; the server is a dumb scheduler.

The key insight — the server learns your email from your cloud, not from what's typed

Cloud auth (Dropbox / Google / GitHub via client-side PKCE) is independent of Shopify — no Shopify account is involved. The cloud connection is the identity. At opt-in the server must learn your verified email from the provider who already checked it — not from whatever the browser types. Otherwise an attacker could connect their own Dropbox (legitimate) but type your address as the destination, and the app would email you on demand. Letting the provider vouch for the address means the only address anyone can ever target is their own.

Endpoint security — who can do what (the threat model, plainly)

Brad has asked twice how the public Fly endpoints stay secure, so here it is as a permanent reference. The key idea: the Origin allow-list is the anti-abuse layer, not the confidentiality layer. A command-line attacker (curl) CAN fake an Origin header — and it gets them almost nothing, because the confidentiality comes from the endpoints' design, not the header check:

LayerWhat it stopsWhat it does NOT stop

No read path — no endpoint returns anyone's email; no list, lookup, or search exists. The cron reads the table only from inside the server.Email-list extraction — by anyone, via any header trick. This is the actual confidentiality boundary.—

The two tokens — and why we never reuse one as the other

"Why a second token? Why not just the cloud login?"

The cron is not the reason — it needs no login at all. Two other things force a small server-issued token regardless:

  • The unsubscribe link. Clicked from the inbox, where the user is not cloud-authed, and legally must work in one click — so it has to carry a server-issued token, not require a cloud login.
  • Editing without re-exposing the powerful key. Using the cloud token to authorize each edit would re-send your whole-folder key to the server every time — and it rotates every few hours, so it isn't a stable handle anyway. A purpose-built, low-privilege, revocable token avoids both.

Once that token exists (the unsubscribe link forces it), in-app schedule edits reuse it too — one uniform, low-risk credential. The cron itself just reads the stored schedule and sends — no token, no re-auth.

Data minimisation, not de-clinicalisation

The reminder really does say "your 5-yearly colonoscopy is due" — personalised and specific is the whole point. What we don't keep is why: the previous results, the reasoning, any lab value. The server knows "Colonoscopy, due 2031" + your email + a capability token, and nothing more. The message text is therefore health-adjacent, accepted as a deliberate, minimal exception to "store nothing" because reminders are a critical function while Brad is online. If Brad goes dark: the cron stops, emails cease, and the data + core app are untouched.

The one decision — how the server gets your verified email

Everything above is fixed. The only choice is how the server learns the verified email at opt-in (the "bootstrap"), and it differs by provider:

ProviderHow the server learns your verified emailDoes the cloud token touch the server?
GoogleThe browser hands over a signed ID token; the server verifies Google's signature against Google's keys — no file-access token ever touches the serverNo — never. Cleanest.
Dropbox / GitHubNo signed ID token exists, so the server calls the provider once with the cloud token to read the verified emailOnce — in memory, then discarded

The chosen approach is the one-time, in-memory read for Dropbox/GitHub — it transits, it's never stored, exactly the "transit, never store" posture the AI features already use (§7). Google avoids even that one-time read.

As built (2026-06-10) — five refinements, none changing the model

  • Vocabulary: "opt-in", not "subscription" (Brad's call — "subscription" means paid product subscriptions in this business). Server table: reminder_optin_v2; one row = one person's opt-in (email + provider + label/date schedule + capability token + re-send bookkeeping). Nothing else.
  • The capability token is stored raw (as the table above always said) — the daily cron writes each email's unsubscribe link, which must carry the actual token, so a hashed-at-rest copy can't work. The accepted leak posture is unchanged: the token can only touch the reminder schedule.
  • Google popup-fallback sessions use the one-time read. The primary Google path is the signed ID token exactly as designed (Drive scope now also requests openid email; the stateless exchange passes id_token through and still stores nothing). But a session authed via the GIS popup fallback has no ID token — there the opt-in click pops the consent window and the server does the same one-time, in-memory userinfo read that Dropbox/GitHub get. Primary path keeps the "never touches the server" property.
  • GitHub needs one extra token permission: the fine-grained PAT must also have "Email addresses: read-only" for the one-time /user/emails read; the opt-in UI explains this when GitHub refuses. (Advanced tier — Drive/Dropbox need nothing extra.)
  • Re-send cadence + unsubscribe semantics: a still-due item re-nudges on the v1 group cooldowns (screening 90 d / blood test 180 d / medication review 365 d) — periodic nudges, never daily spam. Unsubscribe (one-click, RFC 8058) deletes the row — no suppression list. A later schedule push with the dead token 404s and the app clears the stale opt-in from the user's cloud file; re-subscribing requires a fresh explicit opt-in + provider proof.

12. Two-layer separation

A clean organising principle for the rebuild:

Open-source core

Client-side app + the user's own cloud. What gets published and what works if Brad goes dark. Calculations, recommendations, history, the client-side reminder-schedule computation, cloud adapters (Drive / Dropbox / GitHub / self-host).

Brad's server layer (free)

The thin Claude-extras server, the email-reminder service, and A/B testing — server-backed and deployed separately, but in the same public repo (transparency; one repo to manage, not a private split). Never holds health values. Secrets live in env vars, never in code.

14. Token refresh — Dropbox in-browser; Google via a stateless exchange + popup fallback

DECISION UPDATE (2026-06-10): Google refresh is server-assisted (stateless) — the original plan didn't survive contact

The original §14 assumed the browser could "silently re-issue" Google access tokens. Brad's live test disproved it: browsers block the silent re-grant popup at page load (no user gesture), and Google grants no refresh token to browser-only apps (the code exchange requires the client secret, which can never ship in page JavaScript — note: the widget on drstanfield.com is still browser JavaScript; only the Fly server can hold a secret). With intermittent use, every visit would have started signed-out — unacceptable UX (Brad's call).

  • Dropbox: client-side PKCE refresh tokens. Clean, no server. Unchanged — and why Dropbox stays the recommended default.
  • Google — primary path: connect is a full-page redirect (like Dropbox); a tiny stateless token-exchange endpoint on Brad's existing Fly server swaps the code / refresh-token with Google (it alone holds the client secret) and hands both tokens straight back. The server stores nothing; the refresh token lives in the user's browser, same as Dropbox's. Tokens transit in-memory only — the same "transit, never store" posture as the AI features (§7.1). Result: connect once, stays connected.
  • Google — fallback path: if the endpoint is unreachable (server down / gone dark), the app keeps the user's choice, runs the session on-device, and the next user click re-acquires a ~1 h token via the GIS popup (auto-closes when already signed in). Sync continues serverless until the server returns. Never data-losing: the file always sits in the user's own Drive as plain JSON.

The "Brad can peek" concern is addressed by statelessness (nothing retained, nothing to peek at later) rather than by avoiding the server entirely; the go-dark guarantee is preserved by the fallback path. Prerequisite: the Google OAuth app must be published (Testing-mode refresh tokens die after 7 days); drive.file is non-sensitive so publishing needs no Google review.

Lab uploads — raw files live in the user's cloud, ORGANISED (Brad's design, 2026-06-10) built · e2e verified on real data 2026-06-10

File naming: YYYY-MM-DD Title.pdf (e.g. Lab results/2024-05-10 Lipid panel.pdf). Date = the document's own date (AI-extracted, user-correctable in the review step; falls back to upload date). Titles are filesystem-sanitised; name collisions get a "(2)" suffix — nothing is ever overwritten.

How the date ordering actually works: we can't control Drive/Dropbox's sort UI — but every cloud sorts file names alphabetically by default, so the names are built so that alphabetical IS chronological. Year-first, zero-padded (2024-05-10, ISO 8601): comparing character-by-character from the left hits years before months before days, so 2023-11-02 … sorts above 2024-05-10 … above 2026-02-14 …. Day-first or spelled months break this ("April" sorts before "January"); the zero-padding matters too (without it, month 10 sorts before month 5). A→Z (every cloud's default) puts the oldest at the top — first scan first; one click on the name column flips to newest-first and both directions stay correct. Because the name carries the document's date, a five-year backlog uploaded in one sitting still files into the right chronological positions.

UX when not cloud-connected (Brad's call, 2026-06-10): encourage, don't block. Clicking "Upload your lab results" while on the device-only tier shows a connect prompt FIRST ("Your lab files need a home…" → opens the backend-picker lightbox), with a quieter "Continue without keeping my files" link — extraction still runs and values are saved, but the original file is discarded, and the copy says so honestly. The connect prompt comes before file selection because the Drive/Dropbox OAuth is a full-page redirect that would lose a selected file — after connecting, the user clicks Upload again and goes straight to the file picker (one extra click, first time only; no IndexedDB stash-and-resume machinery).

Privacy posture: the raw file itself never touches Brad's server — PDF text/image extraction is client-side; only the extracted text transits the thin server for the Claude call (§7 transit-never-store), and the browser writes the original straight into the user's own cloud. Caveat: the GitHub backend caps documents at ~1 MB (Contents API) — fine for most lab PDFs, not for phone photos; friendly error now ("values extracted; file too large to store in GitHub"), blob-API upgrade later. Google Drive grows real subfolders (its adapter currently flattens names); Dropbox/GitHub/WebDAV get folders natively from the path.

16. Rejected paths & why don't relitigate

Ed Lawrence "sell a daily-use SaaS" model

Requires constant use; contradicts "don't let health rule your life". The tool is intermittent by design.

PewDiePie "self-hosted server" as the default

Makes the user the server operator — fine as an option (§5 door B), fatal as the mainstream path for grandma.

Keep data in Brad's Supabase

Makes Brad the custodian (privacy + HIPAA burden) and breaks "works if I go dark". The whole pivot is to remove this.

Client-side end-to-end encryption in the default tier

Key-recovery landmine: forgotten key = years of health history lost. Fails the grandma test. Self-host is the privacy-maximalist answer instead.

"No server at all / pure P2P" sync

Multi-device sync needs something always-on. Pure P2P only syncs when both devices are online + reachable — bad default UX. The user's own cloud is the always-on relay.

CloudKit as the sync backend

Rejected outright: CloudKit is Apple-only, so a native app syncing via CloudKit couldn't sync with the web version — it would fragment the data into two incompatible stores. The web app / PWA serves Apple devices instead, via the same Drive/Dropbox sync. This does NOT reject Apple Health (HealthKit): a future native iOS app may read/write Apple Health while still syncing via Drive/Dropbox (one data store) — planned, not rejected. See implementation plan §12.

iCloud Drive as a web sync target

No third-party web/Android API. Only Dropbox + Google Drive are viable on web.

Gating the recommendations behind a paywall

Would wound mission + funnel + trust. Charge for infrastructure (server services), never for the advice.

19. The dev/CI pipeline built 2026-06-08

§18 sets the strategy (build the free core on GitHub Pages first, keep the live app untouched). This section records the concrete four-stage pipeline that gives a clean path from a code edit to the live Shopify widget — with a deliberate gate so nothing reaches the live widget by accident.

The four stages

  1. localhost — npm run dev:pages runs a Vite dev server with HMR / Fast Refresh at http://localhost:5173/roadmap/. The rapid-iteration surface for non-OAuth work only (UI, the on-device tier, merge logic) — see the hard rule below.
  2. dev-branch GitHub Pages preview — the dev branch deploys to drbradstanfield.github.io/roadmap/dev/ while prod (main) stays at /roadmap/. The real-URL + mobile testing surface before anything touches Shopify.
  3. Shopify dev app — a separate Shopify app (its own extension + client_id) installed on the existing store, with the widget embedded on a hidden test page (e.g. /pages/roadmap-test, noindex). Deploying to it (shopify app deploy --config dev) targets that app alone and never touches the live widget. pending setup.
  4. production — merging dev → main auto-deploys the prod GitHub Pages site; the live Shopify widget changes only on an explicit shopify app deploy to the prod app.

Decision: a simple GitHub /dev/ subpath, NOT Cloudflare / Netlify per-branch previews

GitHub Pages serves one artifact per repo, so the Pages workflow now rebuilds both branches into that single artifact on every run — main → site root (VITE_BASE=/roadmap/), dev → /dev/ (VITE_BASE=/roadmap/dev/). The prod root is always the latest main (never stale); the dev build is best-effort — a broken dev branch warns and is omitted, and can never block the prod deploy. Chosen for simplicity: no extra hosting provider, no new account or secrets, one workflow file.

Decision: a separate dev app installed on the existing store + a hidden test page — NOT a separate dev store

The isolation comes from the dev app being a distinct app (its own extension + client_id), so shopify app deploy --config dev targets it alone and structurally cannot touch the live widget — not from a separate store. Installing it on the existing store and embedding the widget on a hidden test page (noindex) lets us test against the real theme + store, which a clean-room dev store wouldn't replicate. The dev app uses a different app-proxy subpath (or none — the local-first core doesn't need it), so it can't collide with prod's health-tool-1; the live /pages/roadmap keeps the prod app's block. Safety rule: always --config dev; never a bare shopify app deploy (that targets the prod app).

The promotion flow (note the deliberate gate)

Iterate on localhost → push to dev (auto-deploys to /roadmap/dev/ for real-URL + mobile testing) → push to the Shopify dev app for in-Shopify testing → merge dev into main (auto-deploys prod GitHub Pages) → explicit shopify app deploy to the prod Shopify app. Merging to main does NOT touch the live Shopify widget — that always needs the explicit deploy, so prod GitHub Pages and the live widget move independently and nothing reaches the live widget by accident.

HARD RULE (Brad, 2026-06-10): localhost is NEVER an approved origin

localhost must not appear in any allow-list: the Fly token-exchange endpoint's CORS list, the Google OAuth client's JavaScript origins and redirect URIs, the Dropbox redirect URIs, or any future OAuth client / API allow-list. Least-privilege: a malicious page or rogue dev server running on a user's own machine must never be able to drive our OAuth flows or server endpoints. All localhost entries were removed and verified 2026-06-10 (endpoint: localhost origin → 403). OAuth-flow testing happens only on the GitHub Pages surfaces — prod /roadmap/ and dev /roadmap/dev/ (same github.io origin); npm run dev:pages on localhost is for non-OAuth work.
