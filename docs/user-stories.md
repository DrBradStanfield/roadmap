# User Stories — Health by Dr Brad

The user-perspective spec for every journey in the tool. Written 2026-08-07, grounded in the first usage audit ([usage-audit-2026-08.md](usage-audit-2026-08.md)); the architecture reference is [architecture-v2.html](architecture-v2.html). Each story carries acceptance criteria (AC), the **usage evidence** we have, and the **test status** against the current suites.

## The product constitution (Brad, 2026-08-14 — read every story against this)

**What this is:** a preventative-care protocol generator plus a recall system. One five-minute check-up tells a user what to actually do — bloods, screenings, medications, supplements, weight, sleep, exercise — and the reminder calendar makes sure it keeps happening over the years. The website is the onboarding funnel and the calculator; **email is the product surface the user lives in.** For preventative care an annual touch is the correct cadence, not a retention failure — never chase app-engagement metrics here.

**The avatar:** 45–55, health-curious but unsystematic, low tech-literacy (they arrive from a longevity YouTube channel, so they already care; they just don't *systematize*). They will type an email address; they will mostly not connect a cloud drive — live funnel 2026-08-14: typed captures outnumber cloud connects roughly 10:1 on any denominator we have (~4–5 captures/day and 874+ lifetime vs 3 cloud connects EVER; a precise percentage depends on which visitor count you divide by, so the RATIO is the decision-driver). Design for zero thought: the right thing happens by default, visibly, with a one-click way out. The genuinely health-indifferent mass market only becomes reachable at the mobile app (US-25); don't contort the web product for a user who can't arrive yet.

**The promise (one sentence — keep it literally true):** *Your health data stays on your device. We keep one thing — your reminder calendar, what's due and when — so we can nudge you.*
What may be STORED on Brad's server, visibly disclosed: reminder labels + due dates, the enrolled email, a capability token. What is never stored as health data: measurements, lab values, medications, results, reasoning. (Precision matters — the loop reads this literally: chat questions and lab-report uploads do TRANSIT the server for AI processing (US-12/US-15/US-16), in memory for extraction, and chat messages persist as conversation logs in `chat_messages` — operational data the user typed at a chatbot, not a parsed health record. The promise is about what we KEEP as your health data: nothing.) A label can carry an inference (a lung-CT row implies smoking history); we **disclose that at enrolment rather than neuter the labels** — specific recall notices are what clinics already send, and specificity is what makes the email valuable standalone (Brad, 2026-08-14, superseding the "vague emails" option).

**Additive promise — applies ONLY to users who connect an AI assistant (US-32 Phase 1).** The sentence above is untouched and stays literally true for everyone who never connects one. For those who do, a second sentence applies. It takes effect when Phase 1 is DEPLOYED; the code ships in this commit, the secrets and the DNS do not.

> *"If you connect an AI assistant, your record still lives only in your storage — but our server reads it, in memory, to answer your assistant, and your assistant holds a sealed credential only we can open. We keep no copy. You cancel it in your Dropbox or Google settings; that also disconnects this website from your folder, and you can reconnect here in one click."*

**Durability (why localStorage loss is a bounded cost, not a crisis):** the artifacts survive — the PDF, every reminder email (each carries the full schedule per US-23 AC3 — for a typed user that's the newest copy we were given at capture, not a live sync), and calendar entries (US-24). Re-entry is cheap by design: the check-up takes five minutes, and re-entering IS re-assessing. Cloud sync (US-09) is the durability upgrade for the motivated, not the front door. The real fix is the mobile app (US-25). We never "fix" durability by holding health data server-side.

**Email architecture (decided 2026-08-11, reaffirmed 2026-08-14):** Resend sends everything programmatic — reminders, the plan-ready email, the feedback path. Klaviyo holds only the marketing list. Never merge them: Klaviyo suppression is list-wide, so a supplement-promo unsubscribe would silently kill "your colonoscopy is due" with no error anywhere. Two consents, two systems, two suppression lists.

**Architectural destination:** the mobile app (US-25) — on-device notifications (reminders with no server at all), HealthKit ingestion (data entry with no typing), durable storage (no wipe anxiety). Check near-term decisions against one question: *does this move toward or away from the phone?*

**Maintenance contract:** when a feature's behavior changes, update its story here in the same commit, then regenerate the browser companion: `npx tsx scripts/build-user-stories-html.ts` → `docs/user-stories.html` (linked from architecture-v2.html; never edit the html by hand). New tests cite the story ID (e.g. `US-04`) in a comment. New features follow CLAUDE.md → Development Pathway Lane B: story + acceptance criteria + a declared usage signal BEFORE code. The weekly product-health loop reads this file to judge whether reported friction contradicts an AC.

Legend for test status: ✅ covered · 🟡 logic covered but UI/journey untested · ❌ untested.

## Epic A — Entering health data

### US-01 · Progressive first fill (guest)
As a first-time visitor, I can start getting value by entering just sex + height, and the form progressively reveals more fields so I'm never confronted with a wall of inputs.
- AC1: Stage 1 shows only Units/Sex/Height; filling Sex+Height reveals Stage 2 (weight, waist, BP, birth month); filling Weight reveals Stage 3 (bloods, meds, screening, supplements).
- AC2: The next-expected field pulses (`.field-attention`).
- AC3: A returning visitor with saved data sees the full form immediately.
- AC4: Everything works with zero account/cloud — data persists in localStorage.
- Evidence: recordings show fast Stage-1 completion (8 clicks in 72s) and long engaged fills; blog→"Build my free plan"→tool is the working funnel.
- Tests: 🟡 `computeFormStage` in mappings.test.ts; no test that stages actually gate rendering. Gap: none planned (low churn).

### US-02 · Vitals entry incl. blood-pressure pair
As a user, I can type height, weight, waist and a paired systolic/diastolic BP quickly, and **my first click/tap on any cell or its unit label focuses the input** — no dead clicks.
- AC1: Clicking anywhere in a vitals cell (including placeholder text and the `mmHg`/unit chip) focuses the editable input.
- AC2: A BP entry is accepted only as a complete sys/dia pair; a half-pair doesn't save.
- AC3: Values are validated against clinical ranges with ok/warn/bad ticks before save.
- AC4: Numeric fields accept only numeric characters — letters and symbols are blocked at the keystroke (and stripped on paste), on every surface incl. Safari where `type="number"` doesn't enforce this.
- AC5: An out-of-range value shows a visible inline error (e.g. "Max 250 mmHg") on the field itself — never a silent save-block where garbage looks accepted.
- AC6: After typing an unambiguous, in-range systolic value, focus auto-advances to diastolic (immediately for 3-digit values 100–250; after a short pause for 2-digit values 60–99 that could still gain a digit).
- Evidence: **top friction in the audit** — dead clicks on the BP `▫▫▫/? mmHg` control and `mmHg` label in 3 of 15 recorded sessions; tooltip/units-picker dead clicks in 4.
- Tests: 🟡 `StartingInfoVitals.test.ts` covers BP pair routing/readiness logic; `blood-test-cell.test.ts` covers validation. ❌ No test that a cell-shell click focuses the input (the actual reported friction). **Action: fix + test (2026-08 backlog #1).**

### US-03 · Blood-test matrix entry & backfill
As a user, I can enter today's blood results in a draft column, and backfill older results under their historical date, and the matrix keeps every column aligned and scroll-synced.
- AC1: Draft column accepts values + a date (DraftDateCell); saving appends immutable measurements under that date.
- AC2: Typing into an existing dated column routes as backfill for that date.
- AC3: At most one active row per (metric, day); a same-day re-entry routes through correction (US-04), never a silent overwrite or lost draft.
- AC4: A failed save preserves the typed draft for retry.
- Evidence: engaged sessions show field-by-field entry of masked numeric values; feedback email 2026-03-22 reported values appearing under a wrong date (root cause never found).
- Tests: ✅ `matrix-save.test.ts` (task routing), `blood-test-cell.test.ts` (validation), merge tests (slot invariant), and date-defaulting semantics pinned in `roadmap-store-data-safety.test.ts` (2026-08-07).

### US-04 · Correcting a saved value (FHIR)
As a user who mistyped or whose lab import was wrong, I can click the saved cell, type the right value, and the display updates — while the old value is preserved as `entered-in-error` with a `correctsId` chain (never mutated or deleted).
- AC1: Correction happens on the surface where I see the value (matrix cell), not a separate admin page.
- AC2: Old row flips to `entered-in-error`; new row has `source='manual_correction'`, `correctsId=old id`; results use only active rows.
- AC3: Corrections converge across devices (status is sticky in merge).
- AC4: Correcting a non-latest value doesn't disturb the latest summary.
- Evidence: correction affordance was a deliberate UX decision (memory: corrections live with the data); `correction_made` funnel event now measures real usage — 9 corrections in the first instrumented week (2026-W32).
- Tests: ✅ merge.test.ts (`correctsId`/sticky status) + `roadmap-store-data-safety.test.ts` (store-level correction flow, 2026-08-07).

### US-05 · Unit switching
As a US/international user, I can flip between conventional and SI units at any time; every field, threshold, and suggestion re-renders correctly and stored data never changes (SI canonical at rest).
- Tests: ✅ units.test.ts round-trips + thresholds; validation error conversion covered. UI re-render untested (accepted).

### US-06 · Medications, supplements & screenings
As a user, I record what I actually take (real drug + dose, or none/not-tolerated/not-yet) and my screening dates; the plan's medication cascade and screening nudges follow the algorithm doc.
- AC1: FHIR MedicationStatement semantics per CLAUDE.md table; history is append-only change log.
- AC2: Brad's products appear as quick-add supplement chips.
- AC3: New screening types must round-trip through the file (7-step checklist in CLAUDE.md).
- Tests: ✅ suggestions/cascade logic in health-core; 🟡 roadmap-store covers med/supplement history appends; screening round-trip tests exist in mappings.test.ts.

## Epic C — Owning my data (local-first)

### US-09 · Choosing where my data lives
As a privacy-conscious user, I choose Google Drive / Dropbox / GitHub / my own WebDAV server / just-this-browser, from a neutral picker with no dark patterns, and can switch later without losing anything (data copies down, tokens dropped, new provider lifted).

**Positioning (constitution, 2026-08-14):** cloud sync is the **durability upgrade for the motivated**, not the front door — the funnel says typed captures outnumber cloud connects ~10:1 (US-23). The picker and its place in the flow stay exactly as they are (Brad's call, 2026-08-14); what changes is expectations: US-23, not this story, is how the mass avatar gets longitudinal value.
- AC1: OAuth (Drive/Dropbox) via PKCE redirect; GitHub/WebDAV via pasted credentials validated before commit.
- AC2: Switching providers copies current data to device first; log-off leaves the local copy intact.
- AC3: On-device guest data migrates up on first connect (merge, not overwrite).
- AC4 (added 2026-08-14, Sentry JAVASCRIPT-REMIX-3X): a failed cloud save is never memory-only — the working copy mirrors on-device at the moment of failure (marker-gated) and merges back up on the next successful cloud session or reconnect.
- AC5 (added 2026-09-03): a guest is told where the record lives as soon as the first value is entered, and every mention of Dropbox or Google Drive opens the picker. The input-tab line appears from the second input onward (form stage 2, the first moment a value exists); the plan-tab lines — one under the email helper, one under the plan beside a "Where do you want to keep your health record?" button — appear once a plan exists. All three are hidden once a cloud is connected. The provider names are buttons that fire `hr:open-backend-picker`, the event the picker host already listens for, so there is still exactly one picker.
- Evidence: a live Dropbox connect was captured on video (audit); privacy is a real user concern (feedback 2026-05-01). `cloud_connect_started/success` events now measure conversion/abandonment — first week (2026-W32): 5 started → 2 succeeded (small n; no failure-step metadata yet); 2026-W34: best week yet — 6 started → 5 succeeded (cumulative 14 → 8); 2026-W35: 5 → 3 (cumulative 19 → 11, ~58% all-time; drop step still unmeasured).
- Tests: ✅ AC5 covered (`storage-notice.test.tsx` gating + link-opens-picker; `standalone/storage-copy.test.tsx` plan block + picker copy; `ResultsPanel.copy.test.ts` pins the email-box line). 🟡 AC4 covered (`roadmap-store-data-safety.test.ts`, 2026-08-14: failure-mirror + merge-back-up + marker gate); AC2/AC3 lift + copy-down covered (`connect-migrate.test.ts`, 2026-08-14, real adapters); `logOff` teardown covered. ❌ Adapters + PKCE + picker flow remain untested.
- **Incident 2026-08-14 (sentry-fix run):** `migrateLocalInto()`/`copyDownToDevice()` had silently no-oped since first commit — `adapter.read()` called without its filename, `{file}` destructured from a `{body,version}` result, `SyncManager` missing its DocumentSpec — so AC3's guest-data lift and the pre-switch copy-down never ran. No error, no Sentry event; nothing typechecks `standalone/`, so tsc never saw it. Fixed same day (commit `665395d`): transfer primitive `saveRoadmapFileInto` beside `ROADMAP_DOC`, one `liftLocalInto` policy at all three connect flows (a failed lift never blocks or mislabels a connect; always Sentry-reported), failing-first tests, tsconfig now includes `standalone/`.

### US-10 · Cross-device convergence
As a user with a phone and a laptop, edits from both devices converge without conflicts: append-only arrays union, mutable scalars last-write-wins, corrections/deletions sticky, `eraseEpoch` wins wholesale.
- AC1: A fast edit on a fresh page load can never clobber unseen cloud data (hydration gate before first flush).
- AC2: Deleted measurements never resurrect via merge.
- AC3: Lab slots are keyed on the catalogue key at merge time (`labSlotKey`), so spelling variants converge: an upload's "Vitamin D" and an agent's `vitamin_d` on one day are one slot with one active row, not two rows the app can never reconcile.
- Tests: ✅ mergeFiles + store resurrect-guard + `sync-manager.test.ts` (read-merge-write, eraseEpoch wholesale win; 2026-08-07). AC3 pinned in `merge.test.ts` (spelling variants same day → one active, the loser `entered-in-error`, both rows kept; different days → both active) and `lab-rows.test.ts` (one series; 2026-09-02). Hydration gate (AC1) lives in HealthTool UI — still untested, accepted. **Writing these tests immediately caught a real defect — see US-11.**

### US-11 · Deleting my data
As a user, I can erase everything from the tool on every device (eraseEpoch bump + empty flush); there is no server copy to chase.

### US-29 · My AI agent reads and writes my record file directly — **docs-only, 2026-09-01**
As a user whose health record is one JSON file in my own cloud, I can point Claude Code or ChatGPT at it and have my agent read my history and append new results, because the format and the safety rules are published — not reverse-engineered.
- AC1: `docs/health-roadmap-file.schema.json` is a draft 2020-12 JSON Schema for `schemaVersion: 1`, published at a stable raw-GitHub URL, and a record built through the real code paths (`createEmptyFile` → `mergeFiles` → `migrateFile`) validates against it; a malformed record fails.
- AC2: `docs/agent-access.md` states where the file lives per backend, and matches the adapters (`adapter.ts` `ROADMAP_FILE_NAME`, `dropbox.ts`, `drive.ts`, `github.ts`) rather than restating folder names from memory.
- AC3: The write rules are stated as hard rules — never mutate or delete a row; a correction appends a row with `correctsId` and flips the old row to `entered-in-error` (one-way); fresh UUID per row; `meta.lamport`/`meta.eraseEpoch` are off-limits; SI canonical units for measurements, the lab's own unit for lab values; catalogue keys from `lab-catalog.ts` for `metricName`.
- AC4: The honest caveats are stated — a filesystem write has no lock and no version guard, the app merges on its next sync, malformed rows are dropped or ignored rather than repaired.
- Usage signal (declared honestly, per the constitution): **there is none from us, by design** — the file is in the user's storage and reading or writing it contacts no server we own, so no `product_events` row can exist without breaking the promise. What we can watch instead: unprompted GitHub issues, stars, and traffic on the repo and the schema URL; and organic movement in the existing cloud funnel (`cloud_connect_started/success`), since an agent user needs a cloud backend first. Both are weak and lagging. If neither moves within a quarter, this stays a docs page and earns no code.
- Tests: ✅ AC1 (`roadmap-file.schema.test.ts` — empty record, full merged record with a real `entered-in-error` correction pair, unknown-field forward-compat, malformed record, ten per-invariant negative cases, and an enum parity pin that deep-equals the schema's `MetricType`/`MeasurementSource`/`medicationKey`/document-`type` enums against `validation.ts` so drift breaks the build). ❌ AC2–AC4 are prose; nothing tests that the doc still matches the adapters — a folder rename would drift silently.

### US-30 · My agent computes my actual plan, offline — **added 2026-09-01**
As a user whose record is one JSON file, I can run `npx tsx tools/get-plan.ts ~/Dropbox/…/health-roadmap.json` and get the same plan the web app would give me — current values, what's due, suggestions with reasons and citations — on my own machine, with no network call and no LLM. US-29 published the format so any agent can READ the file; this is the part only this repo can do: turn it into Brad's protocol.
- AC1: `get-plan <file>` prints the plan — profile line, current key values (value + unit + clinical date), what's due, and suggestions grouped by priority with reason, guideline tags and citation URLs. The process opens no socket: the module graph is health-core + node builtins, nothing from `app/` or `widget-src/`.
- AC2: For the same record file the derived inputs and the resulting suggestion set are IDENTICAL to what the widget computes — same `latestActivePerMetric` → `measurementsToInputs` → `calculateHealthResults` path (US-07 AC4), asserted against a real `RoadmapStore.loadLatestMeasurements()` over a file built through the real code paths.
- AC3: `--json` emits `{ instruction, schemaVersion, generatedAt, today, profile, inputs, unitSystem, medications, screenings, currentValues, labValues, due, suggestions, source }` — stable field names, every current value and lab row carrying its `id` (what `edit-record.ts correct --id` takes), every suggestion carrying `id`/`category`/`priority`/`reason`/`guidelines`/`references`, so an agent can act on it without scraping prose. Documented in `--help`.
- AC4: `--html <out>` writes ONE self-contained file — inline CSS, no CDN, no script needed to read it — rendering the same plan for a human to keep or print.
- AC5: The file is untrusted input: it is loaded through `migrateFile`, so the hardened second-writer boundary applies (US-10/US-29), and a missing file, unparseable JSON, a newer `schemaVersion`, or a record with no height/sex exits 1 with one plain line plus a hint — never a stack trace.
- AC6: Read-only and silent: the tool never writes the record file, never mutates a row, never calls a model, and never emits telemetry. Health values reach stdout, or the `--html` file the user named, and nowhere else.
- Usage signal (declared honestly, per the constitution): **none from us, by design** — same as US-29, and for the same reason: the computation happens on the user's machine against their own file, so any event we could count would break the promise. What we can watch: Brad's own recurring use (user zero runs it from Claude Code against his real record), and unprompted outside interest — GitHub issues, stars, repo traffic. Both weak and lagging. If neither moves within a quarter this stays a tool for one user, and that is an acceptable outcome for a conviction bet.
- Tests: ✅ `tools/get-plan.test.ts` — AC2 parity against the real store (deep-equal inputs + identical suggestion ids), AC3 JSON shape + parseability, AC4 self-contained HTML (no `http(s)://` script/link refs), AC5 all four error paths + a null-riddled file surviving `migrateFile`, AC1 static import guard (no `app/`, no `widget-src/`, no network module). ❌ Not tested: how the HTML looks in a browser (read by eye).

### US-31 · My agent adds and corrects values in my record — **added 2026-09-01**
As a user whose record is one JSON file, I can run `npx tsx tools/edit-record.ts add ~/Dropbox/…/health-roadmap.json --metric ldl --value 2.1` and have the value land in my file with the FHIR rules kept for me — one active value per metric per day, corrections that append instead of overwrite, a backup before every write — instead of hand-editing JSON and hoping. US-29 published the write rules and US-30 gave the read half; this is the code that enforces those rules, and the same code the hosted MCP server will call.
- AC1 (altitude): the write operations are PURE FUNCTIONS in `packages/health-core/src/record-edits.ts` — `appendMeasurement`, `appendLabValue`, `correctValue` — each taking a `RoadmapFile` plus a request and returning a NEW file; the input is never mutated. Every rule below is enforced there, never in the CLI, so the CLI and the remote MCP server cannot drift apart.
- AC2 (slot): appending into a `(metric, calendar day)` slot an active row already holds is REJECTED, not written — a typed rejection carrying that row (agent-access rule 3; mirrors `RoadmapStore.addMeasurement`'s 409 semantics). Lab slots key on the catalogue key, so "Gamma GT" and `ggt` collide exactly as a lab import would.
- AC3 (correction): `correctValue` appends a row with `correctsId` and the ORIGINAL `recordedAt`, then flips the corrected row to `entered-in-error` — a correction changes the value, never the date. It works on measurements and lab values, and rejects an id that is absent or already `entered-in-error`.
- AC4 (range): a measurement outside `healthInputSchema`'s range for that metric is rejected with the range in the message. Lab values carry no ranges, so they are accepted as the lab reported them.
- AC5 (catalogue + units): `metricName` is stored as the `lab-catalog.ts` key whenever the test is catalogued (rule 10), and folded to lower case when it is not, so two spellings of one test share one slot. That resolution covers the spaced and Title-cased forms of a snake_case key — "Vitamin D" and "vitamin d" both file under `vitamin_d` — which is what an agent or a person actually types; the single `labSlotKey()` in `lab-catalog.ts` is the one place that key is computed, at write, merge and read time alike. `value` on a measurement is SI canonical (rule 8): the OPS resolve `--unit` through `units.ts`'s `resolveUnitSystem` — the same match the chatbot's proposed edits use, so the two writers cannot accept different spellings of one unit — and refuse anything else, so the CLI cannot mis-scale a value the MCP would scale correctly. A core metric written as a lab test is refused under any spelling — key or display label — because a core metric in `labValues` is invisible to the suggestion engine.
- AC6 (clocks + dates): every op moves `meta.updatedAt` to the write clock and touches no other `meta` field (rule 6), so the load clamp never rewinds the row just written — and it moves FORWARD only, as `mergeFiles` does, so a writer whose clock lags the file cannot rewind every other row's `createdAt` and hand the slot tie-breaks to a UUID comparison. `recordedAt` is refused if it is a day NO ONE has reached yet — the check is the latest calendar day anywhere on Earth (UTC+14), not the writing machine's own day, because an Auckland user's real today is tomorrow to a server in UTC and refusing it would be the server calling the user wrong. It is also refused if it is not a day that exists (`2026-02-30` rolls forward in `Date`, so it is caught by round-trip), and is STORED as the calendar day — never the caller's string, so what is echoed back and what lands on disk are the same thing.
- AC7 (no delete, v1 scope): there is no delete operation, and no medication, supplement or screening op — v1 writes clinical values only. Deletion stays what the app makes it (a document tombstone, or an `eraseEpoch` bump for everything), and neither is reachable from the CLI. The current-state rows are last-write-wins, so a second writer editing them needs the lamport discipline this v1 deliberately does not take on.
- AC8 (safe write): the CLI backs the record up beside itself (`health-roadmap.json.bak-<ISO>`, the last 3 kept and older ones pruned), then writes atomically — temp file, then rename, keeping the record's own permissions rather than widening them to the umask default. It refuses to write anything that is not a record (valid JSON that is an array, a string or an object without `schemaVersion` would otherwise be replaced by a blank record), refuses a `.bak` sibling as a target, follows a symlink to the real file instead of replacing the link, and refuses to write at all if the file changed between being read and being replaced. It writes the record and its `.bak` siblings and nothing else; no network, no model, no telemetry. **Strengthened 2026-09-01 by US-32, unified 2026-09-02:** that write boundary is now `packages/health-core/src/file-adapter.ts` — a `StorageAdapter` over one local path — and the CLI writes through `SyncManager` over it, exactly as the hosted server writes through `SyncManager` over Dropbox. So there is ONE write path across all three shells, and the storage backend is chosen purely by which adapter `SyncManager` is handed. Two consequences: the changed-file guard is now a `ConflictError` that `SyncManager` answers by re-reading and re-MERGING (a second writer costs a retry rather than a refusal, and cannot cause a lost update), and the stale-bytes check is a content hash rather than mtime+size, so an equal-length edit inside the same millisecond is still caught. **Made true 2026-09-02:** that check and the replace it guards are held under a `.lock` sibling (`O_EXCL`, 25 ms backoff, 5 s wait, abandoned after 10 s), because a backup, a prune and a temp write sit between them — four concurrent `edit-record` PROCESSES used to keep one row and print "Wrote" four times. `SyncManager`'s verify-after-write now also asserts every row id it just wrote is present on the re-read, so a writer that loses anyway reports it instead of confirming it. It also refuses a file that carries `schemaVersion` but holds junk where its rows belong (`measurements`, `labValues`, `medications`, `supplements` present but not a list) — `migrateFile` would have blanked such a file and the CLI would have reported success — and refuses a record written by a newer app at the READ, so it is out of reach in both directions. **Moved 2026-09-02:** that shape gate is `ROADMAP_DOC.migrate` (`roadmap-doc.ts`), not the adapter, so EVERY adapter inherits it — Dropbox, Drive, GitHub, the local file — on `SyncManager.load()` and on the re-read that precedes every save. A null or absent row array still normalises to `[]`: it holds no rows, so nothing is lost.
- AC9 (round-trip): bytes the CLI wrote load identically in the widget's own data layer — a real `RoadmapStore` over the written file reads the new value as current — and `migrateFile` plus a self-merge leave the file unchanged, because the edit is already canonical. Two devices that edit different slots from the same base both keep their edit through `mergeFiles`.
- AC10 (errors): the same discipline as US-30 — exit 1 with one plain line plus a hint, never a stack; an occupied slot prints the row that holds it and how to correct it instead; a correction echoes old → new. Text out of the record reaches the terminal as data: control characters are stripped and newlines collapsed, so a lab name cannot forge a line of output that reads as the tool's own.
- AC11 (today, per writer): "today" — the day a plan or a reminder measures against, and the default `recordedAt` where there is one — is the WRITER's own local calendar day. That works where the writer runs on the user's machine: the widget slots by the browser's local day and the CLI's `--date` defaults to the terminal's. **It cannot work on the hosted server, and pretending otherwise was the bug (fixed 2026-09-03):** a Fly box in UTC has no way to know an Auckland user's day, so a defaulted date was the UTC day and every user east of UTC was logged a day behind for part of their day. The hosted answer is not a better default but no default: `recordedAt` is REQUIRED on `add_measurement` and on every `add_lab_values` row, and the assistant — which does carry the user's date — passes the user's own local calendar day, asking if it does not know it. The schema is shared, so the stdio server asks for it too. `get_plan`'s due-dates still measure against the server's day and can be a day out either way; that is cosmetic and is not fixed here. On the hosted surface `expected` is REQUIRED for every field being changed (`null` claims the field is unset) and the write costs a correction's weight — 5 — because a profile field has no superseded copy to read back. Display preferences (`unitSystem`, `unitOverrides`) stay out of reach: they are how the app draws the screen, not what the record says about the person.

Because it now writes to an external system the tool is no longer read-only (`readOnlyHint: false`, `openWorldHint: true`) and costs a correction's five against the connection's hourly write allowance — charged before the call, so a refusal spends too, exactly as `correct_value` does. - AC10 (nothing per user is stored, anywhere): no table, no row, no session. We hold the key and no blob; the vendor holds a blob and no key. What DOES exist and is counted, not hidden: a per-machine authorization-code set, per-IP rate maps, a bounded client-metadata cache, and Fly's own proxy metadata. None is health data and none is a per-user row. What sealing does NOT protect: the blob the vendor holds is a live bearer against `/mcp` until it expires — no key needed. - AC11 (revocation is honest about what it cannot do): the access blob expires in 1 hour and the refresh blob in 90 days. - AC13 (the accepted residual, stated rather than softened): an injected agent reads first, so it knows every row id and value, and with `correct_value` it can silently falsify current values — each original flipping to `entered-in-error`, irreversibly — and `get_plan` will then generate a coherent, wrong protocol from the falsified record. - AC14 (`state` comes back byte-identical): `state` is the client's own opaque value, so it is returned **byte-identical up to 1024 characters; longer is refused with `invalid_request`, never truncated**. We used to `.slice(0, 512)` it. OpenAI's platform relay sends 521 characters, got a 512-character stump echoed back on the callback, and rejected every ChatGPT connection with "Invalid OAuth state" — a truncated `state` is worse than a missing one, because it looks valid until the far end compares it. The cap is set by the `__Host-mcp-state` cookie rather than by taste: the sealed state is padded to a fixed bucket, and 1024 keeps the whole Set-Cookie line near 3.1 KB, inside the 4096 bytes browsers allow, where the next bucket up would put it at ~5.8 KB and the browser would drop the cookie in silence. Twice what OpenAI sends, and more than Claude does.
- AC14 (the front door): OAuth 2.1 with PKCE S256 only, our own consent screen — and the consent screen is ENFORCED, not merely displayed: pressing Connect mints a 32-byte nonce, seals the state naming it into a first-party `__Host-mcp-state` cookie (Secure, HttpOnly, SameSite=Lax, 10 minutes), and hands Dropbox the nonce alone. The callback requires the cookie, compares the echoed value to the sealed nonce timing-safely, and clears it; without the cookie it is a 400 page and no redirect. (Before this, found by review 2026-09-02, a state blob from an unauthenticated `GET /mcp/authorize` could be replayed into a forged callback and mint an authorization code with no consent at all.) The refresh lifetime is 90 days ABSOLUTE from consent — it used to slide forward on every refresh, so it expired for nobody. A record whose `schemaVersion` is newer than this server understands is out of reach in BOTH directions: the record is migrated before any tool sees it, so reads refuse too, and the refusal says so rather than claiming the record is readable. Known residual, unchanged from US-11: a RAW deletion in the Dropbox UI carries no `eraseEpoch` signal, so a stale writer legitimately re-creates the content.
- AC17 (bounded, and honest when it refuses): request bodies are capped — 64 KB at the OAuth doors, 1 MB at `/mcp`, 413 over. `/token` is rate-limited per IP and `tools/call` per connection, both generously: a whole vendor's users arrive from one egress range, so a tight per-IP limit would lock out honest traffic rather than an attacker. The IP those limiters key on is `Fly-Client-IP`, which Fly's proxy writes, not `X-Forwarded-For`, which a client can forge. A malformed `MCP_SEAL_KEYS` or `MCP_CLIENT_HMAC_KEY` disables the feature (404) with one log line naming the variable and never its value, rather than turning every route into a 500. A record written by a NEWER app version refuses reads as well as writes — it is migrated before any tool sees it — and the refusal says that rather than claiming the record is readable. A failure that is ours, not the record's and not the provider's, reaches the client as JSON-RPC -32603 on the request's own id, never worded as a refusal the user could act on, on the hosted and the local server alike.

### US-34 · The record on screen keeps up — **added 2026-09-02**
As someone with the roadmap open in a tab while my AI assistant edits my record — or with the same record open on my laptop and my phone — I see the change appear where I am looking, instead of wondering whether it worked and reloading the page to find out. US-32 made an assistant able to write; this is the half that makes a write visible to the person it was made for.
- AC1 (when it re-reads): `RoadmapStore.refreshFromRemote()` re-reads the record through the ordinary `SyncManager.load()` and merges what comes back with `mergeFiles` — no second read path, no second source of truth. It runs when the provider says the file moved, when the tab becomes visible, and when the window takes focus. **The provider's own change signal replaced the 60-second timer on 2026-09-02**: `StorageAdapter.watch(fileName, onChange, signal)` is optional, and an adapter that has one never runs the poll. Dropbox holds a `files/list_folder/longpoll` open against the app folder root (the `notify` host, which takes no access token — the cursor is the credential; `files/list_folder/continue` advances it before the store is told), so a write from another device or an assistant arrives in about a second, and a quiet tab costs two requests a minute. Google Drive has no browser long-poll — its push channels need a public webhook — so it walks `changes.list` from a `changes/startPageToken` every 3 seconds and calls only when a change names our file id: 20 requests a minute while the tab is visible, and none when it is not. Both back off on failure, doubling to a 60-second ceiling, and re-establish their cursor from scratch. A backend with no watch (localStorage has no second writer; GitHub and WebDAV have no cheap one) keeps the 60-second poll. A hidden tab watches and polls nothing — it has no screen to keep up to date, and a phone left on a background tab would spend the day holding a connection open; the watch is aborted when the tab is hidden and taken up again on return. A leading-edge 5-second throttle stops `focus` and `visibilitychange` — which fire together on a tab switch — making two round trips out of one return, and a push it swallows is held and re-read when the window is out: a watch fires once per change and then goes quiet, so dropping one would lose it.
- AC2 (a pending local edit always wins): it re-reads NOTHING while a save is in flight or the persist debounce is still pending, and it throws away a merge whose base moved while the read was in the air — the check after the read is that the working copy is the same OBJECT it merged from, because a save can start and finish inside the read window and leave `writePending` false again by the time the answer lands. The working copy is then AHEAD of the cloud, and merging a read taken before the edit existed would fight the write that is about to go up. It also does nothing on a localStorage-only backend: there is no second writer to hear from.
- AC3 (only a real change is announced): the merged file is compared to the working copy by CONTENT, with `meta` excluded — a merge always bumps the file's own clock, and Drive returns no version to compare, so bytes are the only honest test. Unchanged means no event, no re-render and no counted event.
- AC4 (how the page hears): the store dispatches a DOM event, `hr:remote-changed` (`REMOTE_CHANGED_EVENT`, the same convention as `hr:sync-pending-changed`), and `HealthTool` re-runs the load path it already uses after an upload — `loadLatestMeasurements`, which carries the profile prefill. The store cannot call the API layer itself: the v2 builds alias `lib/api` to `lib/roadmap-data`, which imports the store, and the cycle would be real. The listener is registered once, in `initRoadmapStore`, which is where both surfaces start their data layer. **It does nothing while the demographics form is dirty** (`hasUnsavedProfileEdits`, over `PREFILL_FIELDS`): re-running the load path replaces the form's inputs, and a change landing on a half-entered height would take those keystrokes with it. Nothing is lost, and nothing waits on the user coming back: the change is HELD, and the save that carries the edit up replays it (`createRemoteChangeRelay`, `widget-src/src/lib/remote-replay.ts`) — several changes held during one edit collapse into a single re-render.
- AC5 (a bug this uncovered, fixed here): a profile-only edit in the app — changing sex, height or birth date with no measurement alongside it — called `applyProfileChanges` and never called `touch()`, so it scheduled no save at all and sat in memory until some later unrelated edit carried it up. Every other mutation on the store touches. Fixed in the same commit.
- Usage signal (declared, per the constitution): `remote_change_applied` in `product_events` — fired by `HealthTool` when it has actually re-rendered on a remote change. The NAME only: never which field changed, never a value. Read against `results_viewed`: if it stays at zero once the connector guides are out, either nobody is running an assistant against a record they also have open, or the re-read is not firing — and the two are told apart by whether hosted MCP tool calls are happening at all.

- AC1 (one tool, two phases, and the first never writes): a single tool `import_documents` in `packages/health-core/src/mcp-tools.ts`, published on every surface like the other seven. - AC2 (the folder route, Dropbox): with no `file` argument the tool lists the ROOT of the connected app folder (`dropboxListFolder`, files only, `has_more` followed) and takes the files named in `fileNames`, or every importable file when the argument is absent. A name in `fileNames` is matched by equality against the listing and the file is downloaded by the listing's `id`, so a name never forms a path; a name not in the listing refuses the call and names what the folder holds. The server fetches `download_url` and nothing else: host on a closed allow-list — `files.oaiusercontent.com` exactly, or the region-suffixed Azure blob family `^oaisdmntprn[a-z0-9-]*\.blob\.core\.windows\.net$` that ChatGPT hands out for a dragged-in file (live 2026-09-05: `oaisdmntprnznorth.blob.core.windows.net`; the exact-host list refused it and the drag failed), plus any exact hosts in `CHATGPT_FILE_HOSTS`; a look-alike (`evil-oaisdmntprn…`, `…windows.net.evil.com`) is refused, and a refused host is warned by hostname only, never the URL, which is how a new legitimate host gets learned, `redirect: "error"`, 10-second abort, a 20 MB byte cap read through `readCappedBytes`, and the type decided by magic bytes (`%PDF-`, `PK\x03\x04`, JPEG, PNG), never by the declared `mime_type` or the file name. Claude cannot pass a file to a remote tool at all; the tool description says the folder route is the Claude way.
- AC5 (one extraction pipeline, not a second): every file goes through the existing `extractOrClassify` (`app/lib/anthropic.server.ts`, `UNIFIED_SYSTEM_PROMPT`, unit resolution) — the same call the website makes — with `attempts: 1, httpAttempts: 1` (no outer retry AND no inner HTTP retry on this path) and a timeout of min(20 s, what is left of the budget), so one model call ends inside the deadline by construction. Every other I/O in the call is ABORTED at the same deadline, not abandoned (2026-09-04): `runImport` starts one clock per call — 40 s, `ImportSurface.budgetMs` — before it reads the record, and every adapter call the call makes carries a `deadlineSignal` derived from it: the record's read and write through `SyncManager` (`load`/`save` take a signal and pass it to `read`/`write`/verify), the folder listing, each download, the stale-pending sweep, the ChatGPT file fetch, the pending-file write in `stash`, and the commit's read and delete of the pending file. `StorageAdapter`'s `read`/`write`/`readDocument`/`list`/`remove` take that signal as an optional last argument; the Dropbox and Drive REST adapters hand it to `fetch` (`fetchOrFail` joins it with the adapter's own 30 s bound via `AbortSignal.any`), so a provider that took the socket and went quiet is cut off at the deadline and its promise rejects with a `TimeoutError`; the memory and file adapters refuse to start once it is aborted. What the assistant sees: a hung listing or pending-file read is a refusal, a hung download is `skipped: "time"`, a hung pending write refuses the extract, a hung delete is swallowed and swept later, and a hung record read or write surfaces as the provider's "did not answer" refusal. An extract's downloads and model calls end 4 s before the deadline (`BUDGET_RESERVE_MS`), leaving that reserve for slotting and the stash. Nothing an import does runs past the deadline. A PDF is passed to the model whole, as a base64 `document` content block (the `'pdf'` page type in `lab-extraction.ts`'s `pagesToContentBlocks`, verified with one real Haiku call 2026-09-04: 3,369 input tokens for a one-page PDF; the website's `text|image` route schema untouched). Images go as `image` blocks; a ZIP is opened server-side with JSZip (already in the Fly image, now declared in the root manifest) under caps: 20 MB per ZIP, 20 importable entries, 5 MB per entry INFLATED — the central directory's declared size is only the cheap first refusal, the bytes are counted as they inflate and the stream is stopped past the cap. Entries are taken by position, typed by magic bytes, and nested zips are skipped by name. The junk filter (`__MACOSX/`, `.DS_Store`, dotfiles at any depth, `Thumbs.db`) lives in health-core and the widget's `zip-extract.ts` calls it.
- AC6 (what the record already holds): every extracted value is slotted against the record by the one rule the website's review table uses — `findActiveInSlot` + `slotState` in `record-edits.ts`, equality on the DISPLAYED string so float noise never manufactures a conflict: `free`, `held_equal` (already recorded; accepting it writes nothing), or `held_different` with the existing row id and value, and `replaceable` when the held row is inside the hosted 90-day correction window. One candidate per (metric, day) slot per call. A document is `already_imported` when a live `documents[]` row carries its `sourceFileName` OR its bytes' hash in `contentHash` (`sha256-<hex>`, the same field the website's archive keys on — ONE dedup key for both writers), and is not sent to the model again; a rename defeats the name check but not the hash, and values are protected by slots regardless. The website's `bulkSaveDocuments` treats a hash on a row WITH a `fileRef` as "already archived" and a hash on a row WITHOUT one as the connector's metadata-only import: uploading that same PDF on the website writes the blob into a new row and tombstones the metadata-only one — only once the blob write succeeds; a failed write leaves the connector row live so its hash still dedups — so the original gets archived rather than silently skipped. A value the record would refuse — out of range, a future day, a core metric under a lab name — is dropped at extract time with the reason, by a dry run of the same `appendMeasurement`/`appendLabValue` the write tools use, so the receipt never carries a value the record would not take. A lab report with no usable collection date is `failed: no_date`.
- AC7 (the receipt): the extract writes its payload — candidates plus document metadata, never document text — to the user's folder as `imports/pending-<uuid>.json` through the same adapter that holds the record, and the receipt the assistant carries is `{id, exp, conn, sha256}` sealed as an `'import'` blob by the same `seal`/`unseal` every credential uses (AES-GCM under HKDF from `MCP_SEAL_KEYS`, bound to the client and resource in the authenticated header, ~550 bytes, under `MAX_RECEIPT_LENGTH`), with `conn` binding it to the connection hash, a one-hour expiry, and every configured key tried so a rotation inside the hour does not strand it. Commit verifies the receipt BEFORE anything is charged — a forged receipt costs nothing — then reads the pending file, checks its hash against the receipt, applies the selection, and deletes the file; a second commit of the same receipt finds nothing and refuses. An extract sweeps its own `imports/pending-*.json` files older than 24 h, never another file the user keeps in that folder. The assistant can only SELECT candidate ids (`accept`, `replace`); it cannot edit a value or invent a document, which is why this write may land `documents[]` rows when `add_lab_values` may not (US-32 AC5). A payload the model retyped is exactly `add_lab_values`, which exists.
- AC8 (the commit): all-or-nothing. Accepted `free` candidates and `replace`d `held_different` ones land through `bulkAppendValues` — the same pure function the website's `bulkSaveMeasurements`/`bulkSaveLabValues` now call — core metrics as measurements in SI, the rest as lab values in the lab's own unit, with `source: "lab_import"`; a `replace` supersedes the held row with `correctsId` and flips it to `entered-in-error`, after the commit's own two checks — the held row still carries the id and value the receipt names (the `expectedValue` guard), and `replaceable` computed at extract against the surface's 90-day rule (enforced ONCE, here; the receipt's hash keeps it honest); a `held_different` id in `accept` but not `replace` writes nothing — silence is not consent. Each extracted document not `already_imported` lands as a `documents[]` row metadata-only (`fileRef: ""`, `contentHash: "sha256-<hex>"` of the bytes, the sniffed `mimeType`, `extractedText: ""`, `metadata: {importedVia: "connector"}`), and the original stays where the user put it until the website archives it (AC6). The commit re-reads the record fresh: a slot whose active row moved since the extract (a different id or value, or a free slot now taken) refuses the WHOLE commit, naming the slot, and the assistant extracts again. A document needs no selection: a clinic letter yields zero candidates, so the only commit it can get is an empty one, and that commit files the letter (`already_imported` keeps it from landing twice). So the extract must not read as "nothing to do" (live 2026-09-05 it did — "0 value(s) are new" — and ChatGPT never offered to file the letter): the extract result carries `documents` (source name, title bounded per AC9, type, date), its `next` says how many documents can be filed and that a commit with empty `accept` and `replace` files them, and the tool description says the same; titles stay out of `next`, the field the assistant follows. A commit whose `accept` and `replace` are both empty AND whose payload holds no unfiled document writes nothing, changes no version, and says so — this is what makes live testing against a real record safe: a lab report's empty commit is a true no-op. Not atomic across devices: a second device writing the same slot at the same moment leaves two actives until the next merge demotes the newer one, as with every write; the commit's text says so.
- AC9 (nothing kept, and who sees what): bytes are held in memory for one request and dropped; no file, no value and no extracted text is written anywhere on our side; the tool result and the pending payload carry numbers, units, dates, file names, a classification and `title`/`question` bounded to 120 printable characters and labelled as text from the document — never `contentMarkdown`, `extractedText` or the extractor's free-form `metadata`. `UNIFIED_SYSTEM_PROMPT` tells the model the document is data, not instructions; a document whose only content is an instruction block reaches the assistant as a bounded title and no candidates. The `mcp_tool_call` counter stays `{tool, client, outcome}`; Sentry gets error names and the file kind only; no log line carries a file name or a value (tested). What DOES change, and is disclosed rather than hidden: on this route the file is sent to Anthropic's API under OUR key for extraction — the consent screen, the privacy addendum, the ChatGPT listing's Compliance section, both connector guides, agent-access.md, lab-upload.md, the architecture map and the READMEs say so, and say that the website's upload instead keeps the PDF in the browser.
- AC10 (bounds): an extract spends `1 + 1 per file` of the connection's 60 weighted writes an hour — the `1` is the tool's declared `cost: 'add'` charged by the loop's `beforeCall` like every write, the per-file charge goes through the same `chargeWrites` before each model call (so a refused file still costs, and there is ONE refusal wording); a commit spends `1 + 5 per replace` (charged after the receipt verifies AND every id is checked against the payload, so invented ids cost nothing); 30 files per connection per day (`IMPORT_FILES_PER_DAY`, the `importFiles` counter beside the write allowance in `mcp-grants.server.ts`, keyed on the connection hash); the website's per-machine daily file cap (`AI_DAILY_FILE_CAP`) is one `createQuotaCounter` both callers spend from (`machineFiles` in `rate-limiter.ts`). All three counters are per machine, so the real ceiling is × machines × 2 Fly apps. Files are extracted three at a time under a whole-call budget of 40 s (`MCP_IMPORT_BUDGET_MS`; ChatGPT cuts a tool call at 60 s), and what is not reached is `skipped: "time"` or `remaining`, never half-answered. `unrecognized` is capped at 50 lines a call (`MAX_UNRECOGNIZED_LINES`), 120 characters each.
- AC11 (the local server): the stdio server holds no model key and opens no socket (US-32 AC7), so `import_documents` there refuses in one sentence pointing at the website or the hosted connector. It stays in the list: one tool list on every surface, no hosted-only subset to drift. A local-path variant was not built: the local server has no model to read a file with.
- AC12 (every place a tool is named moves together): `MCP_TOOL_NAMES` (parity test), `OUTPUTS`, the prompts list (a fourth prompt, "Import my lab files"), the guards test's hand-written name list, the consent page's capability list, the privacy addendum, `chatgpt-app-listing.md` (annotations table, three justifications, a starter prompt, two test cases, the Compliance sentence), `agent-access.md`, `mcp-architecture.md` §3, both connector guides, `getting-started.md`, `reference.md`'s inventory, `deploy-runbook-mcp.md`'s verify sequence, the architecture map, both READMEs, `.env.example`. Annotations, honestly: not read-only, destructive (a `replace` flips a row for good), not idempotent, open-world (it reaches Anthropic's API and, on the ChatGPT route, OpenAI's file host).
- Usage signal (declared, per the constitution): `mcp_tool_call` with `tool: "import_documents"` covers success and refusal. One more event, value-free: `mcp_import` with `route` (`dropbox` | `chatgpt_file` | `chatgpt_refused` — a drag the server would not read: host, size, timeout — | `drive_refused`), `phase` (`extract` | `commit`) and `files` as a bucket (`0` | `1` | `2-5` | `6-20`). It answers the one question that decides the feature's shape — which route people actually use, and whether the Drive refusal is met often enough to be worth a different answer. Never a file name, never a value, never a count precise enough to identify a record.
