# User Stories — Health by Dr Brad

The user-perspective spec for every journey in the tool. Written 2026-08-07, grounded in the first usage audit ([usage-audit-2026-08.md](usage-audit-2026-08.md)); the architecture reference is [architecture-v2.html](architecture-v2.html). Each story carries acceptance criteria (AC), the **usage evidence** we have, and the **test status** against the current suites.

## The product constitution (Brad, 2026-08-14 — read every story against this)

**What this is:** a preventative-care protocol generator plus a recall system. One five-minute check-up tells a user what to actually do — bloods, screenings, medications, supplements, weight, sleep, exercise — and the reminder calendar makes sure it keeps happening over the years. The website is the onboarding funnel and the calculator; **email is the product surface the user lives in.** For preventative care an annual touch is the correct cadence, not a retention failure — never chase app-engagement metrics here.

**The avatar:** 45–55, health-curious but unsystematic, low tech-literacy (they arrive from a longevity YouTube channel, so they already care; they just don't *systematize*). They will type an email address; they will mostly not connect a cloud drive — live funnel 2026-08-14: typed captures outnumber cloud connects roughly 10:1 on any denominator we have (~4–5 captures/day and 874+ lifetime vs 3 cloud connects EVER; a precise percentage depends on which visitor count you divide by, so the RATIO is the decision-driver). Design for zero thought: the right thing happens by default, visibly, with a one-click way out. The genuinely health-indifferent mass market only becomes reachable at the mobile app (US-25); don't contort the web product for a user who can't arrive yet.

**The promise (one sentence — keep it literally true):** *Your health data stays on your device. We keep one thing — your reminder calendar, what's due and when — so we can nudge you.* What may be STORED on Brad's server, visibly disclosed: reminder labels + due dates, the enrolled email, a capability token, and the date each label was last sent — that row and nothing else (`app/lib/reminder-v2.server.ts`). "No health data on the server" means no health VALUES; a screening label and a due date are not nothing, which is why they are disclosed at enrolment. What is never stored as health data: measurements, lab values, medications, results, reasoning. (Precision matters — the loop reads this literally: chat questions and lab-report uploads do TRANSIT the server for AI processing (US-12/US-15/US-16), in memory for extraction, and the blog chat bubble, Discord and YouTube persist their conversation logs in `chat_messages` — operational data the user typed at a chatbot, not a parsed health record. The main widget's chat, which sends the record with every turn, persists no message content at all since 2026-09-10 (US-15 AC7); the question text alone is kept 30 days for the matching audit and then removed. The promise is about what we KEEP as your health data: nothing.) A label can carry an inference (a lung-CT row implies smoking history); we **disclose that at enrolment rather than neuter the labels** — specific recall notices are what clinics already send, and specificity is what makes the email valuable standalone (Brad, 2026-08-14, superseding the "vague emails" option).

**Durability (why localStorage loss is a bounded cost, not a crisis):** the artifacts survive — the PDF, every reminder email (each carries the full schedule per US-23 AC3 — for a typed user that's the newest copy we were given at capture, not a live sync), and calendar entries (US-24). Re-entry is cheap by design: the check-up takes five minutes, and re-entering IS re-assessing. Cloud sync (US-09) is the durability upgrade for the motivated, not the front door. The real fix is the mobile app (US-25). We never "fix" durability by holding health data server-side.

**Email architecture (decided 2026-08-11, reaffirmed 2026-08-14):** Resend sends everything programmatic — reminders, the plan-ready email, the feedback path. Klaviyo holds only the marketing list. Two consents, two systems, two suppression lists.

**Architectural destination:** the mobile app (US-25) — on-device notifications (reminders with no server at all), HealthKit ingestion (data entry with no typing), durable storage (no wipe anxiety). Check near-term decisions against one question: *does this move toward or away from the phone?*

## Epic A — Entering health data

### US-01 · Progressive first fill (guest)
As a first-time visitor, I can start getting value by entering just sex + height, and the form progressively reveals more fields so I'm never confronted with a wall of inputs.
- AC1: Stage 1 shows only Units/Sex/Height; filling Sex+Height reveals Stage 2 (weight, waist, BP, birth month); filling Weight reveals Stage 3 (bloods, meds, screening, supplements).
- AC2: The next-expected field pulses (`.field-attention`).
- AC3: A returning visitor with saved data sees the full form immediately.
- AC4: Everything works with zero account/cloud — data persists in localStorage. Components import the local-first data module directly; retired account flags cannot enable an old server health-data path.
- Evidence: recordings show fast Stage-1 completion (8 clicks in 72s) and long engaged fills; blog→"Build my free plan"→tool is the working funnel.
- Tests: 🟡 `computeFormStage` in mappings.test.ts; no test that stages actually gate rendering. Gap: none planned (low churn).

### US-02 · Vitals entry incl. blood-pressure pair
As a user, I can type height, weight, waist and a paired systolic/diastolic BP quickly, and **my first click/tap on any cell or its unit label focuses the input** — no dead clicks.
- AC1: Clicking anywhere in a vitals cell (including placeholder text and the `mmHg`/unit chip) focuses the editable input.
- AC2: A BP entry is accepted only as a complete sys/dia pair; a half-pair doesn't save.
- AC3: Values are validated against clinical ranges with ok/warn/bad ticks before save.
- AC4: Numeric fields accept only numeric characters — letters and symbols are blocked at the keystroke (and stripped on paste), on every surface incl. Safari where `type="number"` doesn't enforce this.
- AC5: An out-of-range value shows a visible inline error (e.g. "Max 250 mmHg") on the field itself — never a silent save-block where garbage looks accepted.
- AC6: After typing an unambiguous, in-range systolic value, focus auto-advances to diastolic (immediately for 3-digit values 100–250; after a short pause for 2-digit values 60–99 that could still gain a digit).
- Evidence: **top friction in the audit** — dead clicks on the BP `▫▫▫/? mmHg` control and `mmHg` label in 3 of 15 recorded sessions; tooltip/units-picker dead clicks in 4.
- Tests: 🟡 `StartingInfoVitals.test.ts` covers BP pair routing/readiness logic; `blood-test-cell.test.ts` covers validation. ❌ No test that a cell-shell click focuses the input (the actual reported friction). **Action: fix + test (2026-08 backlog #1).**

### US-03 · Blood-test matrix entry & backfill
As a user, I can enter today's blood results in a draft column, and backfill older results under their historical date, and the matrix keeps every column aligned and scroll-synced.
- AC1: Draft column accepts values + a date (DraftDateCell); saving appends immutable measurements under that date.
- AC2: Typing into an existing dated column routes as backfill for that date.
- AC3: At most one active row per (metric, day); a same-day re-entry routes through correction (US-04), never a silent overwrite or lost draft.
- AC4: A failed save preserves the typed draft for retry.
- Evidence: engaged sessions show field-by-field entry of masked numeric values; feedback email 2026-03-22 reported values appearing under a wrong date (root cause never found).
- Tests: ✅ `matrix-save.test.ts` (task routing), `blood-test-cell.test.ts` (validation), merge tests (slot invariant), and date-defaulting semantics pinned in `roadmap-store-data-safety.test.ts` (2026-08-07).

### US-04 · Correcting a saved value (FHIR)
As a user who mistyped or whose lab import was wrong, I can click the saved cell, type the right value, and the display updates — while the old value is preserved as `entered-in-error` with a `correctsId` chain (never mutated or deleted).
- AC1: Correction happens on the surface where I see the value (matrix cell), not a separate admin page.
- AC2: Old row flips to `entered-in-error`; new row has `source='manual_correction'`, `correctsId=old id`; results use only active rows.
- AC3: Corrections converge across devices (status is sticky in merge).
- AC4: Correcting a non-latest value doesn't disturb the latest summary.
- Evidence: correction affordance was a deliberate UX decision (memory: corrections live with the data); `correction_made` funnel event now measures real usage — 9 corrections in the first instrumented week (2026-W32).
- Tests: ✅ merge.test.ts (`correctsId`/sticky status) + `roadmap-store-data-safety.test.ts` (store-level correction flow, 2026-08-07).

### US-05 · Unit switching
As a US/international user, I can flip between conventional and SI units at any time; every field, threshold, and suggestion re-renders correctly and stored data never changes (SI canonical at rest).
- Tests: ✅ units.test.ts round-trips + thresholds; validation error conversion covered. UI re-render untested (accepted).

### US-06 · Medications, supplements & screenings
As a user, I record what I actually take (real drug + dose, or none/not-tolerated/not-yet) and my screening dates; the plan's medication cascade and screening nudges follow the algorithm doc.
- AC1: FHIR MedicationStatement semantics per CLAUDE.md table; history is append-only change log.
- AC2: Brad's products appear as quick-add supplement chips.
- AC3: New screening types must round-trip through the file (7-step checklist in CLAUDE.md).
- AC4: History charts show recorded medication starts, stops, switches and dose changes. Dates mean when the change was recorded, not a claimed treatment start date. Legacy rows without a change type stay stored but produce no invented event. Stops with a status placeholder identify the medication category. Chart ranges include recorded events even with one old result; each pin stays at its exact recorded date, with a numbered dated list below. Selecting or keyboard-focusing a list entry shows only that event's number, above other lines, using its stable row ID; dense same-time events remain readable.
- Usage signal: `medication_history_viewed` measures annotated-chart reach; no medication names, doses or dates enter telemetry.
- Tests: ✅ suggestions/cascade logic in health-core; ✅ roadmap-store covers med/supplement history appends and US-06 AC4 projection; medication-annotations tests cover labels/stops/legacy rows/dose edge cases; HistoryPanel.test.tsx covers numbered pins, list order, toggle and the event (live verification pending); screening round-trip tests exist in mappings.test.ts.

## Epic C — Owning my data (local-first)

### US-09 · Choosing where my data lives
As a privacy-conscious user, I choose Google Drive / Dropbox / GitHub / my own WebDAV server / just-this-browser, from a neutral picker with no dark patterns, and can switch later without losing anything (data copies down, tokens dropped, new provider lifted).

**Positioning (constitution, 2026-08-14):** cloud sync is the **durability upgrade for the motivated**, not the front door — the funnel says typed captures outnumber cloud connects ~10:1 (US-23). The picker and its place in the flow stay exactly as they are (Brad's call, 2026-08-14); what changes is expectations: US-23, not this story, is how the mass avatar gets longitudinal value.
- AC1: OAuth (Drive/Dropbox) via PKCE redirect; GitHub/WebDAV via pasted credentials validated before commit.
- AC2: Switching providers copies current data to device first; log-off leaves the local copy intact.
- AC2b (2026-09-10): Connecting GitHub refuses a PUBLIC repository, and so does writing to one. `connect()` reads the repo's `private` flag and throws before `setJson(CONFIG_KEY, …)`, so a refused repo saves nothing and leaves nothing to reconnect from. A saved connection resumes with a bare `new GitHubAdapter()` and never calls `connect()`, so `write()` and `writeDocument()` — every write funnels through those two — re-read the flag once per adapter instance before the first PUT: one GET, shared by concurrent first writes, retried on the next write if it failed. The check fails closed; reads stay ungated. Accepted residual, stated: a repo flipped to public mid-session keeps writing until the next page load, which re-checks.
- AC3: On-device guest data migrates up on first connect (merge, not overwrite).
- AC6 (2026-09-09): Cloud-storage failure diagnostics retain operation/provider context but never document titles, refs, provider bodies, arbitrary exception text or request breadcrumbs. Local console diagnostics follow the same boundary. **Widened 2026-09-10 to the server's own console:** a Klaviyo failure logged the provider's response body to the Fly log, which is unscrubbed and where a Klaviyo error echoes the address that was submitted — both the subscribe and the suppress path now log the status and a fixed message only, and the body reaches ops through Sentry, where `scrubEventText` runs over it. **Widened again 2026-09-10 (night):** the Discord bot attached the author's Discord id to a dedup diagnostic and the author's tag to a persist failure, so an account name reached Sentry beside the message length. Both `extra` fields are gone; the conversation id, the age and the length stay, and they are enough to read the event. Tests: `app/lib/klaviyo.server.test.ts` for the Klaviyo logging; no test for the Discord change (the Discord module has no test file — the two fields were removed and verified by reading).
- AC7 (2026-09-10, from a ChatGPT audit of the server `beforeSend`): a health value written into free text never leaves the app in an error report. The audit fed the hook "My LDL is 3.2 mmol/L and I have diabetes": the LDL FIELD was redacted by the key scrub, but the sentence itself survived in the exception value, in an `extra.message` string and in console breadcrumb arguments. A text scrub now runs over every free-text field of an event on BOTH sides — server `instrument.server.mjs` and browser `sentry.ts`, one shared implementation (`scrubEventText`): `exception.values[].value`, `message`, `logentry`, every string under `extra`, `contexts` and `tags`, breadcrumb messages and data, and `request`. Rules, layered on the existing key scrub: a number with a unit → `[value]`; a number within 20 characters of a metric or lab name → `[value]`; an email address → `[email]`. Error class names, stack frames and filenames stay intact — they are the diagnostic. Server-side the console breadcrumb integration is off (console arguments are raw application text) and any `extra` string over 200 characters is dropped, key and all. Honest limits, stated not hidden: condition and drug words in prose are NOT scrubbed ("I have diabetes" survives) — no word list reads a sentence reliably, and a value-free condition word was judged the lesser risk against unreadable diagnostics; and a bare number with neither unit nor nearby metric name is left alone; fullwidth digits and date-shaped numbers pass through; and the 20-character window is blunt at both ends — it misses a metric name further away and can clip a neighbouring one (the `1` in "HbA1c was 42 mmol/mol; weight 96.4kg" is redacted because `weight` sits inside its window), which redacts more, never less, and is cosmetic. The unit and metric vocabularies are literals in two files (the pre-bundle `.mjs` cannot import the clinical engine), kept honest by `instrument-scrub-parity.test.ts`, which compares both implementations AND fails when `UNIT_DEFS` or `METRIC_LABELS` gains an entry the lists miss. **Amended 2026-09-10 (afternoon):** the key scrub redacts a family of credential keys, not one name at a time, so a new secret-shaped field is caught the day it appears; the metric and unit vocabularies are DERIVED from the clinical catalogue rather than retyped, so a new metric cannot be scrubbed in one implementation and missed in the other; and the parity test covers the whole pipeline, browser and server, not the vocabulary lists alone. Tests: `packages/health-core/src/instrument-scrub-parity.test.ts`, `packages/health-core/src/sentry-scrub.test.ts`, `widget-src/src/lib/sentry-pipeline-parity.test.ts` **Amended 2026-09-10 (late):** a breadcrumb's `data` is now an allow-list — `method`, the URL's origin, `status_code` — instead of a scrub run over whatever the SDK attached, so a field nobody anticipated cannot ride out inside a fetch breadcrumb: a Dropbox request whose `data` carried an `input` object or a `Dropbox-API-Arg` header keeps only the three. Tests: `packages/health-core/src/instrument-scrub-parity.test.ts`, `widget-src/src/lib/sentry-pipeline-parity.test.ts` **Amended 2026-09-10 (sixth pass):** the key list gains the families a lab report and a patient profile are actually spelled in — date of birth (`dob`, `dateOfBirth`, `date_of_birth`, `birthDate`), `gender` beside `sex`, `patientName`, and the patient identifiers `nhi` and `mrn` — plus the generic carriers a row or an extraction hangs its content on: `value`, `values`, `result`, `results`, `title`, `note`, `notes`, `summary`. No live `extra`, `tags` or `contexts` site uses any of those names for a diagnostic we read (checked across `app/` and `widget-src/`), so nothing legible is lost. - AC5 (catalogue + units): `metricName` is stored as the `lab-catalog.ts` key whenever the test is catalogued (rule 10), and folded to lower case when it is not, so two spellings of one test share one slot. That resolution covers the spaced and Title-cased forms of a snake_case key — "Vitamin D" and "vitamin d" both file under `vitamin_d` — which is what an agent or a person actually types; the single `labSlotKey()` in `lab-catalog.ts` is the one place that key is computed, at write, merge and read time alike. `value` on a measurement is SI canonical (rule 8): the OPS resolve `--unit` through `units.ts`'s `resolveUnitSystem` — the same match the chatbot's proposed edits use, so the two writers cannot accept different spellings of one unit — and refuse anything else, so the CLI cannot mis-scale a value the MCP would scale correctly. A core metric written as a lab test is refused under any spelling — key or display label — because a core metric in `labValues` is invisible to the suggestion engine.
- AC6 (clocks + dates): every op moves `meta.updatedAt` to the write clock and touches no other `meta` field (rule 6), so the load clamp never rewinds the row just written — and it moves FORWARD only, as `mergeFiles` does, so a writer whose clock lags the file cannot rewind every other row's `createdAt` and hand the slot tie-breaks to a UUID comparison. `recordedAt` is refused if it is a day NO ONE has reached yet — the check is the latest calendar day anywhere on Earth (UTC+14), not the writing machine's own day, because an Auckland user's real today is tomorrow to a server in UTC and refusing it would be the server calling the user wrong. It is also refused if it is not a day that exists (`2026-02-30` rolls forward in `Date`, so it is caught by round-trip), and is STORED as the calendar day — never the caller's string, so what is echoed back and what lands on disk are the same thing.
- AC7 (no delete, v1 scope): there is no delete operation, and no medication, supplement or screening op — v1 writes clinical values only. Deletion stays what the app makes it (a document tombstone, or an `eraseEpoch` bump for everything), and neither is reachable from the CLI. The current-state rows are last-write-wins, so a second writer editing them needs the lamport discipline this v1 deliberately does not take on.
- AC8 (safe write): the CLI backs the record up beside itself (`health-roadmap.json.bak-<ISO>`, the last 3 kept and older ones pruned), then writes atomically — temp file, then rename, keeping the record's own permissions rather than widening them to the umask default. It refuses to write anything that is not a record (valid JSON that is an array, a string or an object without `schemaVersion` would otherwise be replaced by a blank record), refuses a `.bak` sibling as a target, follows a symlink to the real file instead of replacing the link, and refuses to write at all if the file changed between being read and being replaced. It writes the record and its `.bak` siblings and nothing else; no network, no model, no telemetry. **Strengthened 2026-09-01 by US-32, unified 2026-09-02:** that write boundary is now `packages/health-core/src/file-adapter.ts` — a `StorageAdapter` over one local path — and the CLI writes through `SyncManager` over it, exactly as the hosted server writes through `SyncManager` over Dropbox. So there is ONE write path across all three shells, and the storage backend is chosen purely by which adapter `SyncManager` is handed. Two consequences: the changed-file guard is now a `ConflictError` that `SyncManager` answers by re-reading and re-MERGING (a second writer costs a retry rather than a refusal, and cannot cause a lost update), and the stale-bytes check is a content hash rather than mtime+size, so an equal-length edit inside the same millisecond is still caught. **Made true 2026-09-02:** that check and the replace it guards are held under a `.lock` sibling (`O_EXCL`, 25 ms backoff, 5 s wait), because a backup, a prune and a temp write sit between them — four concurrent `edit-record` PROCESSES used to keep one row and print "Wrote" four times. `SyncManager`'s verify-after-write now also asserts every row id it just wrote is present on the re-read, so a writer that loses anyway reports it instead of confirming it. It also refuses a file that carries `schemaVersion` but holds junk where its rows belong (`measurements`, `labValues`, `medications`, `supplements` present but not a list) — `migrateFile` would have blanked such a file and the CLI would have reported success — and refuses a record written by a newer app at the READ, so it is out of reach in both directions. **Moved 2026-09-02:** that shape gate is `ROADMAP_DOC.migrate` (`roadmap-doc.ts`), not the adapter, so EVERY adapter inherits it — Dropbox, Drive, GitHub, the local file — on `SyncManager.load()` and on the re-read that precedes every save. A null or absent row array still normalises to `[]`: it holds no rows, so nothing is lost. **Lock hardening (2026-09-09):** locks never expire solely by age. A suspended owner keeps its lock; publication/release verify its filesystem identity. Abandoned locks fail closed and require exclusive offline recovery with all writers terminated. This covers cooperative updated writers on one local filesystem, not legacy stealers or external lock replacement. **Hardened again 2026-09-10 (late), five things the outside security read found in the same file.** A backup made before the record's erase epoch is removed on the next write: an erase used to leave every pre-erase `.bak` sitting beside the erased file, which put "delete all my data" one rename away from undone; backups at or above the epoch are kept, because those are the user's ordinary undo, and a sibling the adapter cannot read as a record is left alone rather than guessed at. The temp file is opened exclusively under an unpredictable name and fsynced before the rename, so nobody can pre-plant it and a crash cannot leave a half-written record; a symlink planted at the temp or the backup path fails the write instead of being followed. Backup names carry no colon, so a Windows record can be saved at all. A record the tools create is `0600`, and one left readable by everyone is narrowed rather than copied forward at that mode, the same rule US-33 AC5 applies to the HTML plan. And `health-roadmap.json.*` is now ignored in both `.gitignore` and `.dockerignore`, so a `.bak`, a `.lock` or a crashed `.tmp` cannot be committed or built into an image, the way US-09 AC9 already covers the record itself. - AC9 (round-trip): bytes the CLI wrote load identically in the widget's own data layer — a real `RoadmapStore` over the written file reads the new value as current — and `migrateFile` plus a self-merge leave the file unchanged, because the edit is already canonical. - AC10 (errors): the same discipline as US-30 — exit 1 with one plain line plus a hint, never a stack; an occupied slot prints the row that holds it and how to correct it instead; a correction echoes old → new. Text out of the record reaches the terminal as data: control characters are stripped and newlines collapsed, so a lab name cannot forge a line of output that reads as the tool's own.
- AC11 (today, per writer): "today" — the day a plan or a reminder measures against, and the default `recordedAt` where there is one — is the WRITER's own local calendar day. That works where the writer runs on the user's machine: the widget slots by the browser's local day and the CLI's `--date` defaults to the terminal's. **It cannot work on the hosted server, and pretending otherwise was the bug (fixed 2026-09-03):** a Fly box in UTC has no way to know an Auckland user's day, so a defaulted date was the UTC day and every user east of UTC was logged a day behind for part of their day. As a user whose record is one JSON file, I can connect an AI assistant to it and say "add my new blood panel" or "what does my plan say about my LDL" — and it reads and writes my file by the app's own rules, because the tools are published by this repo rather than improvised by the model. **Phase 0, shipped: a local stdio MCP server over a file path** (Claude Desktop, Claude Code). **Phase 1, LIVE at `https://mcp.drstanfield.com/mcp`: the same tools behind a hosted connector**, so a web ChatGPT or Claude user clicks connect and reaches their Dropbox folder — the clunky step [getting-started.md](guides/getting-started.md) admits. Both items in [deploy-runbook-mcp.md](deploy-runbook-mcp.md) step 4b are now closed: Google brand verification is approved (the consent screen shows the branded "Dr Brad" screen, no "unverified app" interstitial), and the live verify over Drive (step 8) passed 2026-09-02 — the hosted MCP via Claude.ai wrote a measurement to the user's Drive file, the website loaded it, and a website correction was read back by Claude.
- AC1 (one tool surface): the tools — `read_record`, `get_plan`, `add_measurement`, `add_lab_values`, `correct_value`, `update_profile`, `report_feedback` (seven at first; eight with `import_documents`, US-35; nine once `file_results` lands, US-36) — defined once in `packages/health-core/src/mcp-tools.ts` as pure functions over `(file, request)` with a Zod schema each, so the local server and the hosted one offer the same thing — the hosted surface exposes every tool in that list, with no hosted-only subset to drift. Reads and writes are separate tools by construction: no catch-all with a `method` argument.
- AC2 (the file is untrusted input): every call reads the record fresh through `migrateFile` — the same hardened boundary US-29/US-30 use — so the assistant never works from a cached copy and a file another device changed mid-session is seen, not assumed.
- AC3 (the capability secret never leaves): `reminderOptIn.token` is stripped from every read (agent-access rule 12). It manages the user's reminder schedule on Brad's server; an assistant has no use for it and a copy in a chat transcript is a copy that can cancel someone's reminders.
- AC4 (writes keep the rules): every write goes through `record-edits.ts` (US-31 AC1–AC6) — one active row per (metric, day), SI canonical measurements, the lab's own unit for lab values, catalogue keys, `meta.updatedAt` forward only. An add into an occupied slot is REJECTED and the refusal names the row holding the day and sends the agent to `correct_value`. `add_lab_values` is the lab-panel case: a batch, capped at 50 rows per call, all-or-nothing, so a half-imported panel never has to be told apart from a whole one.
- AC5 (corrections are their own pathway): `correct_value` appends a row with `correctsId` and the ORIGINAL date and flips the old row to `entered-in-error` — never folded into an add. `expectedValue` — the agent stating what it believes it is replacing — is OPTIONAL on the local surface, where the user is watching their own file and the CLI has never asked for it, and REQUIRED on the hosted one, where it is what stops an agent writing from a stale or invented read. v1 writes clinical values only: no delete, and no medication, supplement, screening or document write, because those are last-write-wins current state a second writer can overwrite. **Reversed for the profile on 2026-09-02 (US-34), for four fields and no others:** `update_profile` changes sex, birth year, birth month and height — what the plan is computed from — as a read-modify-write of the whole last-write-wins profile object, so every field it does not name survives, `unitSystem` and any field a newer app added included. It refuses what the app itself would refuse (`healthInputSchema`'s own ranges, and the same male/female enum), refuses a call naming no field, and refuses a wrong `expected` without disclosing what the record holds. On the hosted surface `expected` is REQUIRED for every field being changed (`null` claims the field is unset) and the write costs a correction's weight — 5 — because a profile field has no superseded copy to read back. Display preferences (`unitSystem`, `unitOverrides`) stay out of reach: they are how the app draws the screen, not what the record says about the person.
- AC6 (the bytes): every surface writes through `SyncManager` over a `StorageAdapter` — read, migrate, merge, conditional write on `expectedVersion`, verify. The stdio server and the CLI hand it `FileAdapter` (`packages/health-core/src/file-adapter.ts`, one local path: backup, atomic replace, symlink target, content-hash precondition); the hosted server hands it the Dropbox adapter. What counts as a record at all is `ROADMAP_DOC` (`roadmap-doc.ts`), above the adapters, so every backend refuses the same bytes. The three shells are literally the same few lines — `runToolOverSync` in `mcp-tools.ts` — so they cannot lose the file in different ways, and the database of record is a constructor argument. A storage failure is worded once, by `describeStorageFailure`, and reaches the agent as a refusal on its own request rather than a protocol error it cannot match.
- AC7 (zero network, phase 0): the local server speaks JSON-RPC 2.0 over stdio and opens no socket — the imports of the server, the tool layer, the plan engine and the local `FileAdapter` are pinned by a guard to health-core sources, their siblings, zod and node builtins. The thresholds, reasons and citations are unchanged — `get_plan` re-exposes existing derivations, so the three-file rule is not triggered.
- AC9 (the assistant files a bug report): `report_feedback` turns a complaint into a GitHub issue on this repo. **On the hosted server the assistant files it itself, with no user action** — a POST to the GitHub issues API under a server-held fine-grained token (`GITHUB_ISSUES_TOKEN`), titled `[connector] <title>`, labelled `from-connector` plus `bug` or `enhancement`, and answering `{ filed: true, url, number }`. The report's text is fenced in the issue body, so a model's markdown renders as written and an `@name` pings nobody; the footer carries the kind, the server version, the cloud provider and one line saying the user's assistant filed it and no health values are included. Nothing identifies the user: no name, no email, no IP, no connection key. The issue is PUBLIC, and the tool description says so. **A server with no token — always the local stdio server, which holds no secret — keeps the old behaviour:** a prefilled `issues/new?labels=from-connector,<bug|feature>` URL, `{ filed: false }`, which the user opens, reads and submits themselves; an over-long one is refused rather than silently truncated by GitHub. Keeping health values out is the tool description's job, and the mechanical backstop is the LAST line of defence, since nobody reviews a hosted report before it is public. Widened 2026-09-10, after a ChatGPT audit of the public repo found "My LDL is 3.2" and "I have HIV. Contact synthetic@example.invalid" both passing: a title or detail is refused as `health-value` when it carries a number wearing a known unit ("2.1 mmol/L", "81 kg", "140 mmHg", read off `units.ts`) OR a bare number within three words of a name this record knows, read off `METRIC_LABELS` and `LAB_CATALOG` so a metric added tomorrow joins the guard for free (single letters go — "k" is a thousand before it is potassium — as do the generic English words a test name is built from, "total", "count", "rate", and six short names that are English or markup first: na, gt, am, oh, sat, hs. Short names that are not stay, so "BP 140/90" and "free T4 15" are refused; "Lp(a)" is folded to one word on both sides so "my Lp(a) is 90" is too; and "the chart shows the wrong unit for HbA1c", a metric name with no number, still files). A second, new reason, `contact`, refuses an email address, a phone-shaped run of 7–15 digits (calendar days and timestamps masked out first) and a URL carrying a query string, which may carry a token. There is deliberately NO diagnosis word list: that cannot be done mechanically, and the description carries what the guard cannot — "This files a public GitHub issue. Do not include diagnoses, names, contact details, or values; describe the behaviour, not the person." The guard over-refuses rather than under: a refused report is rephrased in a turn, a filed one is public forever. Because it now writes to an external system the tool is no longer read-only (`readOnlyHint: false`, `openWorldHint: true`) and costs a correction's five against the connection's hourly write allowance — charged before the call, so a refusal spends too, exactly as `correct_value` does. Two more bounds live on the server: at most 20 issues an hour across the whole machine (over that, "Feedback is paused for an hour. Nothing was filed."), and the same title filed twice in 24 hours returns the first issue's URL instead of a second issue. A third bound is per connection: three reports in a rolling 24 hours (over that, "You have filed three reports today. Nothing was filed." — and, like every refusal here, it still spends the write allowance), and the GitHub call itself is abandoned after 8 seconds, which lands in the same "GitHub did not answer" refusal. A GitHub failure is worded as ours — "GitHub did not answer. Nothing was filed. Try again later." — never a protocol error, and the log line carries the status and not a word of the report. It still opens no cloud connection: `RECORD_FREE_TOOLS` runs it before any record is loaded, which is the point — the likeliest moment to report a bug is the moment the record would not open.

- AC10 (nothing per user is stored, anywhere): no table, no row, no session. The Dropbox refresh token is sealed into the bearer token the AI vendor holds — AES-256-GCM under a per-blob-type HKDF key, a 12-byte nonce, AAD binding the blob to one client and one audience, and fixed-bucket padding so the blob's length says nothing about the credential inside. We hold the key and no blob; the vendor holds a blob and no key. What DOES exist and is counted, not hidden: a per-machine authorization-code set, per-IP rate maps, a bounded client-metadata cache, and Fly's own proxy metadata. None is health data and none is a per-user row. What sealing does NOT protect: the blob the vendor holds is a live bearer against `/mcp` until it expires — no key needed. Split custody protects the DROPBOX credential inside it, not access to our endpoint.
- AC11 (revocation is honest about what it cannot do): the access blob expires in 1 hour and the refresh blob in 90 days. Rotating `MCP_SEAL_KEYS` with no overlap kills every connection at once, and that is our ONLY server-side revocation — a per-user denylist needs state we refuse to keep. The real kill switch is the user's own: `dropbox.com/account/connected_apps`. Because Dropbox's app-folder scoping is tied to the app identity, unlinking there ALSO disconnects this website from the folder; that is disclosed on the consent screen, not hidden.
- AC12 (the four mandatory corrections mitigations): `expectedValue` is REQUIRED on the hosted surface (optional on the CLI and the local server); a correction on a row older than 90 days is refused; `add_lab_values` is capped at 50 rows per call; and writes are bounded at **60 weighted writes per connection per hour, per machine**, where a correction costs five adds. The allowance is keyed on the connection (the hash of the sealed provider refresh token), so minting extra access tokens buys no extra writes, and it comes back with the hour, so an honest user is never locked out. **Corrected 2026-09-02 by review:** the approved design put a lifetime pool inside the credential, spent by refreshing. It locked honest users out — fifty ordinary refreshes with zero writes exhausted it — and bounded nobody, because replaying one refresh blob mints a fresh access blob every time. It is deleted. The honest bound is a RATE, per machine, and the refusal now says so.
- AC13 (the accepted residual, stated rather than softened): an injected agent reads first, so it knows every row id and value, and with `correct_value` it can silently falsify current values — each original flipping to `entered-in-error`, irreversibly — and `get_plan` will then generate a coherent, wrong protocol from the falsified record. Append-only prevents data LOSS, not data CORRUPTION. Brad accepted this knowingly on 2026-09-01, choosing protocol completeness, bounded by AC11. Vendor confirmation prompts are NOT counted as a boundary: the MCP spec calls annotations untrusted hints and "always allow" is one click.
- AC14 (`state` comes back byte-identical): `state` is the client's own opaque value, so it is returned **byte-identical up to 1024 characters; longer is refused with `invalid_request`, never truncated**. We used to `.slice(0, 512)` it. OpenAI's platform relay sends 521 characters, got a 512-character stump echoed back on the callback, and rejected every ChatGPT connection with "Invalid OAuth state" — a truncated `state` is worse than a missing one, because it looks valid until the far end compares it. The cap is set by the `__Host-mcp-state` cookie rather than by taste: the sealed state is padded to a fixed bucket, and 1024 keeps the whole Set-Cookie line near 3.1 KB, inside the 4096 bytes browsers allow, where the next bucket up would put it at ~5.8 KB and the browser would drop the cookie in silence. Twice what OpenAI sends, and more than Claude does.
- AC14 (the front door): OAuth 2.1 with PKCE S256 only, our own consent screen — and the consent screen is ENFORCED, not merely displayed: pressing Connect mints a 32-byte nonce, seals the state naming it into a first-party `__Host-mcp-state` cookie (Secure, HttpOnly, SameSite=Lax, 10 minutes), and hands Dropbox the nonce alone. The callback requires the cookie, compares the echoed value to the sealed nonce timing-safely, and clears it; without the cookie it is a 400 page and no redirect. (Before this, found by review 2026-09-02, a state blob from an unauthenticated `GET /mcp/authorize` could be replayed into a forged callback and mint an authorization code with no consent at all.) Then RFC 8707 audience validation, RFC 9207 `iss`, and `invalid_grant` on every dead grant. The refresh lifetime is 90 days ABSOLUTE from consent — it used to slide forward on every refresh, so it expired for nobody. Clients arrive by client-id metadata document or by a self-contained DCR client id carrying its own HMAC — no registry, no row. The metadata fetch is an SSRF surface and is treated as one: https only, every resolved address public, zero redirects, a 5-second timeout, a 64 KB cap, `application/json` required, no credentials, and per-IP rate limiting BEFORE the fetch. Unauthenticated calls get 401 with `WWW-Authenticate: Bearer resource_metadata="…"`; the only unauthenticated documents are the two `.well-known` files.
- AC15 (it is not a browser endpoint): no `Access-Control-Allow-Origin` is ever emitted, `ALLOWED_ORIGINS` is untouched, a present-but-foreign `Origin` gets 403, and localhost is on no list. GET and DELETE at the endpoint are 405, no `Mcp-Session-Id` is ever minted, and an incoming one — like `Last-Event-ID` — is ignored. No route logs a request URL, because `code`, `state` and `code_verifier` travel in query strings.
- AC16 (consistency is the widget's, not a second implementation): every write goes through the same `SyncManager` read → migrate → merge → conditional-write → verify loop the widget runs, now living in health-core so both surfaces share it. The Dropbox conditional write sends `strict_conflict`, which is what stops a stale write re-creating a record the user erased. A record whose `schemaVersion` is newer than this server understands is out of reach in BOTH directions: the record is migrated before any tool sees it, so reads refuse too, and the refusal says so rather than claiming the record is readable. Known residual, unchanged from US-11: a RAW deletion in the Dropbox UI carries no `eraseEpoch` signal, so a stale writer legitimately re-creates the content.
- AC17 (bounded, and honest when it refuses): request bodies are capped — 64 KB at the OAuth doors, 1 MB at `/mcp`, 413 over. `/token` is rate-limited per IP and `tools/call` per connection, both generously: a whole vendor's users arrive from one egress range, so a tight per-IP limit would lock out honest traffic rather than an attacker. The IP those limiters key on is `Fly-Client-IP`, which Fly's proxy writes, not `X-Forwarded-For`, which a client can forge. A malformed `MCP_SEAL_KEYS` or `MCP_CLIENT_HMAC_KEY` disables the feature (404) with one log line naming the variable and never its value, rather than turning every route into a 500. A record written by a NEWER app version refuses reads as well as writes — it is migrated before any tool sees it — and the refusal says that rather than claiming the record is readable. A failure that is ours, not the record's and not the provider's, reaches the client as JSON-RPC -32603 on the request's own id, never worded as a refusal the user could act on, on the hosted and the local server alike.
- Known spec deviation, documented not papered over: OAuth 2.1 requires single-use authorization codes and statelessness cannot enforce that across Fly machines. The per-machine set is best-effort; the window is 60 seconds, and redemption still needs the PKCE `code_verifier`, which never leaves the client.
- AC18 (phase 2 — the user picks the cloud, and the token remembers): the consent screen offers one button per configured provider, each carrying its own sealed state, so the choice is made before the browser leaves us and cannot be edited afterwards. `provider` lives INSIDE the sealed state, code, access and refresh payloads, under the same AES-256-GCM tag as the credential — so a Dropbox connection cannot be steered into opening a Drive folder, or the reverse, and an edited token dies rather than changing clouds. `/mcp` builds its adapter from the bearer token alone; no tool argument ever names a provider, a file or a user.
- AC19 (phase 2 — Drive without a conditional write): Drive v3 has no `etag`, so `DriveAdapter` (`packages/health-core/src/drive-rest.ts`) substitutes the four steps of [mcp-architecture.md](mcp-architecture.md) §7 — read with `fields=version`, re-fetch the version immediately before uploading and refuse if it moved, verify every written row id on the re-read, and retry, bounded. Step 3 is `SyncManager`'s existing verify-after-write, not a second implementation, and a failed verify is now a RETRYABLE lost update rather than a dead end; when the retries run out the message says some of the change may have landed, which is the truth. **Stated residual:** the pre-upload check narrows the window, it does not close one. **Probed 2026-09-10 against a scratch account, so this is not re-litigated:** Drive v3 returns no ETag anywhere (`fields=etag` is `400 Invalid field selection`, no `ETag` header on the metadata or media GET) and answers `200` to a media PATCH and a metadata PATCH carrying `If-Match: garbage-etag`. ### US-34 · The record on screen keeps up — **added 2026-09-02**

- AC1 (when it re-reads): `RoadmapStore.refreshFromRemote()` re-reads the record through the ordinary `SyncManager.load()` and merges what comes back with `mergeFiles` — no second read path, no second source of truth. It runs when the provider says the file moved, when the tab becomes visible, and when the window takes focus. **The provider's own change signal replaced the 60-second timer on 2026-09-02**: `StorageAdapter.watch(fileName, onChange, signal)` is optional, and an adapter that has one never runs the poll. Dropbox holds a `files/list_folder/longpoll` open against the app folder root (the `notify` host, which takes no access token — the cursor is the credential; `files/list_folder/continue` advances it before the store is told), so a write from another device or an assistant arrives in about a second, and a quiet tab costs two requests a minute. Both back off on failure, doubling to a 60-second ceiling, and re-establish their cursor from scratch. A backend with no watch (localStorage has no second writer; GitHub and WebDAV have no cheap one) keeps the 60-second poll. A hidden tab watches and polls nothing — it has no screen to keep up to date, and a phone left on a background tab would spend the day holding a connection open; the watch is aborted when the tab is hidden and taken up again on return. A leading-edge 5-second throttle stops `focus` and `visibilitychange` — which fire together on a tab switch — making two round trips out of one return, and a push it swallows is held and re-read when the window is out: a watch fires once per change and then goes quiet, so dropping one would lose it.
- AC2 (a pending local edit always wins): it re-reads NOTHING while a save is in flight or the persist debounce is still pending, and it throws away a merge whose base moved while the read was in the air — the check after the read is that the working copy is the same OBJECT it merged from, because a save can start and finish inside the read window and leave `writePending` false again by the time the answer lands. The working copy is then AHEAD of the cloud, and merging a read taken before the edit existed would fight the write that is about to go up. The listener is registered once, in `initRoadmapStore`, which is where both surfaces start their data layer. **It does nothing while the demographics form is dirty** (`hasUnsavedProfileEdits`, over `PREFILL_FIELDS`): re-running the load path replaces the form's inputs, and a change landing on a half-entered height would take those keystrokes with it. ### US-35 · My assistant imports my lab files — **built 2026-09-04, verified live 2026-09-05 (hosted API on the scratch Dropbox: commit, replay, conflicts, 90-day rule, documents; ChatGPT drag + folder routes on Brad's record, extract only; Drive refusal)**
As someone who keeps a ZIP of lab PDFs and clinic letters (Brad's own is `health.zip`), I can drop the file into my connected Dropbox folder and say "import it", or drag it into ChatGPT and say the same, and my assistant reads every document, shows me what it found against what my record already holds, and files only what I confirm — instead of retyping thirty numbers or leaving the chat for the website. The website's upload already does extraction, review and a bulk save (lab-upload.md); this is the same pipeline reached through the connector, with the review step done in words. Design brief and the resolved decisions from its adversarial review: [mcp-import-design.md](mcp-import-design.md). Architecture context: [mcp-architecture.md](mcp-architecture.md) §3, §7.
- AC1 (one tool, two phases, and the first never writes): a single tool `import_documents` in `packages/health-core/src/mcp-tools.ts`, published on every surface like the other seven. Called with a source (AC2, AC4) it EXTRACTS and returns candidates plus a `receipt`; called with `commit` (AC8) it WRITES; `commit` beside a source is refused. An extract call opens the record read-only and saves nothing, ever — a test asserts the record's version is unchanged after an extract that found values. The server keeps nothing between the two phases: the candidate payload is parked in the USER's own folder (AC7).
- AC2 (the folder route, Dropbox): with no `file` argument the tool lists the ROOT of the connected app folder (`dropboxListFolder`, files only, `has_more` followed) and takes the files named in `fileNames`, or every importable file when the argument is absent. Importable is `.pdf`, `.jpg`, `.jpeg`, `.png`, `.zip` by the shared `isImportableEntryName` rule; `health-roadmap.json`, folders, dotfiles and everything else are ignored, not refused. A name in `fileNames` is matched by equality against the listing and the file is downloaded by the listing's `id`, so a name never forms a path; a name not in the listing refuses the call and names what the folder holds. Five files per call by default (`IMPORT_FILES_PER_CALL`), the rest come back in `remaining` with `next` telling the assistant to commit this receipt first, then call again with those names; a file not reached inside the budget (AC10) comes back `skipped: "time"` AND in `remaining` — on the drag route too, where `next` asks for the ZIP again after the commit (2026-09-07). A folder that holds no PDF, JPEG, PNG or ZIP refuses in words naming the folder and the four types.
- AC3 (Google Drive, honestly): the folder route on a Drive connection is refused in words, not attempted: the connector holds `drive.file`, which sees only files this app created or the user opened through Google's picker — a file the user drops into the folder is invisible to it (Google's scope definition, confirmed 2026-09-04; `GOOGLE_DRIVE_SCOPE` in `drive-rest.ts`). The refusal is per client and puts the way that works for THAT assistant first: ChatGPT → drag the file into the chat from a desktop browser, or the website's upload; Claude and everything else → the website's upload. Dragging into ChatGPT works on a Drive connection because the bytes come from ChatGPT, not the folder. Counted as `mcp_import {route: drive_refused}`. Widening the scope is not on the table: `drive.readonly` is a restricted scope with a security assessment attached, for a feature whose alternative is a drag.
- AC4 (the ChatGPT file route — **deleted 2026-09-10 on Brad's decision, 27 days early**): the tool descriptor carried `_meta["openai/fileParams"]: ["file"]` and an input field `file` whose schema declared exactly `download_url`, `file_id` (required) and `mime_type`, `file_name` (optional) — the shape OpenAI's reference required — and the server fetched `download_url` and nothing else: https only, host on an exact allow-list (`files.oaiusercontent.com`, plus anything in `CHATGPT_FILE_HOSTS`; the region-suffixed Azure blob family `^oaisdmntprn[a-z0-9]*\.blob\.core\.windows\.net$` was dropped 2026-09-10 because it was a namespace, not a list — any Azure account named `oaisdmntprn…` passed it), a refused host warned by hostname only, `redirect: "error"`, a 10-second abort, a 20 MB byte cap through `readCappedBytes`, and the type decided by magic bytes (`%PDF-`, `PK\x03\x04`, JPEG, PNG), never by the declared `mime_type` or the file name. A bare `chat_upload://…` reference — what the phone apps hand over — was a schema error whose message was the mobile sentence. All of it is now deleted: the argument, the fetch, the host list, `IMPORT_REFUSALS.mobile`/`dragFallback` and the `chatgpt_file`/`chatgpt_refused` counters. What is left is one guard line in `runImport`: a call still carrying `file` — a tool list cached before 2026-09-07 — is answered with `IMPORT_REFUSALS.refresh`, and nothing is fetched. Claude cannot pass a file to a remote tool at all; the tool description says the folder route is the Claude way.
- AC5 (one extraction pipeline, not a second): every file goes through the existing `extractOrClassify` (`app/lib/anthropic.server.ts`, `UNIFIED_SYSTEM_PROMPT`, unit resolution) — the same call the website makes — with `attempts: 1, httpAttempts: 1` (no outer retry AND no inner HTTP retry on this path) and a timeout of min(20 s, what is left of the budget), so one model call ends inside the deadline by construction — and the `{`-prefill second call, made when the first answer does not parse, shares that same deadline (`extractOrClassifyOnce` computes one `until` for the pair; it gets what is left, never a fresh window; tested with a spy on `AbortSignal.timeout`). Non-lab documents are asked for metadata only (`documentMode: 'metadata'`: title, date, a one-line `summary` ≤120 chars, `contentMarkdown` empty, 2048 tokens), since the connector files no text; the website's upload keeps the full-transcription prompt (`unifiedSystemPrompt('full')`, the same head and response format). Every other I/O in the call is ABORTED at the same deadline, not abandoned (2026-09-04): `runImport` starts one clock per call — 40 s, `ImportSurface.budgetMs` — before it reads the record, and every adapter call the call makes carries a `deadlineSignal` derived from it: the record's read and write through `SyncManager` (`load`/`save` take a signal and pass it to `read`/`write`/verify), the folder listing, each download, the stale-pending sweep, the ChatGPT file fetch, the pending-file write in `stash`, and the commit's read and delete of the pending file. `StorageAdapter`'s `read`/`write`/`readDocument`/`list`/`remove` take that signal as an optional last argument; the Dropbox and Drive REST adapters hand it to `fetch` (`fetchOrFail` joins it with the adapter's own 30 s bound via `AbortSignal.any`), so a provider that took the socket and went quiet is cut off at the deadline and its promise rejects with a `TimeoutError`; the memory and file adapters refuse to start once it is aborted. What the assistant sees: a hung listing or pending-file read is a refusal, a hung download is `skipped: "time"`, a hung pending write refuses the extract, a hung delete is swallowed and swept later, and a hung record read or write surfaces as the provider's "did not answer" refusal. An extract's downloads and model calls end 4 s before the deadline (`BUDGET_RESERVE_MS`), leaving that reserve for slotting and the stash. Nothing an import does runs past the deadline. A PDF is passed to the model whole, as a base64 `document` content block (the `'pdf'` page type in `lab-extraction.ts`'s `pagesToContentBlocks`, verified with one real Haiku call 2026-09-04: 3,369 input tokens for a one-page PDF; the website's `text|image` route schema untouched). Images go as `image` blocks; a ZIP is opened server-side with JSZip (already in the Fly image, now declared in the root manifest) under caps: 20 MB per ZIP, 20 importable entries, 5 MB per entry INFLATED — the central directory's declared size is only the cheap first refusal, the bytes are counted as they inflate and the stream is stopped past the cap. Entries are taken by position, typed by magic bytes, and nested zips are skipped by name. The junk filter (`__MACOSX/`, `.DS_Store`, dotfiles at any depth, `Thumbs.db`) lives in health-core and the widget's `zip-extract.ts` calls it.
- AC6 (what the record already holds): every extracted value is slotted against the record by the one rule the website's review table uses — `findActiveInSlot` + `slotState` in `record-edits.ts`, equality on the DISPLAYED string so float noise never manufactures a conflict: `free`, `held_equal` (already recorded; accepting it writes nothing), or `held_different` with the existing row id and value, and `replaceable` when the held row is inside the hosted 90-day correction window. Candidates are shown in the record's own unit system (`profile.unitSystem`, default SI: `displayValue`/`displayUnit` for a US user read "131 mg/dL", not "3.4 mmol/L"), stored canonical, and slot equality is judged in that system (2026-09-07). Two files offering one (metric, day) in one call are BOTH offered, the second marked `sameDayAs` the first, so a preliminary and a final report are seen, not silently dropped. A document is `already_imported` hash-first: when a live `documents[]` row carries its bytes' `contentHash` (`sha256-<hex>`, the same field the website's archive keys on — ONE dedup key for both writers), or by `sourceFileName` ONLY against a live row that has no hash (a pre-hash website row) — a lab portal that names every download `Results.pdf` must not make the second report "already imported" (2026-09-07; before, the name alone blocked it with no way past). The same bytes under two names in ONE call (a browser's `Results.pdf` + `Results (1).pdf`) file one row: the twin is `already_imported` with a hint naming the first file ("The same file as Results.pdf in this call"), so two rows never share the archive key (2026-09-07; before, both landed, the website's upload could tombstone only one and re-offered the other on every upload). It is not sent to the model again, and the entry's `hint` names the row's file and date ("the same file was filed on … as …" / "a file with this name was filed on … and that row carries no fingerprint… Rename the file to import it"). A ChatGPT drag with no `file_name` is named from its bytes (`file-<sha8>.pdf`), never a shared word that would dedup every later nameless drag. The website's `bulkSaveDocuments` treats a hash on a row WITH a `fileRef` as "already archived" and a hash on a row WITHOUT one as the connector's metadata-only import: uploading that same PDF on the website writes the blob into a new row and tombstones the metadata-only one — only once the blob write succeeds; a failed write leaves the connector row live so its hash still dedups — so the original gets archived rather than silently skipped. A value the record would refuse — out of range, a future day, a core metric under a lab name — is dropped at extract time with the reason, by a dry run of the same `appendMeasurement`/`appendLabValue` the write tools use, so the receipt never carries a value the record would not take. A lab report with no usable collection date is `failed: no_date` with the ask-the-user hint; the caller's `fileDates: {name: 'YYYY-MM-DD'}` on the next call supplies it (AC13).
- AC7 (the receipt): the extract writes its payload — candidates plus document metadata, never document text — to the user's folder as `imports/pending-<uuid>.json` through the same adapter that holds the record, and the receipt the assistant carries is `{id, exp, conn, sha256}` sealed as an `'import'` blob by the same `seal`/`unseal` every credential uses (AES-GCM under HKDF from `MCP_SEAL_KEYS`, bound to the client and resource in the authenticated header, ~550 bytes, under `MAX_RECEIPT_LENGTH`), with `conn` binding it to the connection hash, a one-hour expiry, and every configured key tried so a rotation inside the hour does not strand it. Commit verifies the receipt BEFORE anything is charged — a forged receipt costs nothing — then reads the pending file, checks its hash against the receipt, applies the selection, and deletes the file; a second commit of the same receipt finds nothing and refuses. A commit deletes the file it consumed at once, best effort: a delete that fails is one Sentry count carrying no file name, no path and no error text, and what it costs is a file that outlives its use, not a leak of anything the user did not already own. There is no discard action — an import the user declines is simply never committed, and its file is swept. The sweep is the backstop, not the cleanup: it takes `imports/pending-*.json` files older than twice a receipt's life (two hours, past which nothing can still be committed from one), never another file the user keeps in that folder. Two changes on 2026-09-10, from the adversarial review: the window was 24 h, and the sweep ran only inside `extract` — which `file_results` and every Google Drive user never call, so their abandoned pending files were never swept at all. It now runs in `stash`, the one door every route passes through, so the next import of any kind clears the last one's residue. The assistant can only SELECT candidate ids (`accept`, `replace`); it cannot edit a value or invent a document, which is why this write may land `documents[]` rows when `add_lab_values` may not (US-32 AC5). A payload the model retyped is exactly `add_lab_values`, which exists.
- AC8 (the commit): all-or-nothing. Accepted `free` candidates and `replace`d `held_different` ones land through `bulkAppendValues` — the same pure function the website's `bulkSaveMeasurements`/`bulkSaveLabValues` now call — core metrics as measurements in SI, the rest as lab values in the lab's own unit, with `source: "lab_import"`; a `replace` supersedes the held row with `correctsId` and flips it to `entered-in-error`, after the commit's own two checks — the held row still carries the id and value the receipt names (the `expectedValue` guard), and `replaceable` computed at extract against the surface's 90-day rule (enforced ONCE, here; the receipt's hash keeps it honest); a `held_different` id in `accept` but not `replace` writes nothing — silence is not consent. Each extracted file, lab report included, lands as a `documents[]` row metadata-only unless `already_imported` (`fileRef: ""`, `contentHash: "sha256-<hex>"` of the bytes, the sniffed `mimeType`, `extractedText: ""`, `metadata: {importedVia: "connector"}`), and the original stays where the user put it until the website archives it (AC6). A lab report's row is the shape the website's upload writes for the same PDF (`synthesizeLabArchiveEntries`: `pathology_report`, title "Blood test results", the report date), which the website's Documents list hides — the values are the record, the row is the file. A row records the file, not acceptance: a commit that declines every value still files it (live 2026-09-05, defect A: lab reports got no row, so a re-extract re-read and re-charged the file and the website had no row to archive the blob behind). The commit re-reads the record fresh: a slot whose active row moved since the extract (a different id or value, or a free slot now taken) refuses the WHOLE commit, naming the slot, and the assistant extracts again. Two chosen candidates for one (metric, day) — `sameDayAs` — refuse the whole commit in words ("c2 and c1 both name ldl on …; the record keeps one value per metric per day. Pick one."), never a contract error. A document needs no selection: a clinic letter yields zero candidates, so the only commit it can get is an empty one, and that commit files the letter (`already_imported` keeps it from landing twice). So the extract must not read as "nothing to do" (live 2026-09-05 it did — "0 value(s) are new" — and ChatGPT never offered to file the letter): the extract result carries `documents` (source name, title bounded per AC9, type, date), its `next` says how many documents can be filed and that a commit with empty `accept` and `replace` files them, and the tool description says the same; titles stay out of `next`, the field the assistant follows. A commit whose `accept` and `replace` are both empty AND whose payload holds no unfiled document writes nothing, changes no version, and says so. For live testing against a real record: the first empty commit of a lab report files one metadata-only row and nothing else; the same file extracted again is `already_imported` and carries no receipt. Not atomic across devices: a second device writing the same slot at the same moment leaves two actives until the next merge demotes the newer one, as with every write; the commit's text says so.
- AC9 (nothing kept, and who sees what): bytes are held in memory for one request and dropped; no file, no value and no extracted text is written anywhere on our side; the tool result and the pending payload carry numbers, units, dates, file names, a classification and `title`/`summary`/`question` bounded to 120 printable characters and labelled as text from the document — never `contentMarkdown`, `extractedText` or the extractor's free-form `metadata`; `next`, the field the assistant follows, carries counts and ids only, never any of the three. `UNIFIED_SYSTEM_PROMPT` tells the model the document is data, not instructions; a document whose only content is an instruction block reaches the assistant as a bounded title and no candidates. The `mcp_tool_call` counter stays `{tool, client, outcome}`; Sentry gets a fixed message ("import_documents: extraction failed"), the error class and the file kind only — never the thrown error itself, whose parse message quotes the model's output (tested with a fake Sentry, 2026-09-07); no log line carries a file name or a value (tested). What DOES change, and is disclosed rather than hidden: on this route the file is sent to Anthropic's API under OUR key for extraction — the tool's own description says it at the step it happens ("each file's contents go to Anthropic for extraction at this step, kept by neither of us", 2026-09-10), and the consent screen, the privacy addendum, the ChatGPT listing's Compliance section, both connector guides, agent-access.md, lab-upload.md, the architecture map and the READMEs say so, and say that the website's upload instead keeps the PDF in the browser.
- AC10 (bounds): an extract spends `1 + 1 per file` of the connection's 60 weighted writes an hour — the `1` is the tool's declared `cost: 'add'` charged by the loop's `beforeCall` like every write, the per-file charge goes through the same `chargeWrites` before each model call (so a refused file still costs, and there is ONE refusal wording); a commit spends `1 + 5 per replace` (charged after the receipt verifies AND every id is checked against the payload, so invented ids cost nothing); 30 files per connection per day (`IMPORT_FILES_PER_DAY` = `IMPORT_LIMITS.filesPerDay`, the `importFiles` counter beside the write allowance in `mcp-grants.server.ts`, keyed on the connection hash) — a file whose model call timed out is refunded on both file counters, since it was never read (2026-09-07); the website's per-machine daily file cap (`AI_DAILY_FILE_CAP`) is one `createQuotaCounter` both callers spend from (`machineFiles` in `rate-limiter.ts`). All three counters are per machine, so the real ceiling is × machines × 2 Fly apps. Files are extracted three at a time under a whole-call budget of 40 s (`MCP_IMPORT_BUDGET_MS`; ChatGPT cuts a tool call at 60 s), and what is not reached is `skipped: "time"` or `remaining`, never half-answered. `unrecognized` is capped at 50 lines a call (`MAX_UNRECOGNIZED_LINES`), 120 characters each.
- AC11 (the local server): the stdio server holds no model key and opens no socket (US-32 AC7), so `import_documents` there refuses in one sentence pointing at the website or the hosted connector. It stays in the list: one tool list on every surface, no hosted-only subset to drift. A local-path variant was not built: the local server has no model to read a file with.
