User Stories — Health Roadmap

The user-perspective spec for every journey in the tool. Written 2026-08-07, grounded in the first usage audit (usage-audit-2026-08.md); the architecture reference is architecture-v2.html. Each story carries acceptance criteria (AC), the usage evidence we have, and the test status against the current suites.

The product constitution (Brad, 2026-08-14 — read every story against this)

What this is: a preventative-care protocol generator plus a recall system. One five-minute check-up tells a user what to actually do — bloods, screenings, medications, supplements, weight, sleep, exercise — and the reminder calendar makes sure it keeps happening over the years. The website is the onboarding funnel and the calculator; email is the product surface the user lives in. For preventative care an annual touch is the correct cadence, not a retention failure — never chase app-engagement metrics here.

The avatar: 45–55, health-curious but unsystematic, low tech-literacy (they arrive from a longevity YouTube channel, so they already care; they just don't *systematize*). They will type an email address; they will mostly not connect a cloud drive — live funnel 2026-08-14: typed captures outnumber cloud connects roughly 10:1 on any denominator we have (~4–5 captures/day and 874+ lifetime vs 3 cloud connects EVER; a precise percentage depends on which visitor count you divide by, so the RATIO is the decision-driver). Design for zero thought: the right thing happens by default, visibly, with a one-click way out. The genuinely health-indifferent mass market only becomes reachable at the mobile app (US-25); don't contort the web product for a user who can't arrive yet.

The promise (one sentence — keep it literally true): *Your health data stays on your device. We keep one thing — your reminder calendar, what's due and when — so we can nudge you.*

What may be STORED on Brad's server, visibly disclosed: reminder labels + due dates, the enrolled email, a capability token. What is never stored as health data: measurements, lab values, medications, results, reasoning. (Precision matters — the loop reads this literally: chat questions and lab-report uploads do TRANSIT the server for AI processing (US-12/US-15/US-16), in memory for extraction, and chat messages persist as conversation logs in chat_messages — operational data the user typed at a chatbot, not a parsed health record. The promise is about what we KEEP as your health data: nothing.) A label can carry an inference (a lung-CT row implies smoking history); we disclose that at enrolment rather than neuter the labels — specific recall notices are what clinics already send, and specificity is what makes the email valuable standalone (Brad, 2026-08-14, superseding the "vague emails" option).

Additive promise — applies ONLY to users who connect an AI assistant (US-32 Phase 1). The sentence above is untouched and stays literally true for everyone who never connects one. For those who do, a second sentence applies. It takes effect when Phase 1 is DEPLOYED; the code ships in this commit, the secrets and the DNS do not.

> *"If you connect an AI assistant, your record still lives only in your storage — but our server reads it, in memory, to answer your assistant, and your assistant holds a sealed credential only we can open. We keep no copy. You cancel it in your Dropbox or Google settings; that also disconnects this website from your folder, and you can reconnect here in one click."*

Durability (why localStorage loss is a bounded cost, not a crisis): the artifacts survive — the PDF, every reminder email (each carries the full schedule per US-23 AC3 — for a typed user that's the newest copy we were given at capture, not a live sync), and calendar entries (US-24). Re-entry is cheap by design: the check-up takes five minutes, and re-entering IS re-assessing. Cloud sync (US-09) is the durability upgrade for the motivated, not the front door. The real fix is the mobile app (US-25). We never "fix" durability by holding health data server-side.

Email architecture (decided 2026-08-11, reaffirmed 2026-08-14): Resend sends everything programmatic — reminders, the plan-ready email, the feedback path. Klaviyo holds only the marketing list. Never merge them: Klaviyo suppression is list-wide, so a supplement-promo unsubscribe would silently kill "your colonoscopy is due" with no error anywhere. Two consents, two systems, two suppression lists.

Architectural destination: the mobile app (US-25) — on-device notifications (reminders with no server at all), HealthKit ingestion (data entry with no typing), durable storage (no wipe anxiety). Check near-term decisions against one question: *does this move toward or away from the phone?*

Maintenance contract: when a feature's behavior changes, update its story here in the same commit, then regenerate the browser companion: npx tsx scripts/build-user-stories-html.ts → docs/user-stories.html (linked from architecture-v2.html; never edit the html by hand). Epic A — Entering health data

US-01 · Progressive first fill (guest)

As a first-time visitor, I can start getting value by entering just sex + height, and the form progressively reveals more fields so I'm never confronted with a wall of inputs.

  • AC1: Stage 1 shows only Units/Sex/Height; filling Sex+Height reveals Stage 2 (weight, waist, BP, birth month); filling Weight reveals Stage 3 (bloods, meds, screening, supplements).
  • AC2: The next-expected field pulses (.field-attention).
  • AC3: A returning visitor with saved data sees the full form immediately.
  • AC4: Everything works with zero account/cloud — data persists in localStorage.
  • Evidence: recordings show fast Stage-1 completion (8 clicks in 72s) and long engaged fills; blog→"Build my free plan"→tool is the working funnel.
  • Tests: 🟡 computeFormStage in mappings.test.ts; no test that stages actually gate rendering. Gap: none planned (low churn).

US-02 · Vitals entry incl. blood-pressure pair

As a user, I can type height, weight, waist and a paired systolic/diastolic BP quickly, and my first click/tap on any cell or its unit label focuses the input — no dead clicks.

  • AC1: Clicking anywhere in a vitals cell (including placeholder text and the mmHg/unit chip) focuses the editable input.
  • AC2: A BP entry is accepted only as a complete sys/dia pair; a half-pair doesn't save.
  • AC3: Values are validated against clinical ranges with ok/warn/bad ticks before save.
  • AC4: Numeric fields accept only numeric characters — letters and symbols are blocked at the keystroke (and stripped on paste), on every surface incl. Safari where type="number" doesn't enforce this.
  • AC5: An out-of-range value shows a visible inline error (e.g. "Max 250 mmHg") on the field itself — never a silent save-block where garbage looks accepted.
  • AC6: After typing an unambiguous, in-range systolic value, focus auto-advances to diastolic (immediately for 3-digit values 100–250; after a short pause for 2-digit values 60–99 that could still gain a digit).
  • Evidence: top friction in the audit — dead clicks on the BP ▫▫▫/? mmHg control and mmHg label in 3 of 15 recorded sessions; tooltip/units-picker dead clicks in 4.
  • Tests: 🟡 StartingInfoVitals.test.ts covers BP pair routing/readiness logic; blood-test-cell.test.ts covers validation. ❌ No test that a cell-shell click focuses the input (the actual reported friction). Action: fix + test (2026-08 backlog #1).

US-03 · Blood-test matrix entry & backfill

As a user, I can enter today's blood results in a draft column, and backfill older results under their historical date, and the matrix keeps every column aligned and scroll-synced.

  • AC1: Draft column accepts values + a date (DraftDateCell); saving appends immutable measurements under that date.
  • AC2: Typing into an existing dated column routes as backfill for that date.
  • AC3: At most one active row per (metric, day); a same-day re-entry routes through correction (US-04), never a silent overwrite or lost draft.
  • AC4: A failed save preserves the typed draft for retry.
  • Evidence: engaged sessions show field-by-field entry of masked numeric values; feedback email 2026-03-22 reported values appearing under a wrong date (root cause never found).
  • Tests: ✅ matrix-save.test.ts (task routing), blood-test-cell.test.ts (validation), merge tests (slot invariant), and date-defaulting semantics pinned in roadmap-store-data-safety.test.ts (2026-08-07).

US-04 · Correcting a saved value (FHIR)

As a user who mistyped or whose lab import was wrong, I can click the saved cell, type the right value, and the display updates — while the old value is preserved as entered-in-error with a correctsId chain (never mutated or deleted).

  • AC1: Correction happens on the surface where I see the value (matrix cell), not a separate admin page.
  • AC2: Old row flips to entered-in-error; new row has source='manual_correction', correctsId=old id; results use only active rows.
  • AC3: Corrections converge across devices (status is sticky in merge).
  • AC4: Correcting a non-latest value doesn't disturb the latest summary.
  • Evidence: correction affordance was a deliberate UX decision (memory: corrections live with the data); correction_made funnel event now measures real usage — 9 corrections in the first instrumented week (2026-W32).
  • Tests: ✅ merge.test.ts (correctsId/sticky status) + roadmap-store-data-safety.test.ts (store-level correction flow, 2026-08-07).

US-31 · My agent adds and corrects values in my record — added 2026-09-01

As a user whose record is one JSON file, I can run npx tsx tools/edit-record.ts add ~/Dropbox/…/health-roadmap.json --metric ldl --value 2.1 and have the value land in my file with the FHIR rules kept for me — one active value per metric per day, corrections that append instead of overwrite, a backup before every write — instead of hand-editing JSON and hoping. US-29 published the write rules and US-30 gave the read half; this is the code that enforces those rules, and the same code the hosted MCP server will call.

  • AC1 (altitude): the write operations are PURE FUNCTIONS in packages/health-core/src/record-edits.ts — appendMeasurement, appendLabValue, correctValue — each taking a RoadmapFile plus a request and returning a NEW file; the input is never mutated. Every rule below is enforced there, never in the CLI, so the CLI and the remote MCP server cannot drift apart.
  • AC2 (slot): appending into a (metric, calendar day) slot an active row already holds is REJECTED, not written — a typed rejection carrying that row (agent-access rule 3; mirrors RoadmapStore.addMeasurement's 409 semantics). Lab slots key on the catalogue key, so "Gamma GT" and ggt collide exactly as a lab import would.
  • AC3 (correction): correctValue appends a row with correctsId and the ORIGINAL recordedAt, then flips the corrected row to entered-in-error — a correction changes the value, never the date. It works on measurements and lab values, and rejects an id that is absent or already entered-in-error.
  • AC4 (range): a measurement outside healthInputSchema's range for that metric is rejected with the range in the message. Lab values carry no ranges, so they are accepted as the lab reported them.
  • AC5 (catalogue + units): metricName is stored as the lab-catalog.ts key whenever the test is catalogued (rule 10), and folded to lower case when it is not, so two spellings of one test share one slot. value on a measurement is SI canonical (rule 8): the OPS resolve --unit through units.ts's resolveUnitSystem — the same match the chatbot's proposed edits use, so the two writers cannot accept different spellings of one unit — and refuse anything else, so the CLI cannot mis-scale a value the MCP would scale correctly. A core metric written as a lab test is refused under any spelling — key or display label — because a core metric in labValues is invisible to the suggestion engine.
  • AC6 (clocks + dates): every op moves meta.updatedAt to the write clock and touches no other meta field (rule 6), so the load clamp never rewinds the row just written — and it moves FORWARD only, as mergeFiles does, so a writer whose clock lags the file cannot rewind every other row's createdAt and hand the slot tie-breaks to a UUID comparison. recordedAt defaults to today, is refused if it is in the future or is not a day that exists (2026-02-30 rolls forward in Date, so it is caught by round-trip), and is STORED as the calendar day — never the caller's string, so what is echoed back and what lands on disk are the same thing.
  • AC7 (no delete, v1 scope): there is no delete operation, and no medication, supplement or screening op — v1 writes clinical values only. Deletion stays what the app makes it (a document tombstone, or an eraseEpoch bump for everything), and neither is reachable from the CLI. The current-state rows are last-write-wins, so a second writer editing them needs the lamport discipline this v1 deliberately does not take on.
  • AC8 (safe write): the CLI backs the record up beside itself (health-roadmap.json.bak-<ISO>, the last 3 kept and older ones pruned), then writes atomically — temp file, then rename, keeping the record's own permissions rather than widening them to the umask default. It refuses to write anything that is not a record (valid JSON that is an array, a string or an object without schemaVersion would otherwise be replaced by a blank record), refuses a .bak sibling as a target, follows a symlink to the real file instead of replacing the link, and refuses to write at all if the file changed between being read and being replaced. It writes the record and its .bak siblings and nothing else; no network, no model, no telemetry. Strengthened 2026-09-01 by US-32: that write boundary moved to tools/record-io.ts so the CLI and the MCP server share one, and it now also refuses a file that carries schemaVersion but holds junk where its rows belong (measurements, labValues, medications, supplements present but not lists) — migrateFile would have blanked such a file and the CLI would have reported success.
  • AC9 (round-trip): bytes the CLI wrote load identically in the widget's own data layer — a real RoadmapStore over the written file reads the new value as current — and migrateFile plus a self-merge leave the file unchanged, because the edit is already canonical. Two devices that edit different slots from the same base both keep their edit through mergeFiles.
  • AC10 (errors): the same discipline as US-30 — exit 1 with one plain line plus a hint, never a stack; an occupied slot prints the row that holds it and how to correct it instead; a correction echoes old → new. Text out of the record reaches the terminal as data: control characters are stripped and newlines collapsed, so a lab name cannot forge a line of output that reads as the tool's own.
  • Usage signal (declared honestly, per the constitution): none from us, by design — the same reason as US-29 and US-30. The edit happens on the user's machine against their own file; any event we could count would break the promise. What we can watch: Brad's own use as user zero, and unprompted outside interest (GitHub issues, stars, repo traffic). Weak and lagging. The one signal that would matter arrives later — whether the hosted MCP server, which reuses these functions, gets used at all.
  • Tests: ✅ packages/health-core/src/record-edits.test.ts (45: purity, slot rejection, correction date + status flip, out-of-range message, unit conversion incl. range-checking the CONVERTED value, micro-sign and internal-space unit spellings, a per-metric sweep pinning that both of a metric's own labels still convert exactly as before, unit refused on a lab correction, core metrics refused under every spelling, catalogue resolution, monotonic meta.updatedAt, impossible and future dates, day-normalised storage, self-merge no-op, concurrent-writer convergence) + tools/edit-record.test.ts (24: add/correct happy paths, slot rejection output, backup created and pruned to 3, no partial file when the write fails, non-record JSON refused, --value coercion refused, output-line forging, permissions kept, symlink target, .bak target refused, changed-file guard, error discipline, RoadmapStore round-trip). ❌ Not tested end-to-end: the changed-file guard is unit-tested on its own helpers — a genuine mid-run write needs a second process. ❌ Nothing checks that docs/agent-access.md still describes what these functions do — the same prose-drift gap US-29 has.

US-32 · My AI assistant connects to my record — phase 0 shipped 2026-09-01; phase 1 built 2026-09-02, not yet deployed

As a user whose record is one JSON file, I can connect an AI assistant to it and say "add my new blood panel" or "what does my plan say about my LDL" — and it reads and writes my file by the app's own rules, because the tools are published by this repo rather than improvised by the model. Phase 0, shipped: a local stdio MCP server over a file path (Claude Desktop, Claude Code). Phase 1, BUILT and not yet deployed: the same tools behind a hosted connector, so a web ChatGPT or Claude user clicks connect and reaches their Dropbox folder — the clunky step getting-started.md admits. The full architecture, and Brad's decisions on it verbatim, are in mcp-architecture.md (rev 4, decided 2026-09-01).

  • AC1 (one tool surface): six tools — read_record, get_plan, add_measurement, add_lab_values, correct_value, report_feedback — defined once in packages/health-core/src/mcp-tools.ts as pure functions over (file, request) with a Zod schema each, so the local server and the hosted one offer the same thing — the hosted surface exposes every tool in that list, with no hosted-only subset to drift. Reads and writes are separate tools by construction: no catch-all with a method argument.
  • AC2 (the file is untrusted input): every call reads the record fresh through migrateFile — the same hardened boundary US-29/US-30 use — so the assistant never works from a cached copy and a file another device changed mid-session is seen, not assumed.
  • AC3 (the capability secret never leaves): reminderOptIn.token is stripped from every read (agent-access rule 12). It manages the user's reminder schedule on Brad's server; an assistant has no use for it and a copy in a chat transcript is a copy that can cancel someone's reminders.
  • AC4 (writes keep the rules): every write goes through record-edits.ts (US-31 AC1–AC6) — one active row per (metric, day), SI canonical measurements, the lab's own unit for lab values, catalogue keys, meta.updatedAt forward only. An add into an occupied slot is REJECTED and the refusal names the row holding the day and sends the agent to correct_value. add_lab_values is the lab-panel case: a batch, capped at 50 rows per call, all-or-nothing, so a half-imported panel never has to be told apart from a whole one.
  • AC5 (corrections are their own pathway): correct_value appends a row with correctsId and the ORIGINAL date and flips the old row to entered-in-error — never folded into an add. expectedValue — the agent stating what it believes it is replacing — is OPTIONAL on the local surface, where the user is watching their own file and the CLI has never asked for it, and REQUIRED on the hosted one, where it is what stops an agent writing from a stale or invented read. v1 writes clinical values only: no delete, and no medication, supplement, screening, document or profile write, because those are last-write-wins current state a second writer can overwrite.
  • AC6 (the bytes): the server writes through tools/record-io.ts — the same backup, changed-file guard and atomic replace the edit-record CLI uses (US-31 AC8), extracted so the two cannot lose the file in different ways.
  • AC7 (zero network, phase 0): the local server speaks JSON-RPC 2.0 over stdio and opens no socket — the four new files' imports are pinned by a guard to health-core sources, their siblings, zod and node builtins. No hosting, no OAuth, no key, and the product promise is untouched.
  • AC8 (get_plan presents honestly): the plan JSON carries a top-level instruction telling the model to keep each suggestion's hedged wording as written and keep the references attached to the suggestion they belong to. The thresholds, reasons and citations are unchanged — get_plan re-exposes existing derivations, so the three-file rule is not triggered.
  • AC9 (the assistant can file a bug): report_feedback turns a complaint into a prefilled GitHub issue URL for this repo — issues/new?labels=agent-feedback,<bug|feature> with the title and body encoded — and stops there. It makes no request, holds no token, touches no record, and submits nothing: the user opens the link, reads what it says and files it themselves. Keeping health values out of it is the tool description's job and the user's review is the real control; the one mechanical backstop refuses any title or detail carrying a number wearing a known unit ("2.1 mmol/L", "81 kg", "140 mmHg"), read off units.ts so a new metric's unit joins the guard for free. An over-long report is refused rather than handed to GitHub, which truncates a long query string silently. On the hosted surface it opens no Dropbox connection either: RECORD_FREE_TOOLS runs it before any record is loaded, which is the point — the likeliest moment to report a bug is the moment the record would not open.
  • Usage signal (declared honestly, per the constitution): none from us, by design — phase 0 runs on the user's machine against their own file, so any event we could count would break the promise, exactly as for US-29/30/31. What we can watch: Brad's own use as user zero, and unprompted outside interest (GitHub issues, stars, repo traffic). Weak and lagging. Phase 1 is where a real signal first exists — a hosted connector is a request to our server, so connection and tool-call counts become countable without any health value in them; that measurement is designed with phase 1, not before.
  • Phase 1 (BUILT, NOT DEPLOYED — the honest status): the code is on claude/us32-phase1 and is INERT in production. Every /mcp path and both .well-known documents return 404 while MCP_SEAL_KEYS is unset, so nothing changes for anyone until Brad sets the Fly secrets on health-tool-edu and points mcp.drstanfield.com at it (the operator steps are in deploy-runbook.md). Architecture and Brad's decisions verbatim: mcp-architecture.md.
  • AC10 (nothing per user is stored, anywhere): no table, no row, no session. The Dropbox refresh token is sealed into the bearer token the AI vendor holds — AES-256-GCM under a per-blob-type HKDF key, a 12-byte nonce, AAD binding the blob to one client and one audience, and fixed-bucket padding so the blob's length says nothing about the credential inside. We hold the key and no blob; the vendor holds a blob and no key. What DOES exist and is counted, not hidden: a per-machine authorization-code set, per-IP rate maps, a bounded client-metadata cache, and Fly's own proxy metadata. None is health data and none is a per-user row. What sealing does NOT protect: the blob the vendor holds is a live bearer against /mcp until it expires — no key needed. Split custody protects the DROPBOX credential inside it, not access to our endpoint.
  • AC11 (revocation is honest about what it cannot do): the access blob expires in 1 hour and the refresh blob in 90 days. Rotating MCP_SEAL_KEYS with no overlap kills every connection at once, and that is our ONLY server-side revocation — a per-user denylist needs state we refuse to keep. The real kill switch is the user's own: dropbox.com/account/connected_apps. Because Dropbox's app-folder scoping is tied to the app identity, unlinking there ALSO disconnects this website from the folder; that is disclosed on the consent screen, not hidden.
  • AC12 (the four mandatory corrections mitigations): expectedValue is REQUIRED on the hosted surface (optional on the CLI and the local server); a correction on a row older than 90 days is refused; add_lab_values is capped at 50 rows per call; and writes are bounded at 60 weighted writes per connection per hour, per machine, where a correction costs five adds. The allowance is keyed on the connection (the hash of the sealed provider refresh token), so minting extra access tokens buys no extra writes, and it comes back with the hour, so an honest user is never locked out. Corrected 2026-09-02 by review: the approved design put a lifetime pool inside the credential, spent by refreshing. It locked honest users out — fifty ordinary refreshes with zero writes exhausted it — and bounded nobody, because replaying one refresh blob mints a fresh access blob every time. It is deleted. The honest bound is a RATE, per machine, and the refusal now says so.
  • AC13 (the accepted residual, stated rather than softened): an injected agent reads first, so it knows every row id and value, and with correct_value it can silently falsify current values — each original flipping to entered-in-error, irreversibly — and get_plan will then generate a coherent, wrong protocol from the falsified record. Append-only prevents data LOSS, not data CORRUPTION. Brad accepted this knowingly on 2026-09-01, choosing protocol completeness, bounded by AC11. Vendor confirmation prompts are NOT counted as a boundary: the MCP spec calls annotations untrusted hints and "always allow" is one click.
  • AC14 (the front door): OAuth 2.1 with PKCE S256 only, our own consent screen — and the consent screen is ENFORCED, not merely displayed: pressing Connect mints a 32-byte nonce, seals the state naming it into a first-party __Host-mcp-state cookie (Secure, HttpOnly, SameSite=Lax, 10 minutes), and hands Dropbox the nonce alone. The callback requires the cookie, compares the echoed value to the sealed nonce timing-safely, and clears it; without the cookie it is a 400 page and no redirect. (Before this, found by review 2026-09-02, a state blob from an unauthenticated GET /mcp/authorize could be replayed into a forged callback and mint an authorization code with no consent at all.) Then RFC 8707 audience validation, RFC 9207 iss, and invalid_grant on every dead grant. The refresh lifetime is 90 days ABSOLUTE from consent — it used to slide forward on every refresh, so it expired for nobody. Clients arrive by client-id metadata document or by a self-contained DCR client id carrying its own HMAC — no registry, no row. The metadata fetch is an SSRF surface and is treated as one: https only, every resolved address public, zero redirects, a 5-second timeout, a 64 KB cap, application/json required, no credentials, and per-IP rate limiting BEFORE the fetch. Unauthenticated calls get 401 with WWW-Authenticate: Bearer resource_metadata="…"; the only unauthenticated documents are the two .well-known files.
  • AC15 (it is not a browser endpoint): no Access-Control-Allow-Origin is ever emitted, ALLOWED_ORIGINS is untouched, a present-but-foreign Origin gets 403, and localhost is on no list. GET and DELETE at the endpoint are 405, no Mcp-Session-Id is ever minted, and an incoming one — like Last-Event-ID — is ignored. No route logs a request URL, because code, state and code_verifier travel in query strings.
  • AC16 (consistency is the widget's, not a second implementation): every write goes through the same SyncManager read → migrate → merge → conditional-write → verify loop the widget runs, now living in health-core so both surfaces share it. The Dropbox conditional write sends strict_conflict, which is what stops a stale write re-creating a record the user erased. A record whose schemaVersion is newer than this server understands is out of reach in BOTH directions: the record is migrated before any tool sees it, so reads refuse too, and the refusal says so rather than claiming the record is readable. Known residual, unchanged from US-11: a RAW deletion in the Dropbox UI carries no eraseEpoch signal, so a stale writer legitimately re-creates the content.
  • AC17 (bounded, and honest when it refuses): request bodies are capped — 64 KB at the OAuth doors, 1 MB at /mcp, 413 over. /token is rate-limited per IP and tools/call per connection, both generously: a whole vendor's users arrive from one egress range, so a tight per-IP limit would lock out honest traffic rather than an attacker. The IP those limiters key on is Fly-Client-IP, which Fly's proxy writes, not X-Forwarded-For, which a client can forge. A malformed MCP_SEAL_KEYS or MCP_CLIENT_HMAC_KEY disables the feature (404) with one log line naming the variable and never its value, rather than turning every route into a 500. A record written by a NEWER app version refuses reads as well as writes — it is migrated before any tool sees it — and the refusal says that rather than claiming the record is readable.
  • Known spec deviation, documented not papered over: OAuth 2.1 requires single-use authorization codes and statelessness cannot enforce that across Fly machines. The per-machine set is best-effort; the window is 60 seconds, and redemption still needs the PKCE code_verifier, which never leaves the client.
