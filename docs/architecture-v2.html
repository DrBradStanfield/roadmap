Health Roadmap — Architecture (v2, local-first)

Last updated 2026-09-02. Live in production — both storefronts serve the v2 local-first build on /pages/roadmap, and the thin server runs React Router 7 on Fly (v361+). As of the §12 split (2026-06-24) the tool runs on two domains / two Shopify apps / two Fly apps from one codebase & one widget bundle: drstanfield.com is the education store (app shopify.app.edu.toml, Fly health-tool-edu) and microvitamin.com is the commerce store (app shopify.app.toml, Fly health-tool-app). This page is the single, self-contained source of truth for v2 architecture. The legacy v1 (Supabase-backed) shape is preserved at architecture.html for historical reference; the blow-by-blow of the migration (dated decisions, deviations, build log) lives in git history, not in a companion doc.
What changed in one sentence: the user's health data moved out of Brad's Supabase and into the user's own cloud (Google Drive / Dropbox / GitHub / self-host) as plain JSON files — Brad now stores no health data and can't read the user's cloud.

What this document is: a single visual map of how the v2 app fits together — the three build flavours, the local-first storage spine, the merge engine, the cloud backends, the thin server that survives, and the data path that deliberately never touches Brad's infrastructure.

What it isn't: a changelog or a build log. It captures architectural shape as it exists in code today. For the dated why behind each decision and the step-by-step migration record, read the git history; for agent-facing build/deploy instructions, see CLAUDE.md.

Companion — the product spec: user-stories.html is the user-perspective catalogue (20 stories: acceptance criteria, usage evidence, test status). This page answers how the system works; that one answers what it must do for users. Every feature or bug fix starts from a story there — the story-driven development pathway (Lane A fixes / Lane B new features) is codified in CLAUDE.md → Development Pathway. Grounding data: the 2026-08 usage audit and the weekly reports in docs/loops/.

New features must declare their usage signal before code is written. Every new story states which product_events funnel event (or existing metric) will prove people actually use the feature — the weekly product-health report then shows its adoption numbers and forces an explicit iterate-or-kill decision. This rule exists because the reminders feature was built without one and sat at 2 total opt-ins for months with nobody noticing. A feature that can't be measured can't be evaluated.
Accuracy note. This map was reconciled against the actual code at HEAD, not just the older design docs. Where the two diverged, code wins — those corrections are called out inline (e.g. the Pages build config is vite.config.standalone.ts, not a "pages" config; the Shopify build swaps only the storage module; crons self-start on import).

The big idea: local-first, user-owned cloud

v1 was a custodial app: Brad's Fly backend held a per-user JWT, wrote every measurement to Brad's Supabase, and RLS gated the rows. v2 inverts that. The valuable part of the product — calculateHealthResults() and the suggestion engine in packages/health-core — already ran entirely client-side. So the data can too.

Interpretation is the product

Google Health and Microsoft HealthVault died as passive vaults. The recommendation engine — not the database — is the product. The engine stays free and client-side; the reminder loop fixes the empty-vault abandonment problem.

Brad is not the custodian

Removing Brad as data holder sheds the privacy and HIPAA-custody burden, and preserves the guarantee that the app works even if Brad goes dark. The data path never reaches Brad's servers.

The grandma test

Every choice is stress-tested against a 70-year-old non-technical user who will never run a server, use a terminal, or store a recovery phrase. This is why there is no client-side encryption by default (a forgotten key = lost history forever) and why Dropbox is the recommended backend.

System diagram

The end-to-end v2 picture. The thick teal path — browser ↔ the user's own cloud — is the entire data layer, and it never crosses into Brad's infrastructure. Brad's thin server (orange) is optional and only handles things that genuinely need a server: AI calls he pays for, and the reminder scheduler.

Thick teal = the data path (app ↔ user's cloud), all client-side, never touching Brad. Orange dashed = optional thin-server AI + scheduling (content transits, is never stored). Red = the server explicitly cannot read the user's cloud; on the Pages build, AI calls go browser→Anthropic direct with the user's own key.

Trust boundaries (v2)

  • Browser — holds the powerful cloud OAuth token and (on Pages) the user's Anthropic key. Both live in localStorage/sessionStorage on the device only and are never synced or sent to Brad.
  • User's cloud — the system of record. Folder-scoped access (the app can only touch files it created). Brad has no credential for it.
  • Brad's thin server — trusted but deliberately starved of health data. It sees AI request content in-memory (never stored) and a reminder's due date + label + verified email + capability token — never the values or reasoning behind them.
  • Supabase — now holds only anonymized chat history (for training) and A/B events. RLS is deny-all; the service-role key lives in Fly secrets. No health tables remain populated.

Front doors × storage (two independent choices)

The single most clarifying idea in v2: where the app is served and where the data is stored are orthogonal. The same React app, built two ways, pairs with any of five storage backends.

Delivery (front door)

  • Two Shopify stores — the same theme extension on /pages/roadmap for both drstanfield.com (education) and microvitamin.com (commerce). The mainstream door; AI runs on Brad's server (free to the user). Each store is a separate Shopify app + Fly app but serves the identical widget bundle — see deployment topology.
  • GitHub Pages / self-host — the same app, statically hosted. The "works if Brad goes dark" door; AI is bring-your-own-key. Also the primary dev/test surface.

Storage (where the file lives)

  • Dropbox — recommended default (true refresh token, App-folder scope).
  • Google Drive — drive.file scope; needs the token-exchange endpoint.
  • GitHub — fine-grained PAT, one repo (advanced/dev).
  • Self-host — WebDAV + Basic auth (the only provider-proof option on iOS).
  • This browser only — localStorage, no sync (guest tier).

Server runtime — the RR7 migration (live)

The thin server was migrated Remix 2.x → React Router 7 (Shopify's recommended path: @shopify/shopify-app-react-router + react-router@7, shopify-api@13, session-storage-postgresql@6, @sentry/react-router). The client widget never imported Remix, so the migration touched only app/: json() sites became Response.json() / data(), RemixServer→ServerRouter, and the admin UI moved off Polaris React onto Polaris web components. Shopify Admin API is on 2026-04. RR7 is live in production (Fly v361+).

HIPAA scrub must survive the Docker image without the workspace. Sentry init runs in a root instrument-scrub.mjs loaded via node --import outside the bundle, so it cannot import the PHI-redaction helpers from @roadmap/health-core — .dockerignore excludes node_modules/ and dist/, and nothing rebuilds health-core's dist in the image, so that import would crash the server on boot and take HIPAA scrubbing down with it. The file is therefore a self-contained plain-ESM copy (COPY . ., relative import, zero workspace/dist dependency), guarded by a 4-test parity suite (instrument-scrub-parity.test.ts) that fails CI if it drifts from health-core's sentry-scrub.ts.
Risky server deploys must use --strategy canary, not the default rolling deploy. The RR7 cutover crashed on boot (a transitive @supabase/realtime-js bump hard-threw on Node 20's missing native WebSocket; local Node 22 hid it). Fly's default rolling deploy + health checks did not protect against a boot crash — it updated both machines to the broken image and took production down. Recovery was fly deploy --image <prev>; the fix was node:20-alpine → node:22-alpine, redeployed via fly deploy --strategy canary (a throwaway canary machine is health-checked first, leaving the serving machines untouched if it fails).

The module-swap mechanism

The whole local-first transformation rides on a Vite resolveId redirect: when any module imports ./api, the build rewrites it to ./roadmap-data. The replacement keeps an identical export surface, so the ~40 call sites in HealthTool.tsx never changed.

A local export of the same name shadows the export * re-export, so the shim overrides exactly the functions it needs (reads, writes, lifecycle, lead-capture) and inherits the rest. The Pages build adds two more swaps for the BYOK AI transports.

What the shim (roadmap-data.ts) overrides: lifecycle (initRoadmapStore, flushRoadmapStore[Sync]); all reads (loadLatestMeasurements, loadAllHistory, loadLabValues, getHealthDocuments, …) and writes (addMeasurement, correctMeasurement, saveMedication, saveScreening, bulkSaveLabValues, deleteUserData, …) against the file; reminders (getReminderOptIn, computeCurrentReminderSchedule); lead capture (getReportEmailCaptured, markReportEmailCaptured); and the report actions — getReportHtml (client-side print) and sendGuestReport(email,…), which POSTs only {klaviyoCapture:{email}} and ignores the health-data arguments. sendWelcomeEmail is a no-op; the mailto "Email Report" path is stubbed.

Local-first storage spine

Three layers: a pure data model + merge engine in health-core (so CI exercises the correctness-critical code), a browser I/O shell in widget-src/src/storage/, and one store the UI talks to.

Pure (health-core)

  • roadmap-file.ts — the RoadmapFile schema + createEmptyFile, stableStringify
  • merge.ts — mergeFiles(): deterministic, symmetric, conflict-free
  • migrate.ts — migrateFile() + SchemaTooNewError (normalise untrusted reads; forward-compat gate)
  • adapter.ts — the StorageAdapter interface every backend sits behind; memory-adapter.ts — the in-memory two-devices-one-cloud test double
  • file-adapter.ts — a StorageAdapter over one local file (Node fs, lock + backup), used by the CLI and local MCP server
  • roadmap-doc.ts — health-roadmap.json as a DocumentSpec, shared by the widget and the hosted MCP server so both migrate/merge the record identically
  • document-path.ts — the organised-archive folder+filename scheme for uploaded documents
  • lab-catalog.ts's labSlotKey() — normalises a lab name to its merge-dedup slot key

Shell (widget-src/storage)

  • dropbox.ts / drive.ts / github.ts / webdav.ts / local-storage-adapter.ts
  • pkce.ts, device-id.ts, chat-history-store.ts, self-test.ts

The RoadmapFile

One JSON file per user. Append-only arrays are never mutated; corrections add a row and flip the prior one to entered-in-error with a correctsId (the same FHIR Observation semantics v1 enforced in Postgres, now enforced in the file). Singletons (profile, screenings) carry a per-record logical clock.

{
  schemaVersion: 1,
  meta:    { createdAt, updatedAt, lastDeviceId, lamport, eraseEpoch },
  profile: { sex, birthYear, birthMonth, heightCm, unitSystem, unitOverrides,
             reportEmailCaptured?,        // monotonic Shopify-surface lead flag
             updatedAt, lamport },
  measurements:  [...],   medications/medicationHistory,
  supplements/supplementHistory,  screenings,  labValues: [...],
  documents:     [ { id, title, type, date, fileRef, contentHash, extractedText, … } ],
  reminderPreferences, reminderOptIn?,  recommendationSnapshots: [...]
}
  • meta.lamport — file-level logical clock, bumped to max+1 on every write.
  • meta.eraseEpoch — added after a real bug: "Delete All My Data" silently failed because the never-lose-data merge union resurrected deleted rows. A higher eraseEpoch now wins mergeFiles wholesale. RoadmapStore.deleteUserData() bumps it.
  • profile.reportEmailCaptured — set once when a user submits their email for the PDF; survives load→migrate (object spread) and merge (whole-profile LWW). See lead capture.
  • Published for agents — six surfaces over the same file. The contract: health-roadmap-file.schema.json (JSON Schema draft 2020-12, pinned to roadmap-file.ts by roadmap-file.schema.test.ts) and agent-access.md (US-29). The CLIs: tools/get-plan.ts, which turns the file into the plan offline — no server, no model (US-30) — and tools/edit-record.ts for contract-enforcing writes (US-31). The servers: tools/mcp-server.ts, a local stdio MCP over a file path (US-32 phase 0, shipped), and the hosted stateless server in app/lib/mcp*.server.ts (US-32 phase 1), live at mcp.drstanfield.com/mcp on health-tool-edu since 2026-09-02, Dropbox only — Google Drive support is built but stays inert until GOOGLE_DRIVE_CLIENT_ID/GOOGLE_DRIVE_SECRET are set on that Fly app. Both expose report_feedback from packages/health-core/src/mcp-tools.ts. Map and trust model: mcp-architecture.md.

The store + sync

RoadmapStore mirrors the old api.ts surface so the UI is oblivious to the swap, and adds local-first specifics: getPrefillInputs() (synchronous profile seed so a returning user's "Starting Info" renders collapsed on first paint), getReportEmailCaptured()/markReportEmailCaptured(), getReminderOptIn/setReminderOptIn/computeReminderScheduleNow, and flush()/flushSync(). app.tsx awaits initRoadmapStore before render.

The SyncManager runs one optimistic-concurrency loop per named document — health-roadmap.json and chat-history.json ride the same loop via injected DocumentSpecs (filename + migrate + merge). After every write it re-reads and confirms the file parses and lamport hasn't regressed — catching half-writes and corruption at the cost of one extra read per save (invisible on an app used a few times a year).

Merge & conflict model

Two devices editing the same cloud file must converge without losing data and without a CRDT library. The model is append-dominant, so the merge is simple and deterministic:

  • Measurements & lab values — slot-keyed by (metric, day); at most one active row per slot; entered-in-error is monotonic (never reverts).
  • Current-state singletons (profile, screenings, reminder prefs) — per-key last-write-wins by logical clock. Wall-clock is only a tiebreak, so two devices with skewed clocks still converge.
  • Logs (medication/supplement history) — unioned. Snapshots — deduped. eraseEpoch — highest wins the whole file.
Every write merges against the freshest read. Backends with conditional writes (Dropbox rev, GitHub sha, WebDAV ETag) raise a ConflictError on a stale token and the loop retries. Google Drive has no conditional write, so it degrades to last-write-wins — made safe because the loop always merges the latest read first.

Identity / auth

v1's three-layer auth (Shopify HMAC → per-user JWT → Supabase RLS) is gone from the data path. In v2, identity is the cloud account: the browser does client-side OAuth (PKCE) directly with Google/Dropbox; no Brad server is in the loop, and Shopify login is irrelevant to where data lives. The cloud token never leaves the device.

The server-side HMAC app-proxy verification still exists, but only as an anti-abuse front door on the AI endpoints (chat, lab-import-v2) and the Klaviyo capture — see Security model. It is no longer how the app knows who you are.

The data path never touches Brad

The core invariant. Reads and writes of health data flow only between the browser and the user's chosen cloud. No measurement, lab value, medication, or document ever transits Brad's server. The only things that reach Fly are: AI request content (in-memory, never stored) and a reminder's due date + label + verified email + capability token.

This is what makes the "works if Brad goes dark" guarantee real. If Fly is down: the app still loads (Pages build is static; the Shopify build is served by Shopify's CDN), still computes results, still reads/writes the user's cloud. Only the optional extras — server-side chat, server lab extraction, reminder scheduling — pause, and on the Pages build even chat and upload keep working via BYOK.

Brad's thin server — what it does and doesn't

Does

  • Chat for the storefront (free; shoppers won't paste API keys)
  • Lab PDF extraction for the storefront (extracted text transits; never stored)
  • Reminder scheduling — stores only verified email + due item + date + capability token
  • Google token exchange (stateless), Klaviyo capture, A/B events, feedback
  • Ops crons + the Discord/YouTube bots + the Polaris admin app

Doesn't

  • Store any health values, history, or reasoning
  • Hold any credential for the user's cloud
  • Mint per-user identity or gate features behind a paid tier (there is none)
  • Keep a read path for emails — no list, lookup, or search endpoint exists
  • Persist AI request content beyond the request

Honest positioning

The approved claim is "Your health data lives in the cloud account you already use and trust — not on our servers." It is deliberately not marketed as "encrypted" or "maximum privacy": there is no client-side encryption by default (a forgotten key is the worst failure mode for the grandma avatar), so Google/Dropbox can technically read the file. Self-host is the provider-proof path for the <1% who want it. Data minimisation, not de-clinicalisation: a reminder still says "your 5-yearly colonoscopy is due" — being specific is the point — but the server never keeps why.

Chatbot — server-proxied vs BYOK

The same chat UI, two transports chosen at build time. The Shopify build keeps chat-api.ts (app proxy → Brad's server, Brad pays). The Pages build swaps in byok-chat.ts (browser → Anthropic direct, user pays). Both send the user's plan as context — the data still comes from the local file, not a server lookup.

Per-store assistant display name

The assistant's display name is per-store, driven by a shop metafield so the same bundle reads differently on each storefront. Default is "Brad AI".

drstanfield (education) → "Brad AI"; microvitamin (commerce) → "MicroVitamin". Set per-store as a shop metafield; the widget bundle is identical — the name is data, not a build flag.

Data-editing via tool-use (the chatbot can pre-fill the form)

The chatbot can now propose edits to the user's roadmap using Anthropic tool-use, on both the server (storefront) and BYOK (Pages) paths. The tool definitions live in health-core/chat-edits.ts — propose_field_edit (a measurement/profile field) and propose_medication_edit — and the parsed intent (parseProposedEdits()) carries structured field / value / unit / date, never fuzzy text.

No health data is ever auto-committed for measurements: the widget pre-fills the real form, highlighted, and the user's Save is the confirmation. Medications save immediately with Undo. Negatives are guarded — a bare number prompts for a unit; a wildly out-of-range value asks to confirm; a normal question fires no edit. Covered by a dedicated tool-use harness (tools/test-tool-edits.ts, fixtures tools/test-tool-edits.json) plus a no-spend self-consistency check in chat-edits.test.ts.

Server pipeline (storefront)

  • chat-classifier.server.ts — short-circuits ~59% of turns past the router
  • chat-router.server.ts — LLM retrieval over the ~991-entry blog index (prompt-cached), returns 0–3 content handles
  • chat.server.ts — context assembly, system blocks, getChatCompletion, titles
  • platform-chat.server.ts — reuses the pipeline for Discord + YouTube

BYOK path (Pages)

  • byok-anthropic.ts — shared browser→Anthropic transport
  • Key hr_anthropic_key in localStorage, this device only, never synced

Training capture: only the storefront server chat is written to Supabase (anonymized). The BYOK/self-host chat is browser→Anthropic and is never sent to Brad.

Lab upload

PDF text/image extraction is client-side (the health-upload.js pdf.js + JSZip bundle, loaded on demand). Only the extracted text goes to an LLM. The extraction prompt lives in health-core/lab-extraction.ts and is imported by both the server route and the BYOK path so the two transports can't drift.

  • Storefront — /api/lab-import-v2, behind the app-proxy HMAC, per-IP + hard per-machine daily caps, nothing stored.
  • Pages — byok-upload.ts, browser → Anthropic with the user's key, a client-side queue (concurrency 2) in place of the Batch API.
  • The files themselves are kept and organised in the user's own cloud (v1 discarded them): AI classifies each into Lab results / Scans / Clinic letters / Other documents, named YYYY-MM-DD Title.ext so alphabetical sort is chronological. Content-hash dedup; nothing overwritten.

Reminders v2

Email-only, free, and website/server-only (no calendar/.ics, and it doesn't run on raw self-host, which has no provider-verified identity). The client computes forward due dates and pushes them; the server is a dumb scheduler holding no health data.

The email is provider-verified, never client-typed — the only address anyone can target is their own. Two tokens, never interchanged: the powerful cloud token stays on the device; a per-subscription capability token (stored raw, because the unsubscribe link must carry it) controls only the reminder schedule. A daily cron emails what's due; one-click unsubscribe (RFC 8058) deletes the row.

Route api.reminders-v2.ts; cron reminder-v2-cron.server.ts (lock reminder_v2_cron); table reminder_optin_v2. Group cooldowns: screening 90 d / blood test 180 d / medication review 365 d. The vocabulary is "opt-in", never "subscription" (which means paid products in this business).

Lead capture — Klaviyo + client-side PDF

The "Get Your Personalized Plan" button does exactly two things: (1) the email address goes to Klaviyo, (2) a PDF is built client-side. No health data reaches any server; there is no Resend report email.

  • Client — the shim's sendGuestReport(email,…) POSTs only {klaviyoCapture:{email}}; the PDF (getReportHtml → print window) is built first, inside the click's user activation. Gated to SHOPIFY_SURFACE — never fires on Pages.
  • Server — api.measurements.ts is gutted to a single survivor, handleKlaviyoCapture: validates {email} only, rate-limited 5/day/email, calls subscribeToKlaviyo (email-only, no profile properties), stores nothing.
  • Per-app Klaviyo (after the §12 split). Each Fly app reads its own KLAVIYO_API_KEY / KLAVIYO_LIST_ID secret, so a roadmap-guest email lands in the right account/list for the store it was captured on: the commerce app (health-tool-app, microvitamin.com) uses the microvitamin Klaviyo (the original drstanfield account, renamed); the education app (health-tool-edu, drstanfield.com) uses a new drstanfield Klaviyo account/list (list R5nrgP "Health Roadmap Guests"). live 2026-06-25 — edu secrets set to the new drstanfield key/list (distinct digests from prod); verified end-to-end (storefront capture → proxy → edu Fly → list 0→1→cleaned).
  • One-time flag — on capture, markReportEmailCaptured() sets profile.reportEmailCaptured in the user's own file. On return, the email box never reappears; instead an inline "Save as PDF" button renders in the "Your plan to discuss with your doctor" header (the same slot the logged-in print button used). The flag rides whole-profile LWW — a concurrent cross-device edit at the exact capture moment could drop it, but it's monotonic and low-stakes (the box reappears once; Klaviyo dedups).

What's separate, what's shared

Separate (per store)

  • A new private custom app (its own client_id) registered in org 222927919, kept as a new config variant shopify.app.edu.toml — the production shopify.app.toml (94c365…) is never overwritten.
  • A second Fly app health-tool-edu from the same Dockerfile, with its own SHOPIFY_API_KEY / SHOPIFY_API_SECRET (the new app's), its own SHOPIFY_APP_URL / app-proxy URL.
  • Bots are commerce-only. The edu Fly app omits the Discord + YouTube bot tokens, so only the commerce app (health-tool-app) runs those gateway/poller bots — the edu app boots without them.
  • Klaviyo is per-app. Each Fly app sets its own KLAVIYO_API_KEY / KLAVIYO_LIST_ID: commerce uses the microvitamin Klaviyo (the original drstanfield Klaviyo, since renamed to microvitamin); education captures roadmap-guest emails to a new drstanfield Klaviyo account/list (list R5nrgP). live 2026-06-25 — edu secrets set + verified end-to-end
  • Chatbot display name is per-store via the health_roadmap.chat_assistant_name shop metafield (drstanfield → "Brad AI", microvitamin → "MicroVitamin"). See chatbot.
  • Order scopes are kept on the edu app (read_orders + read_all_orders) so the chatbot's order-lookup path works there too.

Shared (Brad-global)

  • The same Supabase project, Anthropic key, and chatbot knowledge files — the chatbot's knowledge base is store-agnostic, so it works on the education store unchanged.
  • The same Postgres session store (SESSION_DATABASE_URL is identical on both Fly apps), so each store's offline OAuth session (offline_<shop> row in shopify_sessions) lives in one table. unauthenticated.admin(domain) resolves the right token by shop domain.
  • The app-proxy subpath /apps/health-tool-1 is reused, so the existing widget build — which hardcodes PROXY_PATH = '/apps/health-tool-1' in widget-src/src/lib/api.ts — works on the edu store with no rebuild.
Per-store crons on a shared Supabase. Both Fly apps run the same in-process setInterval crons (they self-start on module import). The trending cron targets the store named by the per-app secret SHOPIFY_SHOP_DOMAIN (prod falls back to microvitamin.myshopify.com; edu is set to sz5utw-1r.myshopify.com) and writes that store's health_roadmap.trending_articles shop metafield. Because the apps share Supabase, they would otherwise contend for the single trending_cron row in cron_lock — only one store's metafield would be written per day. So the cron picks its lock name by shop: prod uses trending_cron, edu uses trending_cron_edu (both seeded in rls-policies.sql). The edu store is new, so its trending payload is empty [] until it accrues ≥7d of landing-page sessions — the storefront's "Trending" sidebar has a graceful empty state.
Why a second app, not one multi-tenant server. The auth path is single-secret HMAC verification (app/shopify.server.ts / route-helpers.server.ts / local-first-route.server.ts). A second app instance keeps that code byte-identical, so the live commerce (microvitamin.com) roadmap cannot be touched by the education store, and vice versa. The alternative — one server resolving a per-shop secret at request time — was rejected: it rewrites the most safety-critical code on the live path for a store that doesn't need shared infrastructure.

Rollback: there is no JS rollback bundle. The legacy health-tool.js was retired on 2026-06-15 (bundle, entry, and config deleted), and even before deletion it was a dead end — its api.ts fetch functions targeted server endpoints and Supabase tables that the v2 teardown removed/purged, so re-pointing app-block.liquid at it would load a non-functional, data-less zombie. A genuine rollback now means reverting the v2 teardown commits and rebuilding the v1 stack from git history.

Security model

  • AI endpoints behind HMAC. /api/chat and /api/lab-import-v2 verify the Shopify app-proxy signature (verifyAppProxySignature(), ±10-min replay window, stale-timestamp rejected before crypto) — a cryptographic front-door check curl can't fake. This superseded the forgeable Origin allow-list.
  • Confidentiality is the absence of a read path, not the allow-list. No endpoint returns anyone's email; no list, lookup, or search exists. The Origin/CORS allow-list is anti-abuse only — and localhost is never on it (hard rule: a rogue local page must not be able to drive OAuth or server endpoints).
  • Rate limits + a hard daily $ cap bound AI abuse cost; per-IP limits + a 10-min block on the opt-in endpoint.
  • Two tokens, never interchanged (reminders): the cloud token stays on the device; the capability token controls only reminder dates.
  • BYOK key hygiene: the user's Anthropic key is localStorage-only, never synced; strict CSP and no innerHTML of untrusted content; users are advised to use a spend-limited key.
  • Supabase RLS is deny-all; the service-role key lives only in Fly secrets. Secrets are env-only and gitleaks-scanned in CI.

Rejected paths (don't relitigate)

  • Keep data in Brad's Supabase — the custodianship + HIPAA burden is the whole thing the pivot removes.
  • Client-side E2E encryption by default — the key-recovery landmine (forgotten key = lost history) fails the grandma test. Self-host is the provider-proof path instead.
  • A daily-use SaaS — contradicts intermittent-by-design (~95% of benefit for ~5–10% of effort, meaningful use every 2–3 months).
  • Self-hosted server as the default — makes the user the operator; fine as door B, fatal as door A.
  • OpenRouter-style AI aggregators — a third party in the data path with users' lab PII.
  • CloudKit / iCloud as the sync backend — Apple-only; would fragment data into two incompatible stores. (A future HealthKit iOS app would still sync via Drive/Dropbox.)
  • A paid feature tier — economics ride on supplements + the email list; never paywall the health advice.

Dangerous gotchas (v2)

Build behaviour belongs in the module swap, not component conditionals. Keep export surfaces identical across the three builds so shared components compile everywhere and the legacy bundle stays byte-stable. The only exception is an inline fetch the shim can't see (e.g. migrateGuestChat), which gets a LOCAL_FIRST/SHOPIFY_SURFACE component gate.
The Shopify config drifts. A bare shopify app deploy targets whatever config was last config use'd — so with both a production and an education app registered, the risk is shipping to the WRONG app (prod vs edu). Always shopify app config use shopify.app.toml first and verify the success banner names the app you intended (prod health-roadmap-<N>).
Crons self-start on import. Importing any *-cron.server.ts (even to call its stop*) starts it. Don't import a cron module from a non-server context.
Risky Fly deploys: use --strategy canary. The default rolling deploy + health checks does NOT protect against a boot crash — during the RR7 cutover it updated both machines to an image that crashed before binding :3000 and took production down. Canary (or bluegreen) health-checks a throwaway machine first, so a failed boot never touches the serving machines. The class of failure (a transitive dep throwing on the container's Node version, invisible to a newer local Node) is exactly what a boot rehearsal — or canary — catches.
CSS scoping across co-loaded bundles. The site-chat / chatbot bundles still ship their own CSS on the same pages, so any changed shared selector must be scoped under .health-tool, or health-site-chat.css can win by document order.
docs/products.md must stay a symlink (git mode 120000). The Fly deploy dereferences it for the Docker context and restores it with git checkout; if that restore is skipped, the next git add bakes the 680-line file into the repo and the chatbot's product context silently drifts.
Google Drive refresh tokens need a published OAuth app. In Testing mode they expire after 7 days — prefer Dropbox as the default for exactly this reason.
