Health Roadmap — System Architecture

Last updated 2026-05-18. Source of truth for project-wide architecture. For implementation detail, see the linked design docs in /docs/ and the per-area files in CLAUDE.md.
What this is: a single visual reference for how every part of the Health Roadmap app fits together — auth, data flow, the widget, the chatbot, lab upload, reminders, A/B testing, blog, and the database schema underneath it all.

What it isn't: a changelog or per-commit log. It captures architectural shape, not in-progress work. Update it when you add a new subsystem or change a flow, not every PR.

Who it's for: Brad (when returning to a feature after months), future contributors, and AI agents that need a high-level map before grepping. CLAUDE.md remains the canonical agent-facing instructions; this page is the map that goes with it.

System diagram

The end-to-end picture. Everything else in this document is a zoom-in on one of these boxes or one of these arrows.

Customer browser → Shopify edge (proxy + webhooks) → Fly.io Remix backend → Supabase + external APIs. Solid teal arrows are user traffic; gray are internal; red are outbound to 3rd parties.

Trust boundaries

  • Customer browser — never trusted. All identity claims must be re-verified server-side.
  • Shopify app proxy — HMAC signature is the only proof of customer identity. logged_in_customer_id comes from here, not from the body or headers the client controls.
  • Fly.io backend — trusted. Holds SUPABASE_SERVICE_KEY, mints per-user JWTs, calls Anthropic, sends email.
  • Supabase — enforces row-level security against auth.uid() in the JWT. Even if the Fly backend has a bug, RLS is a second line of defense.

Guest vs logged-in

The most important architectural split. Two completely different data paths share one UI.

Guest user

  • Storage: localStorage only. No server calls for measurements.
  • Auth: none. Anonymous.
  • Backend load: zero (chatbot is the one exception — guests can chat, get a scoped JWT).
  • Limits: data lost on browser clear; no cross-device sync.
  • UI signal: sticky "Create account to save" CTA banner in results panel.

Logged-in user

  • Storage: Supabase via app proxy + HMAC + per-user JWT. localStorage is a cache only.
  • Auth: Shopify customer login → logged_in_customer_id from HMAC-verified app proxy.
  • Sync: guest localStorage flushes to Supabase on first authenticated page load (see Data sync).
  • Features unlocked: reminder emails, lab upload, health documents, chat history, supplement tracking.
  • UI signal: "Welcome back, {firstName}" + "Save New Values" buttons appear.

Auth flow (HMAC → JWT → RLS)

Three nested layers of verification. Each independent — a bug in one doesn't compromise the others.

Three-step auth: Shopify session cookie → HMAC-signed proxy request → per-user Supabase JWT → RLS enforcement. Client never holds the JWT — it lives only on the server.

Key files

  • app/lib/supabase.server.ts — dual-client setup, getOrCreateSupabaseUser(), createUserClient(userId)
  • app/routes/api.measurements.ts — reference for all proxy endpoints
  • app/shopify.server.ts — authenticate.public.appProxy

Critical invariants

NEVER trust client-supplied identity. The logged_in_customer_id must come from the HMAC-signed query string injected by Shopify, never from the body, custom headers, or a cookie the client controls. authenticate.public.appProxy() is the only entry point that proves customer identity.
NEVER expose an endpoint without HMAC verification. Every /api/* route under the app proxy path runs authenticate.public.appProxy() first, before any DB read or LLM call.

Data sync (guest → logged in)

Guests accumulate measurements in localStorage. The first time they log in, that data must flush to Supabase exactly once and never duplicate on subsequent visits.

Sync-embed and widget are mutually exclusive: only one runs per page. Critical cleanup must be synchronous because users frequently navigate away mid-request.

The auto-redirect mechanism

Shopify customer accounts live on shopify.com, not the storefront. Once a user has logged in, their storefront session can expire while the Shopify account session stays alive. We use the health_roadmap_authenticated localStorage flag as the bridge: if it's set but the page has no storefront customer ID, we redirect once per browser session to re-acquire the session cookie. The flag is only ever set after we've confirmed cloud data exists, so we never redirect a "real" guest.

Do not modify sync-embed cleanup logic without reading the whole flow. Three localStorage operations must run synchronously and unconditionally. Putting them in .then() or .finally() breaks auto-login. See "Dangerous gotchas" below.

Widget two-phase load

To eliminate jank, the widget renders in three stages: a static skeleton (no JS), localStorage cache (instant), then the authoritative API response (~100–300ms later).

Three-phase load minimises perceived latency. The hasApiResponse flag is the critical safety: without it, cache-based auto-saves would overwrite cloud data during the 100–300ms window before the API response arrives.

Measurements (FHIR Observation)

Time-series blood test & vitals data follows FHIR R4 Observation semantics. Stored values are never mutated; corrections create new rows that supersede old ones.

Storage rules

  • All values stored in SI canonical units (kg, mmol/L, mmol/mol IFCC, etc.).
  • Conversion handled in units.ts.
  • status = active | entered-in-error. Only active rows feed results.
  • corrects_id self-FK points at the row this one replaces.
  • source: manual, lab_import, lab_import_edited, manual_correction, apple_health, fitbit.

Server-side invariants

  • enforce_measurement_correction_only trigger blocks any UPDATE that changes more than status.
  • validate_corrects_id_ownership trigger rejects cross-user corrections.
  • Partial UNIQUE index on (user_id, metric_type, recorded_at) WHERE status='active' — guarantees one active row per slot.
  • Duplicate active insert → 23505 → API returns 409.

Correction flow

  1. User clicks a value in BloodTestTimeline, types new value, hits Enter.
  2. Widget calls correctMeasurement(oldId, newValueSI).
  3. correct_measurement SECURITY DEFINER RPC atomically:
    • UPDATE old row: status = 'entered-in-error'
    • INSERT new row: source='manual_correction', corrects_id = oldId
  4. Audit log records MEASUREMENT_CORRECTED with {oldId}.

Medications & supplements

Both follow FHIR MedicationStatement shape and use the same append-only history pattern.

Medications

  • medications table: mutable current state, one row per (user_id, medication_key).
  • medication_history: immutable append-only log, FHIR effective_start/effective_end periods.
  • Keys: statin, ezetimibe, statin_escalation, pcsk9i, bempedoic_acid, glp1, glp1_escalation, sglt2i, metformin.
  • drug_name stores the actual drug (e.g. atorvastatin) plus dose. Status values: none, not_yet, not_tolerated — never yes.
  • status is auto-derived in deriveMedicationStatus(); immutable trigger blocks edits to history rows.

Supplements

  • Same shape: supplements (mutable) + supplement_history (immutable).
  • Logged-in users only.
  • Brand's own products (MicroVitamin, MicroVitamin+, Sleep, Omega-3) appear as quick-add chips.
  • Delete = soft-delete: status set to stopped, history row appended.

Why the dual-table design

The mutable current table makes day-to-day reads (and the suggestion algorithm) trivial — one row per medication. The immutable history table preserves the full timeline for chart annotations (e.g. "you started atorvastatin here") and for any future EHR export that needs the FHIR period semantics. Triggers trg_medication_history_immutable and trg_supplement_history_immutable enforce that history rows can never be edited or deleted.

Lab upload pipeline

User uploads PDF, image, or ZIP → client extracts text/images → Anthropic Haiku extracts structured values → user reviews/edits → bulk save. Files themselves are never stored.

Three storage destinations: 11 core lab metrics → health_measurements (FHIR Observation, SI canonical), other flexible values → lab_values (as-reported), and any uploaded documents → health_documents (markdown only, originals discarded).

Two processing paths

  • Pipeline mode (<20 files): client extracts concurrently (3 at a time), feeding a queue of LLM workers (concurrency=5). Files in front of the queue extract while files in the LLM are still being processed.
  • Batch mode (≥20 files): client extracts all sequentially, then sends one batch POST; Anthropic batch API processes in parallel server-side. ~50% cheaper.

Source field distinctions

  • lab_import — LLM extracted, user accepted without edit
  • lab_import_edited — LLM extracted, user edited at review time
  • manual_correction — post-save correction via the timeline UI
  • manual — typed directly into the form

Health documents

For non-lab uploads: scans, clinic letters, discharge summaries, pathology reports, vaccination records. Stored as markdown only — the canonical form for both LLM tokenization and browser rendering.

  • Table: health_documents (document_type, title, document_date, content_md ≤200KB, metadata JSONB, source_file_name)
  • Immutable: no UPDATE policy. Delete + re-upload to fix mistakes.
  • NOT cached in localStorage (kept lean — loaded from API on demand).
  • If LLM detects a screening-relevant document (e.g. colonoscopy), the review UI requires explicit checkbox confirmation before pushing the screening date forward.

A/B testing

Metafield-driven, zero-flash variant assignment. Admin creates a test in the Polaris dashboard → Supabase row written → shop metafield health_roadmap.ab_config updated → storefront app-block renders all variants in HTML → inline <script> picks one from localStorage before first paint.

Pipeline

  1. Admin creates test in app.ab-testing.tsx (Polaris).
  2. Supabase ab_tests row created; metafield health_roadmap.ab_config written via Shopify Admin GraphQL.
  3. app-block.liquid reads the metafield server-side; renders all variants.
  4. Inline script picks variant from localStorage['hr_ab'] (or assigns randomly + writes).
  5. Widget React calls trackABImpression(), then trackABConversion() on goal events.
  6. api.ab.ts writes to ab_events.
  7. Dashboard computes two-proportion z-test via ab-stats.ts.

Constraints

  • Only one test active at a time. Activating new test pauses old.
  • Pausing/completing deletes metafield → storefront falls back to default text.
  • Targets: heading, subheading. Adding a new target requires updates in 4 places (see CLAUDE.md).
  • localStorage keys shared between Liquid + React: hr_ab, hr_vid, hr_ab_imp_<testId>.

Blog & trending

Blog content lives on Shopify (HTML articles, served via the storefront's theme). A daily cron at 03:00 UTC computes which articles are "trending" and writes the top 5 to a shop metafield; the theme reads the metafield and renders the trending sidebar.

  • Sources: Shopify sessions dataset via ShopifyQL — current 7-day window vs prior 37-day baseline → fold-change ratio.
  • Cron: trending-cron.server.ts, 60-min polling tick, fires after 03:00 UTC, guarded by cron_lock.
  • Output: shop metafield health_roadmap.trending_articles (JSON array of {handle, score}).
  • Content sync to chatbot: docs/blog/*.md are LLM-readable copies. New posts written by the /blog-post skill in claude_business. Full rebuild: npx tsx scripts/build-blog-content.ts.
  • Inline CTAs: <div class="roadmap-embed"></div> markers in blog HTML split the article and inject Roadmap CTAs via Liquid.
  • Sidebar: replaced MicroVitamin promo with email signup + Roadmap CTA; per-article copy via Shopify metafields.

Gotchas

ShopifyQL sessions means landing-page sessions, not page views. Internally-linked articles get underweighted. Use the cron_lock table with a NOT NULL lock_date — PostgreSQL NULL != $today is NULL (falsy), and the cron silently never fires.

Database schema

22 tables total in supabase/rls-policies.sql. Every table has RLS enabled; every policy is scoped by auth.uid(). The diagram below groups them by purpose.

22 tables across 5 functional clusters. All user-scoped tables use the same RLS pattern (auth.uid() match). Triggers + partial UNIQUE indexes enforce structural invariants the application can't be trusted to maintain.

Adding a new measurement metric type

This is the trip-wire. CREATE TABLE IF NOT EXISTS is a no-op on existing tables, so column-level checks need explicit ALTER TABLE migration. Missing steps cause silent data loss (the row inserts but never appears in reads). Required checklist for any new metric or screening type:

  1. types.ts — add field to interface
  2. mappings.ts — add case to relevant *ToInputs() / diffInputs*
  3. rls-policies.sql — add to BOTH CREATE TABLE CHECK and ALTER TABLE migration; run migration in Supabase
  4. suggestions.ts — add logic
  5. InputPanel.tsx — UI controls
  6. HealthTool.tsx — handler dispatch
  7. mappings.test.ts — round-trip tests

Audit logging

  • Every write logs to audit_logs via logAudit().
  • Events include: measurement created/corrected, medication updated, supplement updated, account deleted, reminder sent.
  • user_id nullable: on account deletion, logs are anonymised (user_id set to NULL) before the auth user is deleted. Audit trail survives; PII does not.
  • HIPAA-aligned: no health values in audit messages, just IDs and event types.

Security model

Defense in depth

  1. Shopify CDN handles DDoS at the edge for storefront assets.
  2. App proxy HMAC verification rejects all unsigned requests at Remix entry.
  3. Per-customer in-memory rate limit (60 req/min) at app layer.
  4. Supabase RLS as backstop — even with a broken backend, no cross-user reads possible.
  5. Triggers enforce structural invariants (immutability, correction-only updates).

Non-negotiable rules

  • NEVER trust client-supplied identity. Only HMAC-signed logged_in_customer_id.
  • NEVER expose unauthenticated API endpoints.
  • NEVER add Access-Control-Allow-Origin: *.
  • NEVER store the Supabase service key client-side. Only the Fly backend holds it.
  • NEVER skip HMAC verification "just for testing".

Account deletion flow

POST /api/user-data with { confirmDelete: true }. Rate-limited 1/hour per customer. Deletion order (each step waits for the previous to complete):

  1. health_measurements
  2. medication_history → medications
  3. supplement_history → supplements
  4. health_documents, lab_values, screenings
  5. chat_messages → chat_conversations → chat_match_events
  6. Anonymise audit_logs (user_id → NULL)
  7. Delete profile
  8. Delete auth user
  9. Clear in-memory user cache (restart machine if needed)

Dangerous gotchas (consolidated)

Things that have caused real outages, silent data loss, or hard-to-debug failures. Each violates an architectural invariant.

Sync-embed cleanup must be synchronous. Three localStorage operations (remove guest data, set auth flag, set session flag) must run before any fetch(). Moving them inside .then() breaks auto-login for users who navigate away mid-request.
Sync-embed and widget sync are mutually exclusive. Sync-embed exits early if #health-tool-root exists. Never run sync logic from both paths simultaneously — duplicate writes and audit log explosion.
CREATE TABLE IF NOT EXISTS is a no-op on existing tables. Adding a column to a CHECK constraint requires ALTER TABLE migration + Supabase SQL execution. Otherwise inserts succeed but reads silently fail.
Never DROP TABLE on Supabase. PostgREST caches OIDs. Use ALTER TABLE ADD COLUMN IF NOT EXISTS. If you must drop: restart the Supabase project.
Never shopify app dev. Creates a dev preview URL that overrides production. Fix: npx shopify app dev clean.
fly deploy from project root only. Dockerfile is at root; running from a subdir silently uses wrong context. Don't use --app flag — let it read fly.toml.
Symlink resolution before fly deploy. Fly's remote builders can't follow local symlinks. docs/products.md must be dereferenced to a temp file, removed, then real file moved into place. Don't use cp -L file file — cp follows the destination symlink, never replacing it.
cron_lock NULL pitfall. PostgreSQL NULL != $today evaluates to NULL (falsy). Seed lock_date with a real date, never NULL — otherwise the cron silently never fires.
Strip .map files before shopify app deploy. Sourcemaps push the extension over the 10MB CDN limit. npx shopify app deploy --force in CI/non-interactive shells.
In-memory user cache after deletion. If you delete a profile/auth user, restart the Fly machine to clear the cache. Otherwise stale rows haunt the next request.
Don't make the health_roadmap_authenticated flag conditional. The flag is the bridge between Shopify customer sessions (on shopify.com) and storefront sessions. Removing or delaying it breaks auto-login.

How to update this document

Update when an architectural shape changes — new subsystem, new external service, new top-level table cluster, or a flow gets restructured. Not per-commit. Aim for the map to stay accurate at the level of "what services exist and how do they talk", even if file paths drift.

If you find yourself adding a paragraph that's specifically about what changed recently, that belongs in a git commit message, not here.
