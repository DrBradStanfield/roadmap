2 · Reuse / what's new

2a — Direct reuse (no new code)

  • All .bt-* CSS classes — live styles.css already has them. Prototype's inline CSS block is dropped.
  • Sparkline from BloodTestTimeline.tsx — exported so StartingInfoVitals can import it. Identical visual to the matrix (area fill + 1.5px line + dashed-empty state).
  • NumericInputCell — used for the draft value input. Carries the iOS WebKit fixes (size={1}, etc.) and the validation / status preview / error-message footer.
  • statusOf / previewStatus / blockBadNumericKeys / validateTypedValue from lib/blood-test-cell.ts — registered with new vitals metrics (see §3).
  • handleSaveLongitudinal(bloodTestDate, explicitMeasurements) — already accepts an arbitrary metric→SI map. The vitals matrix Save just calls onSaveBloodTestBatch(date, { weight: 80 }) (same path the blood-test matrix uses).
  • Live renderProfile() + renderBirthInfo() — unchanged. The Starting Info header + demographics summary live there already; the new component is purely the per-metric rows that replace the current vitals fields below.

2b — Genuinely new (couldn't avoid)

  • StartingInfoVitals + a small internal VitalsRow. Live's BloodTestTimeline assumes one shared scroll context and shared dates across rows. Vitals has per-metric dates, so each row is its own self-contained mini-matrix with its own .bt-cell-strip scroller + scroll-to-rightmost effect.
  • Combined date+value draft cell. Live splits DraftDateCell (header, date-only) from DraftCell (body, value-only) because the matrix's column-header is shared. Vitals needs both date and value in the same cell. Implementation composes the same JSX/CSS pattern (day on line 1, year+icon button on line 2, hidden <input type="date">, showPicker()) but doesn't reuse DraftDateCell as a black box.

3 · Decisions made on the fly (not in spec)

3a — Vitals status thresholds live inside StartingInfoVitals.tsx, not lib/blood-test-cell.ts

DECISION The shared statusOf(metric, siValue, sex?) can't classify weight / waist / BP without extra user context (height for IBW + WHtR, age for the BP <120 vs <130 cutoff). Rather than widen the signature for two callers, the per-metric thresholds live as local helpers inside StartingInfoVitals.tsx:

  • Weight → calculateIBW(heightCm, sex) from health-core/calculations.ts; ok = within IBW − 5 to + 2 kg, warn up to + 5 kg, bad otherwise.
  • Waist → WHtR cutoff at 0.5 × heightCm (AACE / NICE); ok at or below, warn up to + 8 cm, bad above.
  • BP → target = <120/80 (age < 65), <130/80 (≥ 65); ok below target, warn within target+10/+5, bad above. Mirrors the live getBpTargetText() in InputPanel.tsx:692.

If we ever ship a fourth consumer that wants the same vitals status, extract to health-core at that point.

3b — Reuse NumericInputCell for the draft inputs, with showStatusPreview={false}

DECISION The shared input cell handles iOS WebKit fixes (size={1}), validation, range errors, and the fixed-height footer slot. But its built-in status preview calls previewStatus() from blood-test-cell.ts, which returns null for vitals metrics. Two options:

  1. Extend previewStatus to know about vitals (and pass height/age in).
  2. Disable the input cell's preview and render the status tick from the vitals row itself.

Chose (2) — keeps blood-test-cell.ts tightly scoped to blood-test metrics and avoids growing its API. The vitals row computes previewStatus locally and renders the tick in the .bt-cell-foot slot after the input.

3c — New vitalsHistory state in HealthTool, populated by the same fetch as bloodTestHistory

DECISION The matrix needs full history (5+ readings per metric) to be meaningful. previousMeasurements is only latest-per-metric, so that won't do. loadAllHistory(200) already fetches every measurement; bloodTestHistory just filters that result. Added a parallel vitalsHistory filtered to weight | waist | systolic_bp | diastolic_bp. No additional API call.

3d — BP is two rows in the DB but one cell in the UI

DECISION The DB stores systolic + diastolic as separate health_measurements rows sharing a recorded_at. The matrix pairs them by date in a useMemo that walks vitalsHistory, groups by ISO date, and yields { date, sys, dia } triples for the BP row only. Save sends both metrics in one onSaveBloodTestBatch(date, { systolic_bp, diastolic_bp }) call.

4 · Tradeoffs

4a — Each row owns its own scroll container (no scroll-lockstep)

TRADEOFF Live blood-test matrix has one big scroll element; all rows scroll together because they share dates. Vitals rows have independent dates, so one scroll-per-row is correct. Cost: 3× the scroll containers, 3× the scroll-to-rightmost effects. Benefit: rows render correctly when each metric has different date counts (the common case).

4b — Save UX is per-row (one Save button per metric) + auto-save on blur/Enter

TRADEOFF Live matrix uses a single CommitTickButton at the top that commits all drafts at once (because the date is shared). Per-row save matches the per-row data model — you save Weight independent of BP. The downside: three buttons can clutter the card if all three drafts are filled. Mitigated by only showing the button when that specific metric's draft is valid.

ADDED Auto-commit on blur (and Enter) for each row, mirroring the blood-test panel. Behaviour:

  • Simple metrics (weight, waist): blurring the value input with a valid value triggers commit() → save + clear.
  • BP: blur on either sys or dia triggers commit(), but commit() bails when valid is false. So sys-blur-with-empty-dia is a no-op; dia-blur with both filled saves both metrics in one batch.
  • Re-entry guard via the saving state — two concurrent blurs (e.g. mouse-down outside the row blurs both BP inputs at once) won't fire two requests.
  • The Save button stays for explicit confirmation — clicking it goes through the same commit().

3e — Mirror typed draft values to inputs[field] via new onFieldChange prop

DECISION Two reasons we need a callback into the parent's inputs state:

  1. Live suggestions. The suggestions engine reads from effectiveInputs (current form + previousMeasurements fallback). Without mirroring, typing a new weight in the draft cell doesn't update suggestions until Save.
  2. Guest persistence. Guest users' cloud save is a no-op (handleSaveLongitudinal early-returns when not logged in). The legacy inline weight/waist/BP inputs persisted via the parent's localStorage auto-save on inputs change. To preserve that path, the matrix calls onFieldChange(field, siValue) on every keystroke. Same approach BloodTestTimeline uses (see InputPanel.tsx:960 — onFieldChange={updateField}).

The Save button is still rendered (and disabled-via-omission for guests by isLoggedIn && valid) — for logged-in users it commits a measurement with the chosen date.

3f — Use .bt-value-num (not .bt-cell-value-num) for the saved-value text

FYI Picked the wrong class name on the first pass. The live blood-test matrix uses .bt-value-num (defined at styles.css:4645); my new CSS adds only the BP-modifier .bt-value-num--bp for the smaller "128/80" font-size.

5 · Things changed from the prototype

5a — Inline CSS dropped; uses styles.css directly

Prototype had its own <style> block mirroring the bt-* classes. The live widget already has them, so the component renders unstyled JSX and inherits all bt-* styles. New rules added at the end of styles.css: .bt-vitals-card, .bt-vitals-row, .bt-vitals-save, .bt-vitals-date-btn, .bt-vitals-date-icon, .bt-vitals-bp-inputs, .bt-vitals-bp-sep, .bt-value-num--bp.

5b — Header (renderProfile()) stays where it lives

Prototype's LiveStartingInfoHeader was a one-off mirror of renderProfile(). In the live port, the header keeps rendering from InputPanel.tsx's existing renderProfile() (above the matrix component). No duplication.

5c — Birth Info (renderBirthInfo()) still renders below the vitals card

The prototype showed the demographics summary inline; in the live widget Birth Month / Birth Year are still a separate group below the vitals matrix (the existing collapse-animated prefill-fields-wrapper). Untouched.

5d — Reference-label units follow the user's display preference

Prototype hardcoded the labels (Target: 80.5 kg). The port uses formatDisplayValue(metric, si, unitSystem) + getDisplayLabel so US users see Target: 178 lbs instead. Same source-of-truth functions the rest of the widget uses.

5.6 · Bug found during QA + fix

FIX First deploy (-704) rendered the matrix with cells sized to content (~91px) instead of the intended 116px name + 82px value + 54px trend columns. Cause: the live .bt-cell-name uses width: var(--bt-name-w), and the same CSS variables (defined on .bt-timeline) weren't in scope because my StartingInfoVitals wrapper used only .bt-vitals-card. With var(--bt-name-w) unresolved, browsers ignore the width property → cells fall back to flex-shrink: 0 content sizing. Fix in -705: add bt-timeline to the wrapper class so the matrix-wide CSS variables (cell widths, ink colors, row min-height) cascade in. Two-character JSX change; no logic touched.
